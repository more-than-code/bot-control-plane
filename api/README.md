# API (`api/`)

The API part of [bot-control-plane](../README.md) (formerly the bot-api-server repo), started as `deploybot-server api` (or as `bot-api-server`). Go service for Deploybot: Google OAuth sign-in and sessions, projects and members, join tokens and host credentials, the bot-agent WebSocket, metrics ingest into Postgres `deploybot`, live probes, and the REST API used by the console (`../console`) and the MCP gateway (`../mcp`).

- Design: `docs/design.md`
- Contracts (frozen, do not edit here): `../docs/contracts/api-v1.md`, `../docs/contracts/oauth-v1.md`, and `../docs/contracts/agent-protocol-v1.md`.

## Run locally

Run the commands below from this `api/` folder. Requires Go 1.27+ and a PostgreSQL 18 database with TimescaleDB. The server does not create tables on startup. `--migrate` does not create roles, schemas, or the TimescaleDB extension.

1. Copy `.env.example` to `.env` and replace every `CHANGE_ME` and `dummy-google-*` value. The example file is not a working configuration.
2. Create empty databases named `deploybot` and, for integration tests, `deploybot_test`. Do not create the extension yourself.
3. As a superuser, start a new session and run `migrations/roles.sql.example` as the first command in that session. Run it once connected to `deploybot`, and again connected to `deploybot_test`. Replace the `CHANGE_ME` passwords first. The script creates `deploybot_owner`, `deploybot_migrator`, and `deploybot_api`, installs `timescaledb`, and creates the `app` and `metrics` schemas. It is not applied by `--migrate`.
4. Apply the numbered migrations as `deploybot_migrator`:

   ```sh
   set -a
   source .env
   set +a
   go run ../cmd/deploybot-server api --migrate
   ```

   `--migrate` reads `BOT_API_MIGRATE_DATABASE_URL`, runs `SET ROLE deploybot_owner`, and refuses to continue when `timescaledb` is missing. It is the only path that runs the numbered SQL files.
5. Start the API with `DATABASE_URL` pointing at `deploybot_api`:

   ```sh
   go run ../cmd/deploybot-server api
   ```

   It listens on `BOT_API_LISTEN`. `GET /health` returns `{"status":"ok"}`.

`DEPLOYBOT_TEST_DATABASE_URL` is for integration tests only. Those tests refuse to run unless the connected database name is `deploybot_test`, and that database must already have had `roles.sql.example` applied. Leave the variable unset for `go test ./...`. `DEPLOYBOT_TEST_API_DATABASE_URL` is the `deploybot_api` login on that same test database (the Connect GitHub and readiness tests need no other variable: GitHub and the registries are faked with `httptest`); with `DEPLOYBOT_TEST_DATABASE_URL` set it is required, because `TestValueRequestsAsAPIRole` and `TestConnectRequestsAsAPIRole` run the value-request and connect-request writes as the role the server uses (a missing column grant fails there, not in production).

## Organizations and host access

Hosts belong to an organization, and projects get access to hosts (api-v1 v1.24, `../docs/contracts/api-v1.md`; spec in the umbrella `docs/spec-organizations.md`). An org has one owner, admins and members. Org owners and admins manage the org's hosts, join tokens, members and per-project host access, and act as `admin` on every project in the org without a member row (D-1); a project reached that way shows `role` `admin` and `via` `org`. Only the org owner or the project owner may rename, delete or transfer a project. A project member does not have to be in the org (D-2). An org member without a project role sees no project and no host. A new user gets a personal org at first sign-in (D-8). `GET /v1/me` returns `orgs`, and each project carries `org_id`, `via` and `org_name` (the project's org name, also for a project member who is not in the org; api-v1 v1.37 item 4; only `/v1/me` sends it).

`host_access` rows give a project `metrics` or `deploy` on a host of its own org; a project in another org is `not_found` (D-3). `PUT /v1/hosts/{id}/access/{project_id}` `{level}` is an org admin upsert, `GET /v1/hosts/{id}/access` lists the rows, and `DELETE` is org admin+ or an admin of that project leaving; it is `conflict` while the project still has live services on the host, unless `?reassign=org` makes them org-level (`project_id` null). An org-level row is not claimed back: after `?reassign=org`, or for a discovered row whose name matches a catalog entry, the service stays org-level (seen by org admins only), and redeploying the entry does not re-own it; the agent's owned report is refused and audited once a day as `service.owner_conflict`. Permissions follow spec-organizations §3.2: seeing the host, metrics, processes and snapshot need org admin+ or any access; the services list, service reads, logs, probe and health history need org admin+ (every service, org-level ones included) or a `deploy` project (its own services); deploy, run, stop, rename and health-check edits need org admin+ or an admin of a `deploy` project (its own services); credential revoke, access and join tokens need org admin+. Anyone else is `not_found`. Per-entry host approvals are gone: a `deploy` grant plus the host's root-owned `runner.toml` `projects` allowlist are the gates, and a run or deploy without deploy access is `forbidden` `this project has no deploy access to the host` (or `not_found` when the caller cannot see the host). `/v1/hosts/{id}/shares*` and `/v1/hosts/{id}/catalog-approvals*` answer 410 `gone`; since v1.26 (migration 0016) their storage is gone too.

Join tokens belong to an org (`POST|GET /v1/orgs/{id}/join-tokens`, `DELETE .../{token_id}`, org admin+) and may carry `grant: {project_id, level}`, applied as an access row when the host enrols. Host names are unique per org. The project routes `POST|GET|DELETE /v1/projects/{id}/join-tokens` stay for one release: org admin+ of the project's org, and the token grants that project `deploy`. Project delete no longer revokes hosts: it removes the project's access rows, revokes unused tokens that grant it, and marks its services gone. Org delete (owner) revokes every host of the org. Host events are audited with `org_id`; `GET /v1/orgs/{id}/audit` lists them for org admins. `Host.project_id`, `relation` and `share_level` were removed in api-v1 v1.26; clients read `org_id` and `access_level`. `programs.projects` is returned only to org admins.

`migrations/0015_orgs.sql` (applied by `--migrate`) adds `orgs`, `org_members` and `host_access`, `org_id` on projects, hosts, join tokens and audit rows, and backfills: projects named in the org mapping go to its orgs, every other project to one personal org per project owner (`u-` and 12 hex digits of the owner id, named "<owner name>'s org"). Hosts follow their former owning project, the former owner gets `deploy`, same-org shares become access rows (a cross-org share is reported and left in `host_shares`), and discovered services with no Deploybot owner become org-level. Org slugs cannot be renamed in phase 1. `hosts.project_id`, `host_shares` and the approval tables stayed for one release so v0.2.29 could run after a rollback; 0016 drops them.

The mapping is a reviewed JSON file named by `BOT_API_ORG_MAPPING_FILE`, read only with `--migrate`: `{"require_all_projects": true, "orgs": [{"slug", "name", "owner_email", "projects": [<project slug>, …]}]}`. `--migrate` puts it in the session setting `deploybot.org_mapping` on its single connection before applying files (a setting needs no database privilege; 0015 copies it into a scratch table it drops at the end). An unknown project slug, an unknown or disabled owner, a bad org slug, one org with two names or owners, or (with `require_all_projects`) a live project left out raises, and nothing of 0015 is applied. While 0015 is pending, `--migrate` refuses to run without `BOT_API_ORG_MAPPING_FILE`: set it to the reviewed file, or to `none` for the default rule (dev, tests and CI, and `.env.example`). Each notice the migration raises is logged, including the cross-org share report.

Release order: stop the API, take a dump, run the before report, run `--migrate` with `BOT_API_ORG_MAPPING_FILE`, run the after report, then start v0.2.30. Never migrate while v0.2.29 is serving. The report queries, including the cross-org share list, are in `docs/design.md` (D38). Unused join tokens made before the release by a project admin who is not an owner or admin of the project's new org stop working after the migration: a token works only while its creator owns or administers the org. An org owner or admin makes new ones.

`migrations/0015_orgs.down.sql` is not applied by `--migrate`, and it no longer works once 0016 has run (the objects it writes back are gone). Before 0016, to switch back to v0.2.29: stop the API, take a dump, run `psql -v ON_ERROR_STOP=1 -f migrations/0015_orgs.down.sql` as `deploybot_owner`, switch `current` to v0.2.29, start the API. It runs in one transaction and deletes its own `schema_migrations` row. A live host keeps its `project_id` when that project is live and has `deploy` access; otherwise it takes the live `deploy` project granted first; with none, the host is revoked (credentials and services too). It never falls back to a metrics-only or deleted project for a live host. Access rows of other live projects become `host_shares` rows, same-org shares without an access row are removed, and cross-org shares stay. Org-level services take the host's project, used org tokens their grant or host project, and unused tokens without a project are deleted. It reports revoked hosts and rewritten shares with `RAISE NOTICE`, restores the `NOT NULL` constraints and drops the org tables and columns. Orgs, org members and org tokens made after the release are lost, and audit rows that have only an org lose it.

`migrations/0016_orgs_phase2.sql` (api-v1 v1.26, organizations phase 2) is forward only and applied by `--migrate`. It drops `host_shares` with its `host_shares_not_owner` trigger and function, `catalog_host_approvals`, `hosts.project_id` and the `hosts_project_name_unique` constraint; `hosts_org_name_unique` (names unique per org) stays. Before dropping, it logs a `migration notice` with the number of share rows (and how many were cross-org, without access) and approval rows it removes, and, when there are cross-org shares, a second notice listing them as `host_id -> project slug (level)`. `join_tokens.project_id` and `service_confirmations.project_id` are left as they are on purpose (backlog). It does not need `BOT_API_ORG_MAPPING_FILE`: `--migrate` asks for that only while 0015 is pending. Ship it only after phase 1 (v0.2.30) has been live and checked. Release order: stop the API, take a dump, run `--migrate`, start the new release; never migrate while an older release is serving, because v0.2.31 and earlier read the dropped column. Never apply 0015 and 0016 in one run on data you care about: run to 0015 (on its release), read its notices, then continue. There is no down script: the rollback is restoring that dump and pointing `current` back at the previous release. Access grants, orgs and other writes made after the dump are lost on that restore.

Before and after the v0.2.30 release, ops runs the read-only report in `docs/design.md` (D38); it reads `hosts.project_id` and `host_shares`, so it does not run after 0016: projects, members and roles, hosts and per-project access. 0015 renames a later duplicate host name inside one org (the first 54 characters, `-`, the first 8 characters of the host id, ordered by `enrolled_at`, then id) and records each rename as a `system` audit row. The after report lists every renamed host; production should have none:

```sql
SELECT a.detail->>'from' AS old_name, a.detail->>'to' AS new_name, a.host_id, o.slug AS org, a.at
FROM app.audit_log a
LEFT JOIN app.orgs o ON o.id = a.org_id
WHERE a.action = 'host.migration_rename'
ORDER BY o.slug, a.detail->>'from', a.host_id;
```

## Service names

A service keeps the discovered `name` the agent uses as its key. People set `display_name` with `PATCH /v1/services/{id}` and body `{"display_name": "<name>" | null}`. The name is trimmed, then it must be 1–64 printable characters. An empty string is `bad_request`. `null` clears it. The same name on one host, ignoring case, is `conflict`. The permission is the service edit capability (api-v1 v1.24): an org owner or admin, or an admin of a `deploy` project renaming a service of its own project. The audit action is `service.rename`, including when the caller is denied. The agent stores the account that owns the listening socket in `owner_user` and never writes `display_name`. A later discovery batch updates `owner_user` and leaves the name.

`GET /v1/projects/{id}/services` lists that project's own services on hosts where it has `deploy` access (api-v1 v1.24). `metrics` access adds no rows, and org-level services are never in a project list. The caller must reach the project (a member, or an org owner or admin); anyone else gets 404. `q` is a case-insensitive substring over the display name, discovered name, kind, host name, owner, and ports. `%`, `_`, and `\` match literally. `sort` is `name` (the display name, or the discovered name when the display name is null), `host`, `kind`, `status`, or `last_seen`. Name order is the byte order of the lowercased label, not the database locale. `dir` defaults to `asc`, and to `desc` for `last_seen`. The payload is `items`, `next_cursor`, `prev_cursor`, and `total`. The cursor is bound to `q`, `host_id`, `sort`, `dir`, and `view`. `include=health_checks` adds `health_checks` to every row, the same objects and order as `GET /v1/services/{id}` and `[]` when there are none; any other `include` is `bad_request` `invalid include`, and `include` is not part of the cursor (api-v1 v1.18). `GET /v1/hosts/{id}/services` orders by name in byte order (`COLLATE "C"`), like every other name sort, so Postgres and memstore agree. That list is otherwise unchanged apart from `display_name` and `owner_user` on each row.

`migrations/0004_service_names.sql` adds the two nullable columns and a unique index on `(host_id, lower(display_name))` where the name is not null. It does not change grants. `--migrate` does not apply `migrations/0004_service_names.down.sql`. That script drops the columns and the unique index. Names typed by people are lost. The project index from 0003 stays. After a hand run, delete the applied row before `--migrate` will apply 0004 again:

```sql
DELETE FROM app.schema_migrations WHERE name = '0004_service_names.sql';
```

`gone_at` is when a service was missing from its host's latest complete services report, or `null` when that report included it. Presence uses the stored name, so a matching catalog entry is kept under the entry name. A `services` frame is that host's full set when every element is valid, and an empty array is an empty set. In the same transaction, rows left out that are not already gone get `gone_at` set to the report time, and rows in the report have `gone_at` cleared. A row that is already gone keeps its time. Other hosts are not touched. `display_name`, health checks, and ids stay as they were. A mix of valid and invalid elements still stores the valid rows and clears their `gone_at`, and does not mark any other row gone. An all-invalid array, or a `services` value that is absent or JSON `null`, is not a report. `hello.services` follows the same rule when `services_complete` is absent or `true`. `services_complete: false` and JSON `null` write nothing and do not change presence. A non-bool fails the frame. `GET /v1/projects/{id}/services` takes `view`: `all` (the default), `deploybot` (`source` is `owned` or `declared`, gone or not, except a gone owned row whose catalog entry was deleted, which only `all` lists), or `deploybot_and_discovered` (those rows plus discovered rows that are still present). Any other value is `bad_request`. `q`, `host_id`, `sort`, `dir`, `limit`, `cursor`, and `total` apply inside the view. A cursor from one view is `bad_request` on another. `sort=status` lists present rows before gone rows, in both directions. `GET /v1/hosts/{id}/services` and `GET /v1/services/{id}` include `gone_at` and do not take `view`. Revoking a host sets `gone_at` to that revoke time on its rows that are still present, in the same transaction (`0012_revoked_host_rows.sql` backfills hosts revoked earlier), and `view=deploybot` and `view=deploybot_and_discovered` exclude rows whose host is revoked (`view=all` still returns them). A services report that places an item as `discovered` ends ownership of an existing `owned` row (`source` becomes `discovered`, `catalog_entry` becomes null, `project_id` becomes the host's project) and keeps the row id, `display_name`, and health checks; a `declared` row is not changed by a report.

`migrations/0008_service_gone.sql` adds nullable `services.gone_at`. On each host, a row whose `last_seen_at` is earlier than that host's newest `last_seen_at` is backfilled with `gone_at = last_seen_at`. Rows tied for that newest time stay null. Grants are unchanged. `--migrate` does not apply `migrations/0008_service_gone.down.sql`. That script drops the column. Presence is lost. After a hand run, delete the applied row before `--migrate` will apply 0008 again:

```sql
DELETE FROM app.schema_migrations WHERE name = '0008_service_gone.sql';
```

## Health checks over MCP

`PUT /v1/services/{id}/health-checks` still replaces the set immediately for a console session and pushes `config_update`. That replace locks the service row. A console session ignores `idempotency_key`. An `api_delegated` session must send one. After the same permission, access, and body checks, that call changes nothing and returns 202 `{"confirmation_id","plan","expires_at"}`. The plan names the service label (the display name, or the discovered name) and the host. The label and every HTTP path are Go-quoted (`strconv.Quote`). The host name is not quoted. A tcp check is `tcp <port>`. An http check is `http <port> <quoted path> every <interval> s`. A check with `enabled` false ends with ` (disabled)`. A tcp check that shares a port with an http check adds `(tcp <port> is redundant with http <port>)`. The set is still applied as given, including that tcp check. `POST /v1/confirmations/{confirmation_id}` reads `catalog_confirmations` first, then `app.service_confirmations`, then `app.catalog_write_confirmations`. Confirm compares the current set, marks the plan used, and replaces the checks in one transaction that locks `app.services` (`SELECT … FOR UPDATE`). A set that changed before that transaction commits is `conflict`, and the plan stays unused. Unknown, used, expired, and foreign ids are `not_found`. A matching confirm pushes `config_update` and returns `{"checks":[...]}`. Audit rows are `health_checks.confirmation_issued` (service, host, and check count) and `health_checks.replace` with `via` `mcp`. The audit `service` value is the raw label, not the quoted plan text.

`migrations/0011_service_confirmations.sql` creates that table. The row stores the normalized checks, because the confirm body does not send them again. `deploybot_api` may select, insert, and delete, and may update only `used_at`. `--migrate` does not apply `migrations/0011_service_confirmations.down.sql`. That script drops the table. Pending plans are lost. Nothing they named was applied yet. After a hand run, delete the applied row before `--migrate` will apply 0011 again:

```sql
DELETE FROM app.schema_migrations WHERE name = '0011_service_confirmations.sql';
```

## MCP OAuth

This process is the OAuth authorization server MCP clients use (`../docs/contracts/oauth-v1.md`, api-v1 v1.4). A public client registers at `POST /oauth/register`. A client that asks for `client_secret_post` or `client_secret_basic` is registered as a public client (`none`, no secret, PKCE) and told so in the response; any other method except `none` is refused (oauth-v1 v1.5). Each refused registration logs one INFO line with the error code and the failed rule, never the request's values. The person approves at the console. `POST /oauth/token` then issues an MCP access token (one hour) and a rotating refresh token (30 days). A second use of that code revokes the whole grant family, including later refreshes and delegated API tokens. The MCP server exchanges a live MCP access token for a five-minute API token. Those exchanges are not counted against the token endpoint's per-IP limit; a missing or wrong client secret is. An MCP access token, an MCP refresh token, or a legacy `mcp` session presented to any `/v1/*` route is `401` with code `invalid_token`. The device flow (`POST /v1/auth/device/token`) issues an MCP access token for 30 days, in a grant family for the pseudo-client `deploybot-cli`. Looking up, approving, or denying a device code needs a console session.

An `api_delegated` session is refused, before membership is checked, on project create, rename, and delete; member add, role change, and remove; ownership transfer; join-token create and revoke; invite create and revoke; host credential revoke; host access put and delete; every org write (create, rename, delete, members, transfer, projects, join tokens); and service display-name patch. It is also refused on the console-only reads of org members, org and project join tokens, org audit and host access, and on both notification routes (`GET /v1/me/notifications`, `POST /v1/me/notifications/read`, api-v1 v1.37); `GET /v1/me`, `GET /v1/orgs/{id}`, `GET /v1/orgs/{id}/projects` and `GET /v1/orgs/{id}/hosts` stay allowed (api-v1 v1.24 item 10). The response is 403 `forbidden`. Nothing is written. One audit row is `delegated.denied`, `decision` `denied`, `via` `mcp`, `error_code` `forbidden`, with detail `{"route":"<method pattern>"}` and null `project_id` and `host_id`. Snapshot, probe, catalog logs, status, and parse, sign-out, and `POST /v1/confirmations/{confirmation_id}` stay allowed. Routes that already plan a write or require a console session keep that behavior. A mutating `/v1` route added later is refused for this session until its route-table value says otherwise.

`BOT_API_PUBLIC_ORIGIN` is the issuer. A trailing slash is removed. `BOT_API_MCP_RESOURCE` is the audience clients must send: the MCP endpoint URL `<mcp origin>/mcp`, exactly as the MCP server publishes it (e.g. `http://localhost:8091/mcp`); it is not trimmed. `BOT_API_CONSOLE_ORIGIN` is where `/oauth/authorize` sends the browser (`/oauth/consent?request=…`). When `BOT_API_MCP_RESOURCE` is set, `BOT_API_MCP_CLIENT_SECRET_FILE` is required before the process opens the database. The file must be a regular non-symlink file with mode `0600`. The first line is the plaintext secret for client id `bot-mcp-server` (a trailing CR is removed; a leading space is kept). That line must be at least 32 characters. A shorter line refuses to start, and the error does not include the secret. The database stores only the SHA-256 of that line. Leave `BOT_API_MCP_RESOURCE` empty to start without that client.

`migrations/0005_mcp_oauth.sql` adds the OAuth tables, the session columns (`audience`, `grant_id`, `client_id`, `code_id`, `rotated_at`), widens `sessions.kind`, inserts `deploybot-cli`, and expires every live `kind = 'mcp'` session. It grants `deploybot_api` select, insert, update, and delete on the four new tables. `--migrate` does not apply `migrations/0005_mcp_oauth.down.sql`. Run that file by hand as `deploybot_owner`. It deletes `mcp_access`, `mcp_refresh`, and `api_delegated` sessions, restores the old kind check, and drops the new columns and tables. Legacy `mcp` rows stay expired. Clients, grants, codes, and pending requests are lost. Then delete the applied row before `--migrate` will apply 0005 again:

```sql
DELETE FROM app.schema_migrations WHERE name = '0005_mcp_oauth.sql';
```

## Project invites

An owner or admin creates a link with `POST /v1/projects/{id}/invites`. The body is `role` (`admin` or `viewer`), optional `expires_in_sec` (3600–2592000, default 604800), and optional `max_uses` (1–50, default 1). The 201 response is the invite plus `token` and `url`. Those two fields are not returned again. `url` is `<BOT_API_CONSOLE_ORIGIN>/invite/<token>`. A trailing slash on the origin is removed. If the origin is empty, create returns 500 and does not store a token. `GET /v1/projects/{id}/invites` lists every invite for that project, newest first, including expired, revoked, and used-up rows. `DELETE /v1/projects/{id}/invites/{invite_id}` sets `revoked_at`. A second delete keeps the original timestamp. An invite that belongs to another project is `not_found`.

`POST /v1/invites/lookup` and `POST /v1/invites/accept` take `{"token":"..."}`. Both require a console session. Any other session kind is 401 `unauthorized`. Lookup and accept share a limit of 30 requests a minute per user and 60 a minute per source IP. Past either limit the response is 429 `rate_limited`. Lookup does not change the invite or the membership. An unknown, malformed, expired, revoked, or used-up token is `not_found`, and those responses are the same body. Accept runs in one transaction. Someone who is already a member gets their current role, and `uses` stays unchanged. Anyone else is added with the invite's role and `uses` increases by one. Concurrent accepts never go past `max_uses`.

The plaintext token is not stored, not logged, and not written into audit detail. Audit actions are `invite.create`, `invite.revoke`, and `invite.accept`. Deleting a project deletes its invites. Contract: `../docs/contracts/api-v1.md` (v1.5). Behaviour: `docs/spec-project-invites.md`.

`migrations/0006_invites.sql` creates `app.invites`. `deploybot_api` may select and insert, and may update only `uses` and `revoked_at`. Soft-delete does not fire the foreign key, so the migration adds `app.invites_delete_for_project`, which runs as `deploybot_owner`. A real `DELETE` of the project still cascades. `--migrate` does not apply `migrations/0006_invites.down.sql`. Run that file by hand as `deploybot_owner`. It drops the helper and the table. Memberships already created by an accept stay. Invite links stop working. Then delete the applied row before `--migrate` will apply 0006 again:

```sql
DELETE FROM app.schema_migrations WHERE name = '0006_invites.sql';
```

## Project catalog

An owner adds a program with `POST /v1/projects/{id}/catalog`. The body is `name`, `kind` (`program`), `command`, `shell`, `dir`, `run_as`, and optional `env`, `port`, and `restart`. `name` is immutable. `POST /v1/projects/{id}/catalog/parse` previews the split (`exec`, `args`, `env`, `command_display`) and does not store a row. A program body that contains top-level `secret_env`, and any `kind` other than `program` or `image`, returns 501 `not_implemented`. An image body is `name`, `kind` (`image`), and `spec`. An image `name` must not end with `-`, `-prev`, or `-old`, which the agent uses for its kept and rollback containers (`bad_request` `invalid name`). Program fields on an image, or a `spec` object on a program, are `bad_request`. Image entries, env sets, and registries are in the next section.

The server splits `command` on POSIX words. Quotes and backslash escapes are kept. With `shell=false`, a pipe, operator, redirect, `$`, backtick, glob, or a first word of `cd` is `bad_request`. Leading `KEY=value` words move into `env`. With `shell=true`, the line is not split: the program runs as `/bin/sh -c`, and that line is not scanned for environment names. Keys that start with `LD_` or `DYLD_`, and `NODE_OPTIONS`, `NODE_PATH`, `BASH_ENV`, `ENV`, `IFS`, `PYTHONPATH`, `PYTHONSTARTUP`, `PERL5OPT`, `PERL5LIB`, `RUBYOPT`, and `RUBYLIB`, are `bad_request` with the message `this variable changes what the program runs`. Hoisted `KEY=value` words are checked the same way. `spec_hash` is the SHA-256 of the canonical spec JSON.

A new program entry grants admins run, stop, restart, and logs, and grants viewers logs. The owner of a program can always run, stop, restart, read logs, and read status. `PUT /v1/projects/{id}/catalog/{name}/permissions` replaces the grant list. A `user:` subject must be a current member and must not be the owner. At most 100 grants. `deploy` is a stored action for image entries only.

`GET /v1/projects/{id}/catalog` and `GET /v1/projects/{id}/catalog/{name}` include `last_deployed_at` (api-v1 v1.21): RFC3339, or `null` when there is none. For an image entry it is the newest `started_at` of its image deploys on any host and with any outcome, started via `console` or `mcp`. For a program entry it is the newest allowed `program.run` audit row for that entry name in the project, via `console` or `mcp`, at or after the entry's `created_at`, so an entry re-created under an old name starts at `null`. An allowed run that then failed or found the host offline still counts. Agent rows (automatic restart, rollback, give-up), denied runs, stop, and restart never count. The list stays in name order and makes one store call for all visible entries (at most one query per kind). The field is read-only: a write body that contains it is `bad_request` `invalid json`, like any unknown field. The replace response (`PUT /v1/projects/{id}/catalog/{name}`, console session) also carries it, with one query; the replace is committed and audited first, so if that read fails the response is still 200 with `null` (the list and `GET` return the error instead). A create response, and the delegated catalog-write confirm response (create or update), carry `null`. Delete returns no entry.

A program entry may also take `env_sets` and `secret_env` (api-v1 v1.22), with the image rules: at most 8 sets of the same project, `secret_env` at most 64 keys as `<set>.<KEY>`, and at most 64 keys after the merge. Precedence is `env_sets` in order, then `secret_env`, then `env`. Inline `env` still refuses a secret-looking key with `use secret_env`. The stored spec always has both fields (`[]` and `{}` when unused). When a set is referenced, `spec_hash` adds `env_keys`, the two fields, and `env_values`: a digest of the plain (`is_secret: false`) values of the keys that take part (every key of a set in `env_sets`, and each `secret_env` target). So adding or deleting a key, changing a plain taking-part value, or marking such a key secret re-hashes the entry; a secret value change does not. Image entries hash key names only, as before. A `secret_env` key may not be one of the variables that change what runs, extended for secret values with `GIT_SSH`, `GIT_SSH_COMMAND`, `GIT_ASKPASS`, `SSH_ASKPASS`, the Java, Python, `GCONV_PATH`, `DOTNET_STARTUP_HOOKS`, CA certificate and proxy variables (`bad_request` `this variable changes what the program runs`). An entry without sets keeps its v1.6 hash. Deleting a set a program uses is `conflict`.

Run of an entry with sets needs a host whose hello sent `programs.secrets` (else `bad_request` `this host's agent does not support program secrets`) and the server secrets key (else `unavailable`). `program_start` then carries the resolved `env` and `secret_keys`; an entry without sets keeps the v1.6 frame. A resolved spec over 64 KiB is `bad_request` `the resolved environment is too large for one task`. Result lines of run, logs and status are redacted with the entry's secret values (shown as their preview) before the keyword rule; logs of such an entry without the key are `unavailable`. Restart reuses the host's stored spec, so a changed value takes effect at the next Run: after changing a secret, Run the entry again (Restart keeps the old value, and the API then redacts with the new one, while the agent still redacts the old one). Before any task and before the idempotency claim, a Run is also refused (`bad_request`, audited as a denied `program.run`) when a key whose value comes from a secret set key is in that extended list, or when a key that looks secret comes from a set key that is not marked secret (`<KEY> looks like a secret but is not marked secret in set <set>; mark it secret`).

When the host's hello sent `programs.projects` (its `runner.toml` allowlist, api-v1 v1.23), a program Run and an image deploy, rollback or restart for a project not in the list are `forbidden` `this host's allowlist does not include project <slug>`, before any task. With an older agent the list is unknown and nothing changes. `Host.programs.projects` is returned only to org owners and admins (api-v1 v1.24 item 1); every view has `project_listed` (`null` when unknown). An agent `policy_denied` refusal of any task kind reaches clients as `forbidden` `the host refused this under its policy (runner.toml)`.

`HostPrograms.shared_networks` (api-v1 v1.25 item 2) is `[{name, subnet, projects}]` from hello, or `null` when the agent did not send it. `parsePrograms` stores the programs as disabled when the list has more than 8 networks, a duplicate or invalid name, a subnet that is not a canonical RFC 1918 IPv4 prefix of length 16–28, more than 32 member slugs, or a duplicate or invalid slug; a null member list reads as `[]`. `projectsView` gives org owners and admins in a session (not delegated) the whole list; every other caller, delegated sessions included, gets only the networks that list the project in view, without `projects`. With no project in view (`GET /v1/hosts/{id}` for a caller in several projects with access, or a delegated `GET /v1/orgs/{id}/hosts`) that is `[]`; `null` stays `null`.

`POST .../run`, `/stop`, `/restart`, `/logs`, and `/status` take `host_id`. Run, stop, and restart also take `idempotency_key`. A non-member is `not_found` before the body is read. Invalid JSON and an invalid `host_id` are `bad_request` before the grant. A member who lacks the action is `forbidden` even when the key or `lines` are invalid. The key format and `lines` (1..1000) are checked after that grant. Status is allowed when they hold any action. The entry's project must have `deploy` access to the host (api-v1 v1.24 item 4). Without it the answer is `forbidden` `this project has no deploy access to the host` when the caller can see the host, and `not_found` otherwise. There is no approval step. The host's `programs` policy must be present, enabled, and list `run_as`. When `allow_shell` is false, shell mode and an exec whose base name is `sh`, `bash`, or `dash` are `forbidden` with message `shell is not allowed on this host`. An offline host is `unavailable`. Policy denials and an offline host are not stored as idempotency responses.

A console session runs the action. An `api_delegated` session, the token MCP uses on `/v1/*`, gets HTTP 202 for run, stop, and restart and does not touch the agent. The body is `confirmation_id`, `plan`, and `expires_at`. `POST /v1/confirmations/{confirmation_id}` takes `{"idempotency_key"}`. That key must equal the key from the original request. The same `api_delegated` bearer may confirm. An invalid key is `bad_request` and does not look up the id. A key that does not match is `conflict` with message `idempotency_key does not match the request that issued this confirmation`, and does not consume the token. The confirmation row stores only the SHA-256 of the id. The idempotency response keeps the 202 body, including `confirmation_id`, until confirm stores the outcome. The id is single use, lasts five minutes, and only the same user can redeem it. An unknown, used, expired, or foreign id is `not_found`. A lost grant, a policy failure, an offline host, or a spec change after the 202 does not consume the token. Logs and status do not ask for confirmation.

Run, stop, and restart insert the idempotency row before acting. The row is the user, the key, and the request hash, with no response yet. A second request with the same key while that response is empty is `conflict` with message `request in progress`, even when its hash differs. After the outcome, including a failed dispatch, the status and body are stored. The same request replays that body for 24 hours and does not act again. A finished row with a different hash is `conflict`. The request hash is the SHA-256 of compact JSON with keys `action`, `entry`, `host_id`, and `project_id`. It does not include `spec_hash`, so the same POST still replays after a replace. Confirm still compares the confirmation's `spec_hash`. A replay of a 202 does not create a second confirmation. Logs and status are not idempotent. The agent receives `program_start`, `program_stop`, `program_restart`, `program_status`, or `program_logs`. Strings in a payload `lines` array are redacted with the cmdline redactor before the HTTP body and before the idempotency write. `policy_denied` from the agent is `forbidden`.

`GET` and `POST /v1/hosts/{id}/catalog-approvals`, and `DELETE` of one entry, answer 410 `gone` (api-v1 v1.24 item 4). There is no approvals table since 0016 (api-v1 v1.26), so a spec change has nothing to void.

The agent hello may include `programs`. That object is stored on the host and returned as `Host.programs` (`null` when the agent sends none). A service report with `owner: {kind:"program", project, entry}` is stored as `source=owned` when that slug is a live project of the host's org with `deploy` access and has that catalog entry (api-v1 v1.24 item 6). `catalog_entry` and the service name are the entry name. Otherwise the service is `discovered` and org-level (`project_id` null). `systemd_unit` is used as that discovered name only when it matches `^[a-z0-9][a-z0-9._-]{0,62}$`. Otherwise the reported name is kept.

Audit rows are `catalog.create`, `catalog.update`, `catalog.delete`, `catalog.permissions`, `program.run`, `program.stop`, `program.restart`, and `program.confirmation_issued`. Delegated calls are `via=mcp`. Logs and status write no audit row. A denied run, stop, or restart records the host, `detail.entry` (the catalog name), and `Result` set to the envelope code (`forbidden` or `unavailable`). Env values and confirmation ids are not stored in the detail. Contract: `../docs/contracts/api-v1.md` (v1.6 and the v1.6.1 amendments) and `../docs/contracts/agent-protocol-v1.md` (v1.3 and the v1.3.1 amendments). This server enforces the v1.6.1 environment denylist. The helper socket and unit hardening in v1.3.1 belong to the agent. Behaviour: `docs/spec-project-catalog.md`.

`migrations/0007_catalog.sql` creates the catalog tables and adds `hosts.programs` and `services.catalog_entry`. `app.idempotency_keys.status_code` and `response` are nullable together: both null while a request is in progress, both set when the outcome is stored. `deploybot_api` may select, insert, and delete. It may update only the columns the server changes. `--migrate` does not apply `migrations/0007_catalog.down.sql`. Run that file by hand as `deploybot_owner`. It drops the new columns and tables. Running units are not stopped. Then delete the applied row before `--migrate` will apply 0007 again:

## Catalog images

An owner creates an image entry with `POST /v1/projects/{id}/catalog` and body `name`, `kind` (`image`), and `spec`. `command_display` is the normalised image reference (`docker.io` and `library/` made explicit, and a missing tag becomes `:latest`). `spec_hash` is the SHA-256 of canonical JSON `{"env_keys","kind","spec"}`. `env_keys` hashes the sorted key names of each referenced env set. A value change does not change the hash. Adding or removing a key does. Replacing the entry with a new hash does the same. Validation errors name the field and do not include the image, a command, an env value, a volume target, a user string, or a set name.

An `api_delegated` session validates an image create, replace, or delete and returns 202 `{confirmation_id, plan, expires_at}` without writing the entry. The plan lists the fields that will change, including inline env values, an entrypoint when set, and a restart policy when it is not the kind's default. It omits env-set values, secret_env values, and file contents. Caller-controlled text is Go-quoted unless it is a plain token. A program create, replace, or delete is `forbidden` with message `program entries are edited in the console`. That refusal, and a delegated permission change or catalog env route, is audited `denied` with `via` `mcp`. Delegated denials of the set routes use `env_set.list`, `env_set.get`, `env_set.replace`, or `env_set.delete`. Key put and key delete are refused before the handler and audited as `delegated.denied`. `POST /v1/confirmations/{id}` reads `app.catalog_write_confirmations` after the earlier confirmation tables, applies the stored spec on the console write path, and marks the plan row used (api-v1 v1.32 item 1: a used row stays until it expires, so the next confirm of it can say so). Applied `catalog.create`, `catalog.update`, and `catalog.delete` rows use `via` `mcp` whichever session confirms them. Issuing the plan writes `catalog.write_confirmation_issued`. Storing a plan deletes rows that expired more than 7 days ago (`store.RequestKeep`), so a recently expired id still answers the expired `conflict`. Project delete deletes that project's rows. Permission changes and catalog env routes stay console-only. The plan no longer counts host approvals (api-v1 v1.24 item 4). `migrations/0013_catalog_write_confirmations.sql` creates the table. `deploybot_api` may select, insert, and delete, and may update only `used_at`. Both the user and project foreign keys use `ON DELETE CASCADE`. `--migrate` does not apply the down script.

A new image entry grants admins run, stop, restart, logs, and deploy, and grants viewers logs. The owner has those actions plus status. A program owner does not receive deploy. `POST .../deploy` on a program entry is `forbidden` for the owner. Image `logs` accepts `lines` from 1 to 2000 (default 200). Program logs stay 1 to 1000.

Deploy and rollback are synchronous: the 200 body is the outcome. A remove that times out is the request-level envelope error `timeout` (HTTP 504), audits outcome `timeout`, and is never reported as `missing`. A deploy or rollback that times out with no agent payload is HTTP 200 with outcome `timeout` and `status.state` `unknown`. `container`, `exit_code`, `started_at`, `finished_at`, and `digest` are null, `restart_count` is 0, and `ports` is empty. An agent result of `unknown` is rejected. The task `timeout_sec` is `300 + healthy_after_sec + 60` for a service deploy and for every rollback. When the spec has `healthcheck`, both use `300 + max(healthy_after_sec, start_period_sec + interval_sec × (retries + 1)) + 60`. A job deploy is `300 + timeout_sec + 60`. Remove, run, stop, restart, status, and logs are 60. `expires_at` is that many seconds ahead when the timeout is above 60, and 60 seconds ahead otherwise. The handler detaches deploy, rollback, and remove from the HTTP request with `context.WithoutCancel`, then bounds the hub wait by the task timeout. The history write, the in-flight release, and the idempotency finish use a fresh context with a five-second timeout and retry once, including when the task context has already expired. The HTTP server does not set `WriteTimeout` (`ReadHeaderTimeout` 10s, `ReadTimeout` 30s, `IdleTimeout` 120s), so that wait is not cut short by the server write deadline. One deploy, rollback, or remove may be in flight per host and entry. A second is `conflict`. The database enforces that with a partial unique index on `app.image_deploys`. Each in-flight row stores `in_flight_until` (the task timeout plus 120 seconds). The next deploy, rollback, or remove for that host and entry marks an expired row outcome `timeout`, clears it in the same transaction, and continues. A row that has not reached that deadline is still `conflict`. Rollback accepts one of the last three distinct digests whose outcome was `succeeded` or `unchanged` for that entry and host. Another digest is `bad_request` with message `invalid digest` and is not echoed.

The host must have reported `programs.images` and `programs.docker`. Otherwise the action is `bad_request` with message `this host does not run containers`. An entry with a non-empty `files` list also requires `programs.files`. Otherwise deploy and rollback are `bad_request` with message `this host's agent does not support files`, before confirmation and before any task. Entries with no files are unchanged. The secrets key is checked before the idempotency claim and before a confirmation is issued, so a missing key is not stored for 24 hours. It is required when the entry names an env set, uses `secret_env`, a `files` row still names a secret file, or the image's registry host has a stored registry. The response is 503 `unavailable` with message `secrets key not configured`. A public image with no matching registry deploys without the key. Run, stop, restart, status, and remove do not need it. Logs need it only when the resolved env includes a secret key or a files row still names a secret file. A missing key is then 503 `unavailable` with message `secrets key not configured`: no task is sent and no lines are returned. A plain winning value, a plain file, and a registry credential do not trigger that refusal. Inline `env` clears a secret flag. Idempotency matches programs: the claim is stored before a delegated session receives its 202. A deploy hash also includes `force`. A rollback hash includes `digest`. The plan text is `will deploy <entry> (<image or digest>) on <host>`, `will remove <entry> on <host>`, or `will <action> <entry> on <host>`. It contains no env values or tokens.

A Docker health sample (`protocol` `docker`, `result` `success` or `unhealthy`, `http_status` and `latency_ms` null, no `check_id` or `port`) is stored only when that host's hello set `programs.docker_health`. Otherwise the batch is rejected as an invalid sample and the socket stays up. `config.docker_health` is `true` on `hello_ok` and `config_update` only for such a host, and is omitted otherwise. Service health uses a `docker` row at most 2 minutes old (`success` is `up`, `unhealthy` is `down`) ahead of the latest non-docker row. `health.source` is `docker`, `check`, or null, and `latency_ms` is null for Docker. `GET /v1/services/{id}/health` includes those rows with `check_id`, `port`, `http_status`, and `latency_ms` null. An optional image `healthcheck` (`test` of 1–32 strings, each 1–1024 bytes and no NUL, plus `interval_sec` 5–300, `timeout_sec` 1–60 and less than the interval, `retries` 1–10, `start_period_sec` 0–600) is stored with omitted numbers filled as 30, 5, 3, and 0, and is part of `spec_hash`. `test` is the bare command: Deploybot adds Docker's `CMD`, and a first item of exactly `CMD`, `CMD-SHELL`, or `NONE` is `bad_request` with message `invalid healthcheck.test: give the command itself, without CMD, CMD-SHELL or NONE` on create, `PUT`, and the delegated confirm (api-v1 v1.18; a later item may be those words, and stored entries are not rewritten). A job is `bad_request` with message `healthcheck applies to services`. Other errors name the field and do not echo `test`. Deploy and rollback of an entry that has one require `programs.healthcheck`, or the response is `bad_request` with message `this host's agent does not support healthcheck`, before confirmation and before any task. `programs` is jsonb, so these booleans need no migration. Deploybot stores an optional ImageSpec `logging` object on services and jobs (`max_size_mb` 1–100 and `max_files` 1–10, both required, null omitted) as part of `spec_hash`, and a deploy, rollback, or job run that sets it is `bad_request` with message `this host's agent does not support log settings` when `programs.logging` is not true, with no task and no deploy row.

Deploybot stores an optional ImageSpec `health_policy` on services (api-v1 v1.15): `on_deploy_failure` `rollback`, `stop`, or `keep`; `on_unhealthy` `none`, `restart`, or `rollback`; `unhealthy_after_sec` 15–600; `max_actions_per_hour` 1–10. Every key is optional, the defaults are `rollback`, `none`, 45, and 3, and the object is stored as written (null means absent). A job with the key is `bad_request` `health_policy applies to services`, an unknown key is `unknown field health_policy.<key>` when the key is at most 64 bytes of `[a-z_]` (otherwise `invalid health_policy`, as for a non-object), a bad value names the key (`invalid health_policy.on_unhealthy`, …), `on_unhealthy` other than `none` without `healthcheck` is `health_policy.on_unhealthy needs a healthcheck`, and with `on_deploy_failure` `keep` it is `health_policy.on_unhealthy cannot be combined with keep`. The policy enters `spec_hash` only when it differs from the defaults, and then with every key filled in, so an entry at the defaults keeps its hash and two spellings of one policy hash alike. A deploy or rollback of an entry whose policy differs from the defaults needs `programs.health_policy`, or the response is `bad_request` `this host's agent does not support health policies`, checked again at confirm, with no task and no deploy row. A host without that flag never receives the `health_policy` key. The v1.12 create plan lists `health_policy on_deploy_failure=… on_unhealthy=… unhealthy_after_sec=… max_actions_per_hour=…` when it differs from the defaults, and an update lists the effective change. On a connection whose hello set `programs.health_policy`, an agent `auto_action` frame (`id`, `t`, `project`, `entry`, `container`, `action` `restart`|`rollback`|`gave_up`, `reason` up to 200 bytes, `result` `ok`|`error`, `digest`) is checked, then stored only when the entry is an image service of a project in the host's org with `deploy` access to the host, its effective `on_unhealthy` equals the action (`gave_up` and an error result need any value other than `none`), `container` is `<project>-<entry>`, and the entry has a `succeeded` or `unchanged` row on the host. It is stored as one finished `app.image_deploys` row (`via` `agent`, `by` null, outcome `auto_restarted`, `auto_rolled_back`, `auto_gave_up`, or `auto_failed` for any `result` `error` with a null digest, `started_at` = `finished_at` = server time, `spec_hash` of the last finished row for that host and entry or the entry's hash, digest from the frame or else the last `succeeded` or `unchanged` user deploy's digest, never an agent row's) and one `audit_log` row (`catalog.auto_restart`, `catalog.auto_rollback`, or `catalog.auto_gave_up`, `via` `agent`, no actor, detail entry, host, container, reason, result, and the frame's `t`). At most 20 rows are stored per entry and host in a rolling hour; later frames are acknowledged and dropped with one warn an hour. Each connection also has an `auto_action` token bucket (burst 10, 1 a second); a frame beyond it is dropped before any database read and not acknowledged, so the agent resends it after a reconnect. Drop warnings are logged at most once an hour per connection and reason, with the number dropped since the last line. The server replies `auto_action_ack` with the id. A replayed id is acknowledged without a second row. Any other frame is acknowledged and dropped with one warn line. A frame without a usable id, or on a connection whose hello did not advertise the flag (checked before any database read), gets no ack. A store failure gets no ack, so the agent resends. Deploy history lists the newest 50 non-automatic rows plus at most the newest 20 automatic rows newer than the oldest of those, merged by time. Automatic rows are never rollback candidates, which stay the last three `succeeded` or `unchanged` digests. `migrations/0014_auto_actions.sql` makes `by_user` nullable with a check that only `via = 'agent'` rows may omit it, widens the `via` and `outcome` checks, adds the unique `auto_action_id` column (present exactly on agent rows), and requires that auto outcomes are agent rows and agent rows are not in flight. `--migrate` does not apply `0014_auto_actions.down.sql`, which in one transaction deletes the agent rows and restores the old constraints. Roll back the agents and clear `health_policy` from every entry before rolling the API back, because an older API cannot parse the key.

Deploybot stores an optional ImageSpec `networks` (api-v1 v1.25): 1–4 unique shared network names matching `^[a-z0-9][a-z0-9-]{0,31}$`, on services and jobs. `null` and `[]` are stored as absent; a bad name, a duplicate or more than 4 is `bad_request` `invalid networks`. The key is in the stored spec and in `spec_hash` only when set (between `memory_mb` and `ports`), so an entry without it keeps its v0.2.31 spec, hash and task payload. A deploy or rollback of an entry with `networks`, and the delegated confirm of one, runs after the feature gates: a host whose `programs.shared_networks` is null (agent before 0.2.9) is `bad_request` `this host's agent does not support shared networks; upgrade it to 0.2.9`, and a name the host does not define, or whose member list lacks the entry's project slug, is `bad_request` `shared network <name> is not open to this project on this host`, with no task and no deploy row. Run, stop, restart and remove are not gated. `catalog.ParseStored` re-checks stored names against the same rule, so a row written outside the API cannot carry an unchecked name into a refusal, plan, audit row or task. The task's `spec.networks` is sent only when non-empty, in stored order. The create plan adds `shared networks: <names>`, an update `shared networks: <before> → <after>` (`none` when absent), and a delegated deploy or rollback plan adds `; also joins shared network(s): <names>`. Operator steps (the `shared_networks` key in `/etc/bot-agent/runner.toml`, and upgrading the host's agent to 0.2.9 first) are in bot-agent `docs/install.md`, section "Shared networks".

Env sets and registries require an owner or admin (`CapMembers`) and a console session. A viewer is `forbidden`. A delegated or MCP token is `forbidden` before any decrypt. A delegated env-set refusal is audited `denied` with `via` `mcp`. A non-member is `not_found`. `GET` and `PUT /v1/projects/{id}/env-sets/{set}` and `DELETE` of that set, `PUT` and `DELETE .../keys/{key}`, and `GET /v1/projects/{id}/registries` plus `PUT` and `DELETE /v1/projects/{id}/registries/{host}` are the routes. `GET` of an env set returns a secret value as JSON `null` and `preview` of that secret, and returns a plain value with `preview` null. `PUT` replaces the set from a dotenv body of at most 256 KiB. A key that already exists keeps its visibility. A key new to the set is stored as secret unless the body sets `new_keys_secret` to false. A key left out of the body is removed. The body may set `mode` (api-v1 v1.19, docs/spec-env-set-merge.md): `replace` (the default, as above), `create`, or `merge`; any other value is `bad_request`. `create` makes a new set and is `conflict` with message `env set {set} already exists` when the name is taken, changing nothing. `merge` needs an existing set (else `not_found` with message `no env set {set}`), upserts each pasted key as the key `PUT` would (an existing key keeps its flag, a new key follows `new_keys_secret`), and keeps the keys left out; an empty value for an existing secret key is `bad_request` `a secret value cannot be empty; delete the key instead` and nothing is written. Each mode is one transaction. `replace` and `create` audit `env_set.replace` (`set`, `keys`); `merge` audits `env_set.merge` (`set`, `keys`, `created`), names only. A delegated refusal is audited `env_set.replace` for every mode, because it comes before the body is read. The grammar is UTF-8, optional `export `, `#` comments, and one pair of matching quotes removed, with no escape processing and no interpolation when parsed (`${KEY}` references are resolved only at deploy, see v1.27 below). `$` and `\` are stored as written. NUL is refused, a value does not span lines, and a value is at most 4096 bytes. Inline ImageSpec `env` keeps the v1.6 item 8 rules. A duplicate or a malformed line is `bad_request` naming `line N` and the key when one was parsed, never the value. `DELETE` of a set that an entry still references is `conflict`. A registry `GET` returns `host` and `username` only. `PUT` takes `username` (1–255) and `token` (1–4096) with no CR, LF, or NUL. The host is a lowercase hostname with an optional port. An invalid host, username, or token is `bad_request` and the message does not echo the value.

`PUT` and `DELETE /v1/projects/{id}/env-sets/{set}/keys/{key}` edit one key. The put body is `{"value","is_secret"?}`, or `{"generate","is_secret"?}` (v1.27 below). `is_secret` applies only to a new key and defaults to true; an existing key keeps its flag, and a different flag is `bad_request` with message `secret flag is fixed; delete and re-add the key`. `"value": ""` on an existing secret key is `bad_request` with message `a secret value cannot be empty; delete the key instead`, stores nothing, and writes no `env_set.key_put` audit row (api-v1 v1.18); a plain key and a new key still accept `""`. The put creates the set when it is missing and returns that one key. A secret key has `value` null and `preview`: the first four runes plus `…` when the value has at least 16 runes, otherwise `••••`. A plain key has `preview` null. Delete of an unknown key is `not_found` and leaves the set in place when it was the last key. Both routes are console-only. ## Registry tags

A user gets 20 uncached lookups per minute across both routes, and at most 32 lookups run at once; beyond either, 429 `rate_limited` with `Retry-After`. ## Project files

## Domains, edge and routes

api-v1 v1.35 (spec `../../docs/spec-domains-edge-routes.md` rev 2, migration 0023). **Domains** (console only, org owner or admin): `GET|POST /v1/orgs/{id}/domains`, `POST …/domains/{domain_id}/verify` (looks up `TXT _deploybot.<name> = deploybot-verify=<token>` through `Server.Resolver`, `net.DefaultResolver` in production), `PUT …/assignments` (`@` the name, `*` one label below it; projects of the org only) and `DELETE …/domains/{domain_id}` (a 202 plan naming every route that stops; `POST /v1/confirmations/{id}` removes the domain, its assignments and those routes). A name is verified (or lapsed) by one org only (partial unique index). `RunDomainChecks` (started by `Run`) re-checks verified and lapsed domains once a day; 7 failures in a row make a domain `lapsed` (audit `domain.lapsed`, via system): its routes keep serving, new routes under it are refused, a later success verifies it again. **Edge** (console only, org owner or admin): `GET|PUT /v1/hosts/{id}/edge`; enabling needs the hello `programs.edge.enabled` and is refused (`conflict`) while discovery shows anything but `deploybot-edge` on 80 or 443: `port 443 is used by web (project Proj); stop it, wait until the host no longer reports that port (up to a minute), then try again`, or `a process outside Deploybot` as the holder. A stopped Deploybot container keeps its service row (no `gone_at`) but drops the port at the host's next services report (about a minute); from then on Turn on is no longer refused. **Routes** (project owner or admin, console or delegated): `GET /v1/projects/{id}/routes`, `GET|PUT /v1/projects/{id}/catalog/{name}/routes`; PUT is always a 202 plan. Routes are their own table and never touch `spec_hash`. An image route's port must be a container port the entry publishes; the config dials the lowest host port that publishes it on `127.0.0.1`. The API builds Caddy JSON per host (`internal/edgeconfig`, golden files in `testdata/`) from routes of entries with a live owned service there, under a verified or lapsed domain assigned to the project, and sends `edge_apply` only to a host whose hello reports `edge.enabled`. Every route, domain, assignment, ACME-email, edge-switch and project-delete change, and every services report, syncs the affected hosts in the background (sends nothing when the config hash is the applied one); every hello re-sends the full config. An offline host shows `pending` and gets the config on reconnect. `PATCH /v1/orgs/{id}` takes an optional `acme_email` (`""` clears; owners and admins read it back). Readiness has a `routes` check. The Cloudflare ranges for `client_ip_from` are a list in `internal/edgeconfig/cloudflare.go`; refresh it at release time. The 0023 down script refuses while any route or domain exists. A route reaches only its own entry: a program must declare `port` (`program E declares no port; add one to route it`), the upstream is 1024 or higher, and on each host a route is live only when the resolved port is a listener of that entry's own live owned service there (an image spec edited without a redeploy, or another project's port, leaves it `pending` and out of the config). Paths and `no_store_paths` are lowercased (Caddy matches paths without case) and may not hold `.` or `..` segments. Plans put each address that goes live or stops on its own line. A domain delete stops only the org's own routes whose hostname no other verified or lapsed domain of the project still covers, and the confirm answers `conflict` `routes changed since the plan; ask for a new one` when that set changed. Deleting a project drops its routes and domain assignments, so the hostnames are free again. A DNS answer of no such record counts as a failed check; any other lookup error is skipped (the on-demand verify answers `unavailable`). A sync writes only the edge state, never the switch, and syncs coalesce to one at a time per host. When a 0.2.11+ agent reports `programs.edge.enabled` false, the API sends `edge_stop` and shows `off` with `the host's runner.toml no longer allows the edge`; an older agent (no `programs.edge`) is never sent an edge task. Agent refusals are stored as sentences in `detail` (`edge_disabled`, `port_in_use`, `invalid_config`, `conflict`, `bad_spec`, `docker_unavailable`, `image_unavailable`, `io_error`, `helper_unavailable`), with the agent's own detail appended. `edge_status` is defined but not sent in stage 1. The project slug `edge`, and the entry name `edge` in a project slugged `deploybot`, are refused at create (they collide with the edge's container and volume names). `BOT_API_EDGE_TLS_ISSUER` (optional) is empty (ACME, the default) or `internal`: with `internal` every edge TLS policy uses Caddy's internal CA (`{"module":"internal"}`) and `acme_email` is ignored. It is for dev and test hosts only (such as pi3, which the internet cannot reach on 80 and 443); never set it on us1. Any other value stops the API at start with `BOT_API_EDGE_TLS_ISSUER must be empty or internal`. The default output is unchanged, so existing `config_hash` values stay the same. The agent accepts only these top-level keys in an `edge_apply` config: `admin` (exactly `{"listen":"unix//run/edge/admin.sock"}`), optionally `config.persist`, and `apps`; the builder emits `admin` and `apps` only, and `TestBuildTopLevelKeys` holds it to that.
