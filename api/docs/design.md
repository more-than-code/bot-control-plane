**Date:** 2026-10-13. **Status:** Approved design (D1–D31), wave 1 = phase 1. D34 (2026-10-14) amends umbrella D21. Service names and `GET /v1/projects/{id}/services` (2026-10-14) follow `docs/spec-project-services.md`. ## Notes

- One process. In-flight tasks, OAuth states, and live agent connections are in memory.
- Metrics tables use `timestamptz`. Raw samples are kept 7 days (TimescaleDB retention policies in migration 0002). There are no continuous aggregates: every chart and the host resource sweep read raw samples.

## D34 Shared hosts (superseded by D38 in v1.24; removed in v1.26)

This section describes v1.1 to v1.23. The API stopped reading `host_shares` and `hosts.project_id` in v1.24 (D38), and migration 0016 (api-v1 v1.26) removed them: `host_shares`, its trigger and function, `hosts.project_id` and `hosts_project_name_unique` are dropped. The text below is history.

Amends umbrella D21 ("a host belongs to exactly one project"). The host still has one owning project (`hosts.project_id`). `app.host_shares` grants another project `metrics` or `deploy` access. A row whose project is the owning project is rejected by a `BEFORE` trigger and by the store. `services.project_id` records which project a service belongs to. The agent still enrolls with no protocol change; a discovered service is inserted on the host's owning project, and rediscovery does not move `project_id`.

Permission checks for host and service routes use `authz.HostRelation` and `authz.AuthorizeHost` (spec §4). A user who is in both the owning project and a share is an owner; that clears the share list. A user in several shares keeps every share. Host view, status, and metrics are allowed when any share allows them. A service check uses only the share whose project is that service's project. `GET /v1/hosts/{id}` `share_level` is the highest of those shares (`deploy` over `metrics`). `GET /v1/projects/{id}/hosts` is different: the label is relative to that project, so the same user listing the sharing project still sees `relation: "shared"`. Owned rows come first, then shared rows, each by name in byte order (`COLLATE "C"`). The host-list cursor is `(rel_rank, name, id)`. The next page compares those values and does not look the cursor host up. A cursor in the previous `(time, id)` shape is rejected. Deploy shares still see only that project's services; anyone who can see the host gets the full process list and may snapshot (v1.1.1). A caller in two deploy shares sees both projects. Metrics shares can read the host and its charts.

Deleting a sharing project drops its shares and moves its services on other hosts back to those hosts' owners, in the same transaction. Deleting the owning project still revokes host credentials, and its shares go too. Deleting a host row drops `host_shares` by `ON DELETE CASCADE`.

`migrations/0003_shared_hosts.sql` is applied by `--migrate` (as `deploybot_owner`). It backfills `services.project_id`, then sets `NOT NULL`, and grants `deploybot_api` select, insert, update, and delete on `app.host_shares`. `--migrate` ignores `*.down.sql`. `migrations/0003_shared_hosts.down.sql` is a hand-run rollback for before phase 2: run it as `deploybot_owner`, then `DELETE FROM app.schema_migrations WHERE name = '0003_shared_hosts.sql'` before `--migrate` will apply 0003 again.

## Service names

`services.display_name` is the name a person types. `services.owner_user` is the account that owns the listening socket, copied from the agent's `Discovered.user`. Both are nullable. Rediscovery updates `owner_user` and the other discovered columns; it does not write `display_name`. A value that is empty, not printable, or longer than 64 bytes is stored as null and does not drop the service.

`PATCH /v1/services/{id}` sets or clears `display_name`. The body is that one field. The handler trims it and requires 1–64 printable characters. The edit permission is the service write capability of D38: an org owner or admin, or an admin of a `deploy` project for a service of that project. A case-insensitive duplicate on the same host is `conflict`, from the partial unique index. The audit action is `service.rename` with detail `from` and `to`, on success and on denial.

`GET /v1/projects/{id}/services` requires `CapRead` on the project. Rows are services whose `project_id` is that project on hosts where it has `deploy` access (v1.24). Metrics access contributes nothing; org-level services (`project_id` null) are never in a project list. Each row is the Service object plus `host_name`, `host_status` (the same rules as `Host.status`), and `project_name`. Search, sort, `total`, and paging run in SQL: one count and one page. `q` is bound with `LIKE` wildcards escaped. Sort and direction are an allowlist. Names sort by byte order of the lowercased label (`COLLATE "C"`), not locale. Host and kind use that same collation on the stored text. Ties break by `id` ascending. Nulls sort last in both directions. The cursor is opaque base64url JSON `{o, h}`: an offset and a short hash of `q`, `host_id`, `sort`, `dir`, and `view`. The first page has `prev_cursor` null. `include=health_checks` (api-v1 v1.18) reads the page's checks with one `ListHealthChecksForServices` call (`service_id::text = ANY($1)`, ordered by service and id) after the page query and adds `health_checks` (`[]` when none) to each row; it is not in the cursor hash, and without it the rows are unchanged. `GET /v1/hosts/{id}/services` orders by name in byte order (`COLLATE "C"`), like every other name sort, so Postgres and memstore agree. That list is otherwise unchanged apart from the two new Service fields.

`migrations/0004_service_names.sql` adds the columns and `services_host_display_name_uidx`. `services_project_idx` already exists from 0003; 0004 creates it only if it is missing, and the down script does not drop it. `--migrate` does not apply `migrations/0004_service_names.down.sql`. Running that file by hand drops the two columns and the unique index. Names typed by people are lost. Then `DELETE FROM app.schema_migrations WHERE name = '0004_service_names.sql'` before `--migrate` will apply 0004 again. Grants are unchanged.

`services.gone_at` is when a service was missing from its host's latest complete services report. Null means that report included it. Presence uses the stored name after placement, so a matching catalog entry is stored under the entry name, not the name the agent sent. The upsert and the presence update run in one transaction when the report is complete: unreported rows that are not already gone get `gone_at` set to the report time, and reported rows have `gone_at` cleared. An already-gone row keeps its time. Other hosts are not modified. A `services` frame is that full set when every element is valid. An empty array is an empty set. A mix of valid and invalid elements still upserts the valid rows and clears their `gone_at`, and does not mark any other row gone. An array whose every element is invalid, or a payload that is absent, blank, or JSON `null`, is not a report. `hello.services` follows the same rule when `services_complete` is absent or `true`. `services_complete: false` and JSON `null` write nothing. A non-bool fails the frame. `GET /v1/projects/{id}/services` accepts `view` `all` (default), `deploybot` (`owned` and `declared`), or `deploybot_and_discovered` (those plus discovered rows still present). Anything else is `bad_request`. Search, sort, paging, and `total` stay inside the view, and the cursor hash includes the view. `sort=status` keeps gone rows after present rows in both directions. Host and service reads include `gone_at` and do not filter by view. `migrations/0008_service_gone.sql` adds the nullable column and backfills each host from its own newest `last_seen_at`. `--migrate` does not apply `migrations/0008_service_gone.down.sql`. Running that file by hand drops the column. Then `DELETE FROM app.schema_migrations WHERE name = '0008_service_gone.sql'` before `--migrate` will apply 0008 again. Grants are unchanged. Revoking a host sets `gone_at` to that revoke time on its rows that are still present, in the same transaction (`0012_revoked_host_rows.sql` backfills hosts revoked earlier), and `view=deploybot` and `view=deploybot_and_discovered` exclude rows whose host is revoked (`view=all` still returns them). A services report that places an item as `discovered` ends ownership of an existing `owned` row (`source` becomes `discovered`, `catalog_entry` becomes null, `project_id` becomes the host's project) and keeps the row id, `display_name`, and health checks; a `declared` row is not changed by a report.

## MCP OAuth authorization server

Public clients register themselves. A registration asking for `client_secret_post` or `client_secret_basic` gets a public client (`none`, no secret, PKCE required) and a response saying `none`; other methods except `none` are refused with `invalid_client_metadata` (oauth-v1 v1.5). A refused registration logs one INFO line, `oauth register refused`, with the error code and the failed rule (`body`, `redirect_uris`, `client_name`, `grant_types`, `response_types`, `token_endpoint_auth_method`, plus a known method name or `other`); no request values are logged. The browser consent routes, the device-code lookup and approve/deny routes, and `GET`/`DELETE /v1/me/grants` require a console session. Any other session kind on those routes is 401. `POST /oauth/token` accepts `authorization_code`, `refresh_token`, and the token-exchange grant. Only `bot-mcp-server`, authenticated with HTTP Basic and the secret from `BOT_API_MCP_CLIENT_SECRET_FILE`, may call token exchange. A request that passes that Basic authentication is not counted against the token endpoint's 60-per-minute per-IP limit. A missing or wrong secret is counted. That client is inserted at process start from the SHA-256 of the file's first line. It is not created by dynamic registration. Codes, refresh tokens, access tokens, and the client secret are stored as SHA-256. Comparison is constant-time. Identifiers and codes are at least 128 bits from `crypto/rand`; tokens are 256 bits. A second redemption of an authorization code revokes every session in that grant family, including tokens from later refreshes and `api_delegated` sessions. Presenting an already-rotated refresh token does the same.

An `mcp_access`, `mcp_refresh`, or legacy `mcp` session on any `/v1/*` route is rejected with `invalid_token` before the handler runs. An `api_delegated` token acts as its user. Audit rows it causes use `via = 'mcp'`. The column check is `allowed|denied`, so an allow or deny decision is stored as `allowed` or `denied`.

Mutating `/v1` routes declare how an `api_delegated` session is treated. The zero value denies the call in the route wrapper, after the MCP audience check and before the handler: 403 `forbidden`, nothing written, and one `delegated.denied` audit row with `via` `mcp`, null project and host, and the route pattern in detail. The project, member, invite, join-token, credential, host access, org and service-rename writes use that default (the list is `delegatedDenyPatterns`). That default covers writes only: every read route declares `delegatedAllow` or `delegatedDenyRead` (D38). Snapshot, probe, catalog logs, status, and parse, sign-out, and confirmation stay allowed. A route that already decides in its handler (a confirmation plan, `refuseDelegated`, `requireConsole`, or `consoleUser`) keeps that decision and is not audited again by the wrapper. Public routes are not checked. Console sessions and GET routes are unchanged.

`migrations/0005_mcp_oauth.sql` is applied by `--migrate` as `deploybot_owner`. It adds `app.oauth_clients`, `app.oauth_grants`, `app.oauth_requests`, and `app.oauth_codes`, the session columns `audience`, `grant_id`, `client_id`, `code_id`, and `rotated_at`, and widens `sessions_kind_chk` to `console|mcp|mcp_access|mcp_refresh|api_delegated`. `kind = 'mcp'` stays legal so the cut-over can expire those rows in place: `UPDATE app.sessions SET expires_at = now() WHERE kind = 'mcp' AND expires_at > now()`. `deploybot-cli` is inserted for the device flow. `deploybot_api` receives select, insert, update, and delete on the four new tables. `--migrate` ignores `*.down.sql`. `migrations/0005_mcp_oauth.down.sql` is a hand-run rollback: run it as `deploybot_owner`, then `DELETE FROM app.schema_migrations WHERE name = '0005_mcp_oauth.sql'` before `--migrate` will apply 0005 again. The down script deletes sessions whose kind is not `console` or `mcp`, restores the 0001 kind check, and drops the new columns and tables. Legacy `mcp` rows stay expired. Clients, grants, codes, and pending requests are lost.

## Project invite links

An invite is a bearer token for project membership, separate from host join tokens. The plaintext is 256 bits, 43-character unpadded base64url, shown once in `POST /v1/projects/{id}/invites` as `token` and as `url`. The store keeps only `secret.Hash` of that string. List, revoke, lookup, and accept never return it. Logs and audit detail do not contain it or its hash.

`url` is `<BOT_API_CONSOLE_ORIGIN>/invite/<token>`. The handler trims trailing slashes on the origin, the same way the OAuth consent redirect does. An empty origin fails the create with 500 before `secret.NewToken` runs. Admin routes use `authz.CapMembers` (owner or admin). A viewer is `forbidden`. A non-member is `not_found`. Lookup and accept require a `console` session; another kind is 401 `unauthorized`. Those two routes call `authz.Authorize` with `CapSession`, then `auth.AllowInvite`: 30 per minute per user and 60 per minute per source IP, one window, and a rejected call is not counted. The HTTP body is the v1 envelope `rate_limited` (429). The OAuth token endpoint still uses its own `{"error":"rate_limited"}` body.

Lookup is a plain select. It returns the invite's role and `already_member`, and it does not write. Accept locks the invite row by `UPDATE app.invites SET uses = uses WHERE token_hash = $1`, which `deploybot_api` is allowed to do. `SELECT … FOR UPDATE` would also need `UPDATE` on every returned column, and this role only has `UPDATE` on `uses` and `revoked_at`. The lock update is rolled back unless a new membership row was inserted and `uses` was incremented. An existing member gets their current role back; `uses` and the role stay as they were. A new member is inserted with the invite's role and `added_by` set to the invite's `created_by`. `uses` is incremented only while `uses < max_uses`. The memstore holds its mutex for the whole accept, so the cap is the same there. Unknown, malformed, expired, revoked, and used-up tokens hash to a lookup and return one `not_found` body. A used-up invite is `not_found` even for someone who is already a member.

Audit rows are `invite.create` (invite id, role, max_uses, expires_at), `invite.revoke` (invite id), and `invite.accept` (invite id, user id), including an accept that finds an existing member. Lookup writes no audit row.

`migrations/0006_invites.sql` is applied by `--migrate` as `deploybot_owner`. `app.invites.project_id` references `app.projects` `ON DELETE CASCADE`. `token_hash` is unique and 32 bytes. `role` is `admin` or `viewer`. `max_uses` is 1–50. `uses` is 0–`max_uses`. Default privileges would grant `deploybot_api` full CRUD, so the migration revokes that and grants select, insert, and update of `uses` and `revoked_at` only. Soft-delete does not fire the foreign key. `DeleteProject` calls `app.invites_delete_for_project`, a `SECURITY DEFINER` function with `search_path = pg_catalog, app`, executable by `deploybot_api` and not by `PUBLIC`. The memstore deletes that project's invite rows under the same mutex. `--migrate` ignores `*.down.sql`. `migrations/0006_invites.down.sql` is a hand-run rollback: run it as `deploybot_owner`, then `DELETE FROM app.schema_migrations WHERE name = '0006_invites.sql'` before `--migrate` will apply 0006 again. The down script drops the function and the table. Memberships already created by an accept stay. Invite links stop working.

## Project catalog (programs)

Wave 1 stores program entries. Any `kind` other than `program` or `image`, and a top-level `secret_env` on a body that is not `kind: program`, is refused with `not_implemented` (HTTP 501) before unknown-field checks. Since api-v1 v1.22 a program body takes `secret_env` and `env_sets` (see Program secrets below). Image entries use `spec` and are described under Catalog images. The `docker run` parser is not implemented. After migration 0009, `catalog_entries.kind` allows `program` and `image`.

An owner creates and replaces program entries. The server splits `command` with POSIX word rules (quotes and backslash escapes only). `shell=false` refuses pipes, operators, redirects, expansion, globs, and a first word `cd`. Leading `KEY=value` words are hoisted into `env`. Keys that start with `LD_` or `DYLD_`, and `NODE_OPTIONS`, `NODE_PATH`, `BASH_ENV`, `ENV`, `IFS`, `PYTHONPATH`, `PYTHONSTARTUP`, `PERL5OPT`, `PERL5LIB`, `RUBYOPT`, and `RUBYLIB`, are refused with `bad_request` and the message `this variable changes what the program runs`, including hoisted words. A `shell=true` line is not scanned for those names. `shell=true` stores `exec=/bin/sh` and `args=["-c", line]`. `spec_hash` is the lowercase hex SHA-256 of the canonical JSON `{"kind":"program","spec":{...}}` with keys sorted and no whitespace. `exec` is part of that document. `command_display` is the argv re-joined with POSIX quoting, or the raw line in shell mode.

Default grants are `role:admin` → run, stop, restart, logs, and `role:viewer` → logs. The owner always has run, stop, restart, logs, and status, and cannot be a subject. `status` is not stored; it is allowed when the caller holds any stored action. `my_actions` is that list in the order run, stop, restart, logs, status. List returns an entry only when `my_actions` is non-empty. A member with no grant who fetches one entry gets `forbidden`. A non-member gets `not_found`.

`last_deployed_at` (api-v1 v1.21, `docs/spec-catalog-last-deployed.md`) is filled by the API on the list, the single-entry read, and the console replace response through `Store.CatalogLastDeployed`, after visibility filtering, with one call per request. Only visible entries are passed, so a hidden entry's id never reaches the query. On a replace the `catalog.update` audit row is written right after the commit, then the field is read; a failed read is logged and the response is 200 with `null`, while the list and `GET` fail the request. A create response and the delegated catalog-write confirm response (create or update) carry `null`; delete returns no entry. The Postgres store runs at most two grouped queries: `max(d.started_at)` from `app.image_deploys d` joined to `app.catalog_entries` on the entry, scoped to the project, for the image entry ids with `via IN ('console','mcp')`, and `max(a.at)` from `app.catalog_entries e` joined to `app.audit_log a` on the project, `a.detail->>'entry' = e.name` and `a.at >= e.created_at`, with `action = audit.ActionProgramRun` and `decision = audit.DecisionAllowed` (bound as parameters), `via IN ('console','mcp')`, grouped by entry id. An allowed run whose agent call failed or found the host offline counts. No column is stored and no migration was added: the image query uses the `(entry_id, host_id, finished_at DESC)` index prefix and the audit query the `(project_id, at DESC, id DESC)` index. Neither table has retention, so the program query reads every audit row of the project on each list and grows with the project's audit history. If that shows up, add a partial index in a new migration: `app.audit_log (project_id, (detail->>'entry'), at DESC) WHERE action = 'program.run' AND decision = 'allowed'`. Audit rows carry only the entry name, so the `created_at` bound keeps an entry re-created under an old name from inheriting earlier runs.

Run, stop, restart, logs, and status use one ordered chain. Membership of project `{id}` is `not_found` before the body is read. Invalid JSON and an invalid `host_id` are `bad_request`. A missing grant is then `forbidden`, including when `idempotency_key` or `lines` would also be invalid. The key format and `lines` (1..1000) are checked after the grant. The entry's project must have `deploy` access to the host (v1.24, D38). Without `deploy` access (D38) the answer is `forbidden` `this project has no deploy access to the host` when the caller can see the host, otherwise `not_found`. Policy is next: null `programs`, `enabled=false`, `run_as` not listed, or shell when `allow_shell` is false. Shell also includes an exec whose base name is `sh`, `bash`, or `dash`. Each of those is `forbidden` with its own reason. The host is then required to be online. Policy denials and an offline host are not stored as idempotency responses. Run, stop, and restart then insert the idempotency row (user, key, request hash, null status, null response) before any agent call or confirmation. A second request with the same key while the response is null is `conflict` with message `request in progress`, even when the hash differs. After the outcome, including a failed dispatch, the status and body are filled in. The same request replays that body for 24 hours and does not act again. A finished row with a different hash is `conflict`. The request hash is the SHA-256 of compact JSON with keys `action`, `entry`, `host_id`, and `project_id`. It does not include `spec_hash`. An `api_delegated` session gets HTTP 202 for run, stop, and restart and does not call the agent. The confirmation id is a 43-character token. The confirmation row stores only `secret.Hash`. The idempotency response keeps the 202 body, including the plaintext id, until confirm replaces it. The id is single use, five minutes, and bound to the user, action, entry, `spec_hash`, and request hash. `POST /v1/confirmations/{confirmation_id}` takes `{"idempotency_key"}`. An invalid key is `bad_request` before lookup. The same `api_delegated` bearer may confirm. The handler checks the user, the used bit, and expiry first (`not_found`), then requires the posted key to equal the stored key (`conflict` otherwise, token unused). It re-runs the grant, relation, policy, and online checks, then returns `conflict` if the spec hash changed. Those failures do not consume the token. The token is marked used before the agent call. An agent error still consumes it and replaces the stored 202 with that error body. Console sessions skip confirmation. Logs and status never confirm and are not idempotent. The agent task uses `program_start`, `program_stop`, `program_restart`, `program_status`, or `program_logs`, with `service` null. Strings in a payload `lines` array pass through the cmdline redactor before the HTTP body and before the idempotency write. `task_reject` and a failed result of `policy_denied` both become `forbidden`.

`hello.programs` is stored on `hosts.programs` and returned on `Host`. Absent or null clears a previous policy. An object that is not the v1.3 shape is stored as disabled with an empty `run_as`. A later `services` frame does not clear it. A discovered service whose `owner` is `{kind:program, project:slug, entry:name}` is stored as `source=owned` on that project when the slug has that catalog entry. The service name and `catalog_entry` are the entry name. Otherwise the item stays `discovered` on the host's project. `systemd_unit` becomes the service name only when it matches `^[a-z0-9][a-z0-9._-]{0,62}$`. Otherwise the reported name is kept. Owned placement is the slug and entry lookup from v1.6. It maps only to a project of the host's org with `deploy` access (D38); without a reported `programs.projects` (agents before 0.2.8) a program maps only for the host's single deploy project (D-10). Rediscovery may upgrade discovered to owned. It does not downgrade `declared` or owned, and it does not clear `display_name`.

Audit actions are `catalog.create`, `catalog.update` (old and new `spec_hash`), `catalog.delete`, `catalog.permissions`, `program.run`, `program.stop`, `program.restart`, and `program.confirmation_issued`. Delegated calls use `via=mcp`. Logs and status are not audited. A denied run, stop, or restart sets `HostID` from the parsed `host_id`, `Detail.entry` to the catalog name, and `Result` to the envelope code (`forbidden` or `unavailable`). Detail does not include env values, tokens, or the confirmation id.

`migrations/0007_catalog.sql` adds the catalog, grants, approvals, confirmations, and idempotency tables, `hosts.programs`, and `services.catalog_entry`. `deploybot_api` may select, insert, and delete those tables. UPDATE is limited to the columns a running server changes (`catalog_entries`: spec, spec_hash, command_display, updated_at; confirmations: `used_at`; idempotency: status_code and response). `status_code` and `response` are nullable, and `idempotency_response_pair_chk` requires both null or both set. A database that already applied an earlier 0007 must have this migration re-applied before those columns can be null. Grants are replaced by delete and insert, so `catalog_grants` has no UPDATE. Postgres needs UPDATE on at least one column before `SELECT … FOR UPDATE`; entry locks use that privilege. Catalog delete is granted, so there is no `SECURITY DEFINER` helper. Soft-delete does not cascade, and `DeleteProject` deletes that project's catalog rows in both stores. `--migrate` ignores `*.down.sql`. `migrations/0007_catalog.down.sql` is a hand-run rollback: run it as `deploybot_owner`, then `DELETE FROM app.schema_migrations WHERE name = '0007_catalog.sql'` before `--migrate` will apply 0007 again. The down script drops the new columns and tables. Running units are not stopped.

## Program secrets and the projects allowlist

api-v1 v1.22 (`docs/spec-program-secrets.md`) and v1.23 (`docs/spec-projects-gate-programs.md`).

`catalog.EnvRefs` (sets in order, `secret_env`, inline env) is the env an entry resolves; `Image.EnvRefs` and `Program.EnvRefs` build it, and the API's `mergeEnv`, `redactEnvValues` and `envNeedsKey` take it, so image deploys and program Runs share one merge. `catalog.BuildProgram` applies image rules 6 and 7 through `validateEnvSets` and `validateSecretEnv` with the project's `SetKeys`, and refuses more than 64 keys after the merge with the current key names. `catalog.ProgramHash` keeps the v1.6 canonical form for an entry without sets (so no existing hash changes on upgrade, as `health_policy` does at its defaults) and otherwise hashes `{"env_keys","env_values","kind","spec"}` with `env_sets` and `secret_env` in `spec`. It takes a `catalog.SetState` (every set's key names, and the plain values of the referenced sets); `EnvRefs.PlainTakingPart` picks the plain keys that take part (all keys of an `env_sets` set, and `secret_env` targets) and `EnvValueDigest` hashes their sorted `KEY=value` lines (api-v1 v1.22 amendment 1). Secret values are never read for the hash. Because plain values are now hashed, both stores re-hash after every `PutEnvKey` (not only a new key) and after `MakeEnvKeysSecret`; the rehash only writes when an entry's hash really changes. `store.ProgramSpec.Norm` makes the new fields non-nil on read and write; specs stored before v1.22 read as empty. Both stores treat program entries like images for set in-use (`DeleteEnvSet`) and for the rehash after a key is added or deleted (`rehashTx` with `rehashStored`, memstore `rehashSetLocked` with `entryRefs`).

Inline env refusal (api-v1 v1.6 rule 8, v1.39 item 4). `validateEnv` (programs and images) walks the keys in sorted order, so a refusal always names the same key, and refuses `LooksSecretNotPath` keys with `<KEY> looks like a secret: put it in secret_env or in a secret env-set key`. `LooksSecretNotPath` is `LooksSecret` minus names ending in `_FILE`, `_PATH` or `_DIR` (case-insensitive), and it is the one rule for a plain value under a secret-looking name (v1.39 item 4 as amended 2026-11-20): the program run gate for plain env-set keys (`originReason` in `program_env.go`) and the env-set plan reminder (`envKeysPhrase`, `envSetUpdatePlan`) use it too, so a plain `X_PRIVATE_KEY_FILE` is neither warned about nor refused. The console image form's `refusedInlineKey` mirrors it; the path-exemption case table in `internal/catalog/path_keys_test.go` is copied in the console's `tests/catalog-image.test.ts`.

`programGate` runs for every program action after the deploy-access check: the v1.6 policy, then for `run` the projects pre-check, `programs.secrets`, the secrets key, and `originReason`; for `logs` the key when a winning value is secret. `originReason` follows the merge precedence over key metadata only (`envOrigins`, no decrypt) and refuses, in key-name order, a key from a secret set key in `catalog.ChangesWhatRunsSecret` (v1.6.1 list plus the amendment 2 keys, proxies in either case) and a key from a plain set key that matches `catalog.LooksSecretNotPath`, the rule inline env uses (amendment 3; path names exempt since v1.39 item 4). It runs before the idempotency claim and is audited as a denied `program.run`. `BuildProgram` refuses a `secret_env` key in the extended list on write. `dispatchProgram` resolves the env only for `run` of an entry with sets, sets `env` and `secret_keys`, and refuses a spec over 64 KiB (the agent's `programs.MaxFrame`) before the hub call. Other actions load only the secret values that open, for redaction. `liveEnvelopeForms` redacts result `lines` with those value forms, then the keyword rule, and for an entry with secrets also the error message and every string of an error envelope, as `imageFail` does; with no forms it is the old `liveEnvelope`. The forms come from the set values stored now. After a value change and before the next Run, the host still runs with the old value: the API cannot redact it, and the agent's helper redacts the values in its stored spec (agent-protocol v1.11 item 4), so the old value is still covered on the host side.

`HostPrograms` stores `secrets` and `projects` from hello. `parsePrograms` stays strict: an unknown field, a non-bool `secrets`, more than 32 projects, a slug that fails the runner.toml grammar `^[a-z0-9][a-z0-9-]{0,63}$` (agent-protocol v1.4), or a `project_listed` key (it is API-computed) stores the host as programs disabled. `projectsView` copies the programs object per response: `projects` only when the viewing project owns the host, `project_listed` for the viewer's slug, `null` when the list is unknown. `GET /v1/hosts/{id}` uses the caller's project with access when there is exactly one; a caller in several, or in none, gets `project_listed: null`. The `projects` list itself goes to org owners and admins only, never to a delegated session (D38). `unlistedReason` is the pre-check for program Run and image deploy, rollback and restart (`imageListed`). `agentws.PolicyDenied` is the message for `policy_denied` from `task_reject` and failed `task_result`, for every task kind.

`HostPrograms.shared_networks` (api-v1 v1.25 item 2) is `[{name, subnet, projects}]` from hello, or `null` when the agent did not send it. `parsePrograms` stores the programs as disabled when the list has more than 8 networks, a duplicate or invalid name, a subnet that is not a canonical RFC 1918 IPv4 prefix of length 16–28, more than 32 member slugs, or a duplicate or invalid slug; a null member list reads as `[]`. `projectsView` gives org owners and admins in a session (not delegated) the whole list; every other caller, delegated sessions included, gets only the networks that list the project in view, without `projects`. With no project in view (`GET /v1/hosts/{id}` for a caller in several projects with access, or a delegated `GET /v1/orgs/{id}/hosts`) that is `[]`; `null` stays `null`.

## Catalog images

Image create and replace take `{"name","kind":"image","spec":ImageSpec}`. An image `name` must not end with `-`, `-prev`, or `-old` (`bad_request` `invalid name`; the agent uses `<project>-<entry>-prev` for the kept container and `<project>-<entry>-old` during a rollback, api-v1 v1.15 rev 3). `command_display` is the normalised reference. `spec_hash` is SHA-256 of canonical `{"env_keys","kind","spec"}`. `env_keys` is one SHA-256 per referenced set, over the sorted key names joined by newlines, not over values. An env-set replace, and a key add or delete, recomputes hashes for entries that reference that set inside the same transaction (until v1.26 it also deleted the unused phase-1 approval rows; that table is gone since 0016). A value-only change does not. Inline env is part of `spec`, so an inline value change does change the hash. `healthy_after_sec` (service, 5–600, default 30) and `timeout_sec` (job, 10–3600, default 600) are both stored, the other kind's at `0`; since api-v1 v1.24.1 a create or replace accepts the other kind's field when it is `0` and ignores it, so a GET body round-trips through PUT with the same `spec_hash`, and any other value is still `bad_request` `invalid timeout_sec` or `invalid healthy_after_sec`. Default image grants are admin `run,stop,restart,logs,deploy` and viewer `logs`. Program default grants are unchanged, and a program owner does not hold `deploy`. `my_actions` for an image owner is `run,stop,restart,logs,deploy,status`. A console catalog PUT and its confirm return `my_actions` for the caller's role: an admin gets the stored admin grants plus `status`, not the owner list.

Deploy, rollback, and remove finish in the HTTP handler. `timeout_sec` is `300 + healthy_after_sec + 60` for a service deploy and for every rollback (including a job rollback). When the spec has `healthcheck`, both use `300 + max(healthy_after_sec, start_period_sec + interval_sec × (retries + 1)) + 60`. A job deploy is `300 + timeout_sec + 60`, and remove and the short actions are 60. `Hub.Image` keeps a frame whose timeout is above 60s until that many seconds (`expires_at` is that deadline). A 60s image frame keeps the 60s TTL. Program frames stay at 15s / 60s. The handler uses `context.WithoutCancel` and then a timeout of `timeout_sec` for the hub wait on remove, and `timeout_sec` plus 30 s on deploy and rollback (api-v1 v1.42: the API's clock starts before the agent's, so without the margin the API always gave up first and dropped the agent's real outcome). The history write, the in-flight release, and the idempotency finish use a fresh context with a five-second timeout and retry once. `http.Server` has no `WriteTimeout`. ReadHeaderTimeout is 10s, ReadTimeout is 30s, and IdleTimeout is 120s. One in-flight row per `(host, entry)` is enforced by `image_deploys_in_flight_uidx` (`WHERE in_flight`) and by the same check in the memstore. The lock is taken after the idempotency claim. A request-level failure deletes that row. A successful remove deletes it too, so remove does not appear in history. A remove that times out is HTTP 504 `timeout`, audits outcome `timeout`, and does not report `missing`. A deploy or rollback timeout with no agent payload stays HTTP 200 with outcome `timeout` and `status.state` `unknown` (`container`, `exit_code`, `started_at`, `finished_at`, and `digest` null, `restart_count` 0, `ports` empty). An agent result of `unknown` is rejected. Each in-flight row stores `in_flight_until` (the API's wait plus 120 seconds). The next deploy, rollback, or remove marks an expired row `timeout`, clears it in the same transaction, and continues. A younger row is still `conflict`, with the message and payload of api-v1 v1.42 item 2 (see Running operations below). History is newest first, at most 50, and since v1.42 starts with the running row, if any. Rollback allows the last three distinct `succeeded` or `unchanged` digests.

The secrets key is `BOT_SECRETS_KEY_FILE` (see Config). AES-256-GCM uses a fresh 12-byte nonce stored beside the ciphertext. Additional data is exactly `project_id|set|key`, `project_id|registry|host`, or `project_id|file|name`. `seal.Box` nil means the key is not configured. Encrypt and decrypt failures are logged as `encrypt failed` or `decrypt failed` with no value, nonce, ciphertext, or path. A decrypt failure on deploy or rollback does not send the task and is HTTP 500 `internal error`. The key is required before the idempotency claim when the entry references any env set, uses `secret_env`, a `files` row still names a secret file, or a stored registry host equals the parsed image host. Run, stop, restart, status, remove, and a public image with no matching registry do not need it. Logs need it only when the resolved env includes a secret key or a files row still names a secret file. A missing key is then `unavailable` `secrets key not configured`: no task is sent and no lines are returned. A plain winning value, a plain file, and a registry credential do not trigger that refusal. Inline `env` clears a secret flag. The nested task `spec` is the stored ImageSpec: inline `env` as written, and `env_sets` and `secret_env` as references. The resolved map (env sets in order, then `secret_env`, then inline `env`) is only the top-level `env`, so each secret value appears once. A top-level `files` array follows `spec.files` order when the list is non-empty, and is omitted when it is empty, as is `spec.files`. `secret_keys` (sorted, possibly `[]`) is sent on `image_deploy` and `image_rollback` only when the host's stored `programs.files` is true. A key is listed when its winning value is an env-set secret that inline env did not override, or references such a key (v1.27). It is omitted for every other host. Secret file content appears only there. `registry_auth` is that one credential, or `null`. A marshalled frame over the agent limit is `bad_request` with message `the resolved environment and files are too large for one task`. Nothing is written, the socket stays up, the in-flight row is released, and the attempt is not audited as a deploy. Every websocket write is capped at 10 seconds even when the task context is longer. The frame is not logged. `ingest.RedactPayload` still only rewrites `cmdline` and is not the secret boundary. Returned lines, audit detail, and the idempotency body replace an env-set secret value (after precedence; inline `env` and plain env-set values are not included) with `preview(v)`, and the registry token and secret file contents with `[REDACTED]`, first (raw, base64, and JSON-escaped, values of at least 6 bytes), then the keyword rule. That replacement applies to free-text `lines`, to error strings, and to every string field of `ImageStatus` and `ImageDeploy` after the agent text has passed the printable-ASCII check. An agent error string that contains one of those forms is redacted in place. The audit reason stays the fixed phrase for its code. `exit_code` is not text. The history row keeps the stored digest. The history GET redacts a copy of each row and does not change the stored value rollback compares. Logs, status, run, stop, restart, and remove do that without putting the values in the task frame (`project` and `entry`, plus a `lines` count for logs). A missing key on status, run, stop, restart, and remove keeps the keyword rule and still returns the agent text. Logs do the same when the entry has no secret env key and no secret file. When it has either, a missing key refuses the call and returns no lines. A decrypt failure logs one `decrypt failed` line with no value, still returns the agent text, and redacts every secret value and secret-file piece that opened. An env or registry decrypt failure does not drop file pieces that opened. An agent field outside the outcome enum, state enum, length caps, or digest shape is outcome `failed` with the fixed message `invalid agent result` on deploy and rollback. The API counts agent lines the way the agent cuts them, in characters (at most 2048 per line and 64 KiB in all), so a long line of non-ASCII text, such as Chinese, is accepted.

Env-set and registry routes use `authz.CapMembers` and require a console session. Any other session kind is `forbidden` before a decrypt. `PUT` parses dotenv before the key check, then seals every key. Inside the same transaction the store keeps each existing key's `is_secret` and stores a key new to the set as secret unless `new_keys_secret` is false. A kept-plain key is written in the clear; a kept-secret key stores that fresh seal. Keys left out of the body are removed. With `mode` `create` (api-v1 v1.19) the store inserts the set row with `ON CONFLICT DO NOTHING` and returns `store.ErrConflict` when no row was inserted, so the existence check and the insert are one statement. With `mode` `merge` `MergeEnvSet` locks the set row (`ErrNotFound` when missing), then its values `FOR UPDATE` (the order `PutEnvSet` and `PutEnvKey` take), refuses an empty value for an existing secret key with `store.ErrSecretEmpty` before any write, upserts each pasted key (existing keys keep `is_secret`), keeps the others, updates the set's `updated_at`, rehashes, and returns the names new to the set for the `env_set.merge` audit row. The handler builds the merge response previews from the stored seals because keys left out of the paste are not in the request. `$` and `\` in a value are stored as written. NUL is still refused, and a value is still at most 4096 bytes. Inline ImageSpec `env` is unchanged. `DELETE` of a referenced set is `conflict` before any rehash. Registry `GET` returns host and username. Tokens are never selected into an HTTP struct. Confirmation rows store `image_digest` and `image_force` so the second step can rebuild the task. Those fields are not on the HTTP confirmation object. Issuing one still audits `program.confirmation_issued` with entry, action, and `spec_hash` only. Image run, stop, restart, logs, and status are not audited. Deploy, rollback, and remove denials are, with the fixed phrase when the agent message contained a secret form and otherwise that message, and with no values. The HTTP `msg` is the redacted text. After the agent answers, those three actions are decision `allowed`: `result` is the outcome, and `error_code` is that outcome unless it is `succeeded` or `unchanged`, which leave `error_code` null.

A single key is written with `PUT /v1/projects/{id}/env-sets/{set}/keys/{key}` and removed with `DELETE` of that path. The put creates the set if needed, seals a secret with additional data `project_id|set|key` and a fresh nonce, and returns the key. `preview` is the first four runes plus U+2026 when the value has at least 16 runes, and four U+2022 bullets otherwise. `GET` returns that preview for a secret and null for a plain key, and never returns the secret. `is_secret` cannot change through the key put. An empty value over an existing secret key is `store.ErrSecretEmpty` (api-v1 v1.18), checked in the store after the `FOR UPDATE` read of the flag, so the transaction writes nothing and the handler audits nothing; a plain or new key still takes `""`. `POST /v1/projects/{id}/env-sets/{set}/secret` `{"keys":[…]}` is the one way to make plain keys secret (api-v1 v1.17, docs/spec-env-make-secret.md): in one transaction it locks the set, then the named values, seals each plain value inside the transaction through a seal callback from the API layer, skips keys already secret, and audits `env_set.key_secret` per changed key. Before sealing, a plain key whose value is empty and that is not a `needs_value` placeholder is refused with `store.EmptySecretKeyError` (it matches `store.ErrSecretEmpty`; `bad_request` `a secret value cannot be empty; give KEY a value first`) and nothing is written (spec-release-v0239 F6). `envChangeFits` refuses the same for `update_env_set` `make_secret` at plan and at confirm, and the confirm maps an `ErrSecretEmpty` from `ApplyEnvSetChange` (a value emptied after its check) to that `bad_request` instead of an internal error. It does not rehash, because the hash covers key names only. A secret key never becomes plain again. A dotenv put takes optional `new_keys_secret` (default true) for new keys only. Key add and delete rehash entries that reference the set; a value-only update does not. There is no visibility `PATCH`. Catalog replace uses `catalog_edit` (owner or admin) for the console put and for the delegated plan and its confirm. Create, delete, and permissions stay `CapProjectWrite`. Log lines, error strings, and the string fields of status and deploy results replace an env-set secret with `preview(v)` and still replace a registry token or a secret-file piece with `[REDACTED]`. The audit reason stays the fixed phrase.

Generated values and references (api-v1 v1.27). `catalog.Generate` validates the generate object and draws values from `crypto/rand`; the password alphabet uses rejection sampling (bytes at or above 248 are dropped) so there is no modulo bias. `keyPutValue` turns the key `PUT` body into the value and the requested flag in one step and forces `Secret` true for a generated value. Generate works on new keys only (rev 3, no regenerate): `PutEnvKey` with `Generated` on any existing key returns `store.ErrKeyExists` under the row lock, before the secret-flag check and before any write, and the handler answers `{KEY} already has a value; edit it to change it` without an audit row. The db and memstore stores decide this the same way. A value is replaced with a typed edit; a database password must be changed in the database first. Generate on a `needs_value` placeholder fills it: the stores read `needs_value` with the row lock and allow it (phase B). Every insert and update of a value writes `reveal_pending`, `needs_value`, and `generated` explicitly: `upsertEnvValue` writes `reveal_pending = generated = <generated secret>` and `needs_value = false`; `insertEnvValue` (set replace and create) and `MakeEnvKeysSecret` write all three false. `generated` stays true after the reveal and only picks the preview: `secretPreview` returns four bullets for it in `envKeyBody`, `fillPreviews`, and `withPreviews`. `RevealEnvKey` is one `UPDATE app.env_values SET reveal_pending = false WHERE … AND reveal_pending AND <project not deleted> RETURNING nonce, ciphertext, key_version, generated`; on no row a second read tells `ErrNotFound` from `ErrConflict`. The memstore does the same under its mutex. The handler opens the seal, then audits `env_set.key_reveal`, then answers; `writeJSON` sends `Cache-Control: no-store`. `mergeEnv` returns an `envMerge` (merged env, sorted secret keys, generated keys) with no reference resolution; program Runs use it as is, so program env stays literal, and their redaction uses `envMerge.forms` too (generated values as four bullets). Image deploys call `mergeImageEnv`, which runs `mergeEnv` and then `catalog.ResolveEnvRefs`, which resolves `${NAME}` in one pass in key order (so the reported error is stable) and returns the referenced names per key; `Resolved.Spread` adds a key to the secret and generated sets when it references a member, one level only because a referenced value is not re-expanded. When the text after `${` up to the next `}` is not a key name, the `${` is literal and scanning resumes after it, so `${A${B}` resolves `${B}`. For a secret key the unknown-name message omits NAME. `refCall` maps a `*catalog.RefError` to `bad_request`; `imageFail` sends that message without `redactExact`, and `auditTaskBuildErr` stores it through `recordImageDeny` without redaction, because `ingest.RedactCmdline` would read a key such as `SECRET_URL` followed by a word as a secret pair, and the message holds only validated key names. A delegated deploy or rollback runs `envRefsOK` before issuing a plan and stores the refusal under the idempotency key; other merge errors are left to confirm. `redactValues` uses the forms of a successful `mergeImageEnv` (exactly the deploy's secret values, generated ones replaced by four bullets instead of a preview) and falls back to the best-effort `redactEnvValues` walk only when `mergeImageEnv` fails. `logsNeedKey` and `imageNeedsKey` need no change: a reference can only make a key secret when the referenced winning key is secret, which they already count (pinned by `TestEnvNeedsKeyAgreesWithMerge`). `imageTask` adds `env_hash` from `seal.Box.EnvHash` (HKDF-SHA256 key, HMAC-SHA256 over sorted `KEY=value\n` lines) only when `host.Programs.EnvHash` and the secrets key is set. `HostPrograms` gains `env_hash` because hello decoding refuses unknown `programs` keys. Phase B (items 4–6): `handleEnvSetCreate` validates the names-only body; a console session calls `createEnvSetNames`, which draws and seals generated values and seals "" for a secret placeholder, then `Store.CreateEnvSetNames`. A delegated session gets `issueEnvSetCreate`: the normalized keys (`envCreateKey`, names, generate objects, flags and, since v1.32 item 2, a plain key's `value`) are the plan body and, with the project and name, the request hash; the plan goes into `app.env_set_confirmations` through `PutEnvSetConfirmation` (rows expired more than `store.RequestKeep`, 7 days, dropped first: an expired plan row, whose body may hold inline plain env values but never a secret value, is kept for up to 7 days after expiry and then pruned at the next plan). `confirmCatalogWrite` falls through to `confirmEnvSetCreate` when no catalog-write plan matches; it checks owner, expiry and key, authorizes `CapMembers`, and calls `CreateEnvSetNames` with the token hash, which locks the plan `FOR UPDATE`, creates the set and its values, and marks the plan used in one transaction (the memstore holds its mutex across the same steps). The delegated GETs return `namesOnly` views without `withPreviews`, so nothing is decrypted. `unfilledReason` reads the entry's set materials (nothing decrypted) and names the first `needs_value` key; `mergeImageEnv` returns it as a `*catalog.RefError` before merging, so the console deploy, the delegated issue (`envRefsOK`) and the confirm check before `MarkConfirmationUsed` (`confirmEnvRefsOK`) all refuse it like a bad reference, and `programGate` refuses program `run` and `restart` with it (the gate runs at issue and at confirm, before the claim and the mark); `stop` is not checked. It refuses even when inline `env` or a later set overrides the key (decision 2026-11-15: "any key the entry resolves" means every key of its env sets and `secret_env` sources). `MakeEnvKeysSecret` keeps `needs_value` in both stores (it is not a value write), and `PutEnvSet`/`CreateEnvSet` refuse `""` for an existing secret key with `ErrSecretEmpty` (`insertEnvValue`, `putEnvSetLocked`), as merge does. `CreateEnvSetNames` refuses duplicate key names with `ErrInvalid` in both stores. `confirmEnvSetCreate` answers a delegated session with `namesOnly` (also the stored idempotent answer) and audits with `viaKind`. `needsSecretsKey` decides whether a create needs the secrets key (a generated key or a secret placeholder).

Value requests (api-v1 v1.28, spec `docs/spec-env-request-value.md`). `store.ValueRequestStore` (embedded in `store.Store`) has create, get, fill and decline; both stores implement it in their own `value_requests.go`. Postgres create takes a per-user `pg_advisory_xact_lock` (no table privilege needed) before it expires the caller's open request for the same key (rev 3) and counts the rest, so concurrent creates cannot pass 20 or leave two open requests for one key; the 7-day cleanup runs after the set lock (the order fill takes) as `DELETE … WHERE id_hash IN (SELECT … FOR UPDATE SKIP LOCKED)`, so it never waits on a fill, and locks the set row so a fill or delete of the set waits. Fill and decline read the request, lock the set row, then lock the request row (`FOR UPDATE OF r`) and check owner, state and expiry again under that lock — the set-then-request order a set delete takes through its cascade, so a fill racing a delete waits instead of deadlocking — then the key row, so a fill and a decline of one request never both succeed and a typed console value written meanwhile wins (`ErrKeyExists`, request left pending). The handler seals before the store call, with the AAD of the request's own project, set and key, so the value never reaches the store unsealed. The read and fill routes call `authz.Authorize` in the handler (`CapRead` for the read, so a creator who no longer reaches the project gets `not_found`; `CapMembers` for the page, fill and decline) and map any denial to `not_found`, so an id says nothing to someone who is not its creator. The memstore drops a deleted set's requests in `DeleteEnvSet`, matching the Postgres cascade, and has `SetNeedsValue` for store tests that need a placeholder without the v1.27 item 4 route. `TestValueRequestUnblocksDeploy` (AC 2) makes placeholders through that route, is refused at deploy, fills them through value requests and deploys.

## Project files

`GET /v1/projects/{id}/files` and `GET`, `PUT`, and `DELETE /v1/projects/{id}/files/{name}` use `authz.CapMembers` and `requireConsole`, the same gate as env sets. A delegated token is `forbidden` before a decrypt. `mcp_access` and `mcp_refresh` never reach that handler: `rejectMCPAudience` returns 401 `invalid_token` on every `/v1` route. A non-member is `not_found`. A name matches `^[a-z0-9][a-z0-9._-]{0,63}$`. Content is UTF-8, 1–65536 bytes, no NUL. A body that is not valid UTF-8 is `invalid json` before decode. `secret` omitted or JSON null means true. `sha256` is stored for every file and returned only for a plain file. List and get do not select ciphertext. `GET` of a secret file is `forbidden`. At most 64 files: the count runs inside a transaction that locks the project row. A new name past that is `bad_request` `too many files`. Replacing an existing name is allowed. `DELETE` takes that same project-row lock before the reference check. `DELETE` of a file named by an image entry of the same project is `conflict` with message `referenced by` and the sorted entry names, and writes one `file.delete` audit row (`name`, `outcome` `conflict`). The handler matches `*store.FileInUse` before the generic conflict mapping.

`seal.FileAAD` is `project_id|file|name`. A nil `Box` refuses a secret `PUT`, a deploy or rollback whose still-existing `files` rows include a secret file, and logs for that entry (`unavailable`, `secrets key not configured`). Logs return no lines and send no task. A missing file does not force the key; the task build returns `bad_request` `file <name> no longer exists` and sends nothing. Tampered ciphertext fails closed (`decrypt failed`, HTTP 500, no task).

ImageSpec rule 13 allows at most 16 rows. `file` must be a file of the same project. `target` is absolute, at most 255 bytes, with no empty, `.`, or `..` segment and no trailing slash, and it is not `/proc`, `/sys`, `/dev`, or under them. Each `file` name appears at most once. Targets are unique among file targets and must not overlap a volume target in either direction. Both sides are cleaned with `path.Clean` first. A volume target that cleans to `/` overlaps every file. Otherwise an exact match or a `/`-boundary prefix either way is `invalid files`. Volume rule 8 still accepts `/`, a trailing slash, and empty segments on an entry with no files. One file under another file's target is allowed. Errors are `invalid files` or `unknown file` and do not echo a value. Omitted or null `files` becomes `[]`. `SpecJSON` always emits `files` (empty is `[]`) for storage and for catalog GET. The hash input omits an empty list, so it matches the wave 2a canonical spec and an env-set replace does not change the hash of an entry without files. A non-empty list is part of the hash. A `GET` of an image row written before this change injects `files:[]` in the JSON response and does not rewrite the stored hash. A file `PUT` does not rehash entries.

Deploy and rollback of a non-empty `files` list require `programs.files`. The refusal is `bad_request` `this host's agent does not support files`, after the container check and before the digest check, the key check, the idempotency claim, and confirmation. `confirmImage` repeats it and does not mark the token used on denial. The task map includes `files` only when the list is non-empty. Secret-file redaction adds the whole content when it is 6–4096 bytes, each trimmed line of 16–4096 bytes, and, when the content is JSON, each string value of 16–4096 bytes and each trimmed line inside it. Those pieces are replaced with `[REDACTED]` in raw, base64, and JSON-escaped form on `image_logs`, on deploy and rollback result lines, and in the string fields of status and deploy results. Secret files under 6 bytes are not redacted from logs. A secret whose single line is longer than 4096 bytes is not exact-matched (the per-piece bound; helper log lines are cut at 2048 characters). Plain file content is not redacted. A missing or undecryptable sibling is skipped while building that set. An env or registry decrypt failure does not drop pieces from files that opened. Deploy and rollback still refuse a missing file. Run, stop, restart, logs, status, and remove do not send files. Audit is `file.put` (`name`, `is_secret`, `size`) and `file.delete` (`name`, `outcome`). A completed delete has `outcome` `deleted`. A delete refused because an entry still names the file has `outcome` `conflict`. Neither row contains content or `sha256`.

Docker health reuses `metrics.health_results` (`protocol` `docker`, `result` `success` or `unhealthy`, null `check_id`, `port`, `http_status`, and `latency_ms`). `hosts.programs` is jsonb, so `docker_health` and `healthcheck` are two more booleans on that object and need no migration; a missing key is false. Ingest accepts the docker sample only when the stored programs advertised `docker_health`, and otherwise rejects the batch without closing the socket. `config.docker_health` is true on `hello_ok` and `config_update` only then, and is omitted otherwise, including when false. The service health join keeps a docker row only when `time` is at or after `now` minus 2 minutes, orders that row ahead of every non-docker row (`protocol IS DISTINCT FROM 'docker'`, so a null protocol stays a check), and otherwise uses the latest non-docker row at any age. A fresh `success` is `up` and any other fresh result, including `unhealthy`, is `down`. `health.source` is `docker`, `check`, or null, and docker latency is null. History returns the same null columns. ImageSpec `healthcheck` is optional, refused on a job with `healthcheck applies to services`, refused when `test[0]` is exactly `CMD`, `CMD-SHELL`, or `NONE` (api-v1 v1.18, in `decodeHealthTest`, so create, `PUT`, and the confirm rebuild all apply it; stored entries are not rewritten), stored complete (defaults 30, 5, 3, and 0; `timeout_sec` must be less than `interval_sec`), included in `spec_hash` only when present, and quoted in the v1.12 plan the same way as `command`. Deploybot stores optional ImageSpec `logging` (`max_size_mb` 1–100, `max_files` 1–10, both required) on services and jobs as part of `spec_hash`, and refuses a deploy, rollback, or job run that sets it when `programs.logging` is not true with `bad_request` `this host's agent does not support log settings`, sending no task and writing no deploy row.

Deploybot stores an optional ImageSpec `health_policy` on services (api-v1 v1.15): `on_deploy_failure` `rollback`, `stop`, or `keep`; `on_unhealthy` `none`, `restart`, or `rollback`; `unhealthy_after_sec` 15–600; `max_actions_per_hour` 1–10. ## Health-check edits over MCP

A console `PUT /v1/services/{id}/health-checks` is unchanged: it replaces the set and pushes `config_update`. `idempotency_key` on that call is ignored, and the call does not claim the key. An `api_delegated` session must send a v1.6 idempotency key. The handler still checks permission (D38), and the body (at most 10 checks, port open on the service, protocol, path, interval, expect) before it looks at the key. A failure there is `bad_request` and claims nothing. A valid delegated call stores a plan and returns 202. The check rows stay as they were, and no `config_update` is pushed.

The plan sentence matches the v1.10 example, with the label and each HTTP path Go-quoted (`strconv.Quote`). The host name is not quoted. The label is the trimmed display name, or the discovered name when that is empty. A tcp item is `tcp <port>` with no interval. An http item is `http <port> <quoted path> every <interval> s`. A check with `enabled` false ends with ` (disabled)`. Items stay in request order. Each port that has both protocols adds ` (tcp <port> is redundant with http <port>)`, ports ascending. An empty set says `will remove all health checks from <quoted label> (<host>)`. One check uses the singular `health check`. The redundant tcp check is still stored.

The confirmation id is a catalog-style token: 256 bits, base64url, stored only as SHA-256. It expires five minutes after issue, is single-use, and is bound to the user, the service, a SHA-256 of the normalized checks in request order plus the service id, and a SHA-256 of the current check set. The current-set hash sorts a copy by protocol, port, path, interval, expect, and enabled, so a memstore map walk cannot change it. Check ids are not part of either hash. The idempotency key is not part of the request hash. The same user, key, and normalized body replays the stored 202. A different body with that key is `conflict`. Confirm requires the same key. A mismatch is `conflict` and does not consume the plan.

`POST /v1/confirmations/{id}` loads `catalog_confirmations` first. A miss loads `service_confirmations`, and a miss there loads `catalog_write_confirmations`. Unknown, used, expired, and foreign ids are `not_found`. Confirm loads the service again and runs `CapServiceWrite` with the same D38 rules. A missing service is `not_found`. A denial is `forbidden` and leaves the plan unused. The handler hashes the current set once. A mismatch is `conflict` with message `conflict`, and the plan stays unused. A match calls the store, which locks the service row (`SELECT … FOR UPDATE` on `app.services`; the memstore holds its mutex), re-reads the set, and marks the plan and replaces the checks in that same transaction. A set that changed after the handler's first read is `conflict`, the transaction rolls back, and the plan stays unused, so a later confirm still sees the conflict. The console replace takes the same service lock. A match pushes `config_update` and returns `{"checks":[HealthCheck]}`. The idempotency row then holds that 200, so repeating the original PUT replays it and does not replace again. A conflict does not replace that stored 202.

Audit is `health_checks.confirmation_issued` at issue (`service` label, `host` name, `count`) and `health_checks.replace` on the replace, both `via` `mcp` for a delegated session. Detail does not include the token or the check paths. The audit row carries the host's org and the service's project. The confirmation row's `project_id` is the service's project (null for an org-level service).

`migrations/0011_service_confirmations.sql` creates `app.service_confirmations`. Columns follow v1.10 item 7, including `checks jsonb NOT NULL` (a JSON array of the normalized inputs, in request order, applied on confirm and not returned on the 202). `action` is fixed to `health_checks`. The service foreign key is `ON DELETE CASCADE`. User and project foreign keys match catalog confirmations. `deploybot_api` may select, insert, and delete, and may update only `used_at`. Table-level UPDATE stays false. `--migrate` ignores `0011_service_confirmations.down.sql`. That file is a hand-run rollback: run it as `deploybot_owner`, then `DELETE FROM app.schema_migrations WHERE name = '0011_service_confirmations.sql'`. Pending plans are dropped. Nothing they named was applied yet.

## Registry tags and tag digests

`GET /v1/projects/{id}/image-tags?image=<ref>` and `GET /v1/projects/{id}/image-digest?image=<repo>:<tag>` follow api-v1 v1.16 (rev 4) and `docs/spec-registry-tags.md` §11–§13. They sit outside `/catalog/` so catalog entries named `image-tags` or `image-digest` stay readable. Both handlers call `authz.Authorize` with `CapMembers`, then `requireConsole`, so a viewer and an `api_delegated` session are `forbidden` and a live MCP token is 401 `invalid_token` before the handler. They are registered `delegatedDeny` and are not MCP tools. `image` goes through `catalog.ParseImageRef`, whose `ImageRef` carries `Path`, `Tag`, `Digest`, and `TagGiven`; the tags route ignores tag and digest, and the digest route needs a written tag and no digest. Either failure is `bad_request` `invalid image`. The host must be a registry host stored in **this** project (`GetRegistryMaterial`) or one of `docker.io`, `ghcr.io`, `quay.io`, `gcr.io`, `registry.gitlab.com`, `public.ecr.aws`, `mcr.microsoft.com`, and must not name a port other than 443; otherwise `bad_request` `registry not allowed`, before any DNS lookup. `docker.io` is fetched from `registry-1.docker.io`.

`main` builds one `registry.Service` (client, per-user limiter, cache, concurrency semaphore) and sets `Server.Registry`; a nil service makes both routes 503 `unavailable` `registry lookups unavailable`. The client ignores proxy variables and dials through a guard that resolves the host, refuses any port but 443, skips refused addresses, and dials the remaining ones by IP in order, so the checked address is the one connected. `net.Dialer.Control` re-checks the socket address and port. Refused addresses: loopback, private (RFC 1918 and ULA), link-local, CGNAT, multicast, unspecified, `0.0.0.0/8`, `192.0.0.0/24`, `192.0.2.0/24`, `198.18.0.0/15`, `198.51.100.0/24`, `203.0.113.0/24`, `240.0.0.0/4` (with broadcast), `168.63.129.16`, `fec0::/10`, `100::/64`, and the translated forms NAT64 (`64:ff9b::/96`, `64:ff9b:1::/48`), IPv4-compatible (`::/96`) and 6to4 (`2002::/16`), which are refused as whole ranges rather than decoded; any zoned IPv6 address is refused, and IPv4-mapped forms are unmapped first. The registry URL, the token realm, every redirect (at most 3; `Authorization` dropped on any host change, including a subdomain), and every `Link` next page (same host) must be HTTPS on port 443 with no userinfo and no IPv6 zone. `BOT_API_REGISTRY_ALLOW_PRIVATE=1` lifts the address and port checks only. Limits: 5 s per request, 12 s per lookup, 32 KiB of response headers, 1 MiB per tags or token body, 4 MiB per manifest body, 5 pages and 500 tags read, 32 lookups at once across all users.

A 401 runs the Bearer flow once with scope `repository:<path>:pull`. The stored username and token go as Basic only to a realm whose host and port equal the registry's (case-insensitive, an explicit `:443` ignored on both sides), or to `auth.docker.io` for `docker.io`; any other realm is asked anonymously. A plain `Basic` challenge is answered with the stored credential for that host. The client reports whether the credential was sent. Tags passing `catalog.ValidTag` are kept, de-duplicated, sorted (semver-like descending, then `latest`, then reverse lexical), and cut to 200; `truncated` is also true when the page or tag cap left tags unread. The digest route sends `HEAD /v2/<path>/manifests/<tag>` with the four manifest media types in `Accept`, reads `Docker-Content-Digest`, falls back to a GET whose body is hashed with sha256, and checks the result with `catalog.ValidDigest`.

A failed lookup is envelope code `registry_unavailable` (HTTP 502) with payload `{"reason":…}`: `auth_failed` (the stored credential was sent and refused with 401 or 403), `not_found` (404, or 401/403 when no credential was sent: missing or private, which is how Docker Hub answers a missing repository), `timeout`, `unreachable` (DNS, connect, TLS, an address, port, or redirect refusal, or a registry or realm answering 429 or 5xx), or `bad_response` (a malformed answer or an invalid digest). Registry bodies, URLs, and tokens are never returned or logged. `cachedLookup` serves both routes: the cache (60 s per project, host, path, and tag for digests; at most 1024 entries, then new results are not stored; errors are not cached), then a concurrency slot (none free: 429 `rate_limited`, `Retry-After: 1`), then the per-user bucket of 20 uncached lookups per minute shared by both routes (429 with `Retry-After` in whole seconds; a refused call is not counted), then `openRegistry` with additional data `project_id|registry|host` (a missing key gives the deploy routes' 503 `unavailable` `secrets key not configured`; a decrypt failure is 500 with the log line `decrypt failed`). Each lookup, cache hits included (`outcome=cache`), logs one `registry lookup` line with `kind`, `host`, `path`, `outcome`, `ms`, and `auth` (`stored` only when the credential was sent, `anonymous` otherwise, `cache` on a hit). When the stored credential was refused (`auth_failed`, or `login_failed` in image access) the line also has `status` (401 or 403), `stage` (`token` for the realm request, `manifest`, or `tags`) and `registry_code`, the first OCI `errors[].code` of a 401/403 body read up to 4 KiB, kept only when it is one of `UNAUTHORIZED`, `DENIED`, `NAME_UNKNOWN`, `MANIFEST_UNKNOWN`, `TOOMANYREQUESTS` or `UNSUPPORTED` (empty otherwise, and empty at the manifest step unless the digest GET fallback ran, since a HEAD answer has no body); the error message is never kept (spec `docs/spec-registry-refusal-detail.md`). There is no audit row.

## Connect GitHub token refresh (api-v1 v1.43)

Spec `docs/spec-github-token-refresh.md` rev 1; migration 0028. `github.Client.Exchange` returns a `github.Token` (`Access`, `Refresh`, `ExpiresAt`, `RefreshExpiresAt`, the times from `expires_in` and `refresh_token_expires_in` on the injectable `Config.Now`; a refresh token must start `ghr_` and pass `tokenOK`). `Client.Refresh` posts `grant_type=refresh_token`; GitHub's `bad_refresh_token` is `github.ErrRefreshRejected`, anything else `ErrFailed`, never with a body. Both share `tokenCall`, which returns those sentinels; `Exchange` maps every failure to `ErrFailed`.

Storage: `store.RegistryRefreshMaterial` (sealed refresh token, `AccessExpiresAt`, `RefreshExpiresAt`) is embedded in `RegistryWrite` and `RegistryMaterial`; `RegistryWrite.Norm` drops it for a manual row, so a manual PUT over a github row clears it. `putRegistryRow` writes it in the same upsert as the token (the callback seals it with `seal.RegistryRefreshAAD` in `sealRefreshMaterial`). `RefreshRegistry` (new token and material, never `updated_at`) and `ClearRegistryRefresh` (refresh token and its expiry only; `access_expires_at` stays) are `UPDATE … WHERE source = 'github' AND refresh_nonce = $old` and report whether a row changed; `ListRegistryRefreshDue` lists github rows of live projects with a refresh token expiring before a time. The memstore does the same under `m.mu`; `TestParityRegistryRefresh` covers both.

Use: `registryToken(ctx, project, host, within)` (`internal/api/registry_refresh.go`) reads the row and, when `refreshDue` (Connect GitHub configured, a secrets key, `GitHubRefreshOff` false, a github row with a refresh token and less than `within` left) or the login holds a pending pair, calls `refreshGitHub`, then opens the access token. Callers: `registryAuth` for the deploy and rollback frames with `refreshOnTask` (75 min), `cachedLookup` (tags, digest) and `probeAccess` (image access, readiness, the hourly registry check) with `refreshOnUse` (30 min). Redaction (`redactValues`, `refreshNever`) and the reconnect and disconnect revokes (`githubTokenOf`, `deleteGitHubRegistry`) open the stored token as it is.

`Server.refresh` (`refreshLocks`) holds one `loginRefresh` per login: a one-slot channel as the lock (the wait selects on the caller's context, spec §10.3), and in-memory state that keeps the entry alive while set: `pending` (a sealed pair not yet stored, with the old refresh nonce it replaces), `retryAfter` (60 s after an unavailable refresh, or after the refresh token failed to open before any GitHub call, so the Error line is not repeated on every use) and `rejectedNonce`. An entry is dropped when its last user releases it and it holds nothing; the upkeep also drops entries whose backoff ran out (`dropIdle`). `refreshGitHub` takes the lock, then works on `context.WithoutCancel`, since once GitHub answers it has rotated. It returns the material to use and, for a pair not sealed yet, its plain access token, which `registryToken` then uses directly. Revokes of tokens nobody holds (a stale or orphaned pending pair, a lost write) are collected and run after the lock is released. Under the lock it re-reads the row and, in order: a gone row (`ErrNotFound`) revokes a pending access token and clears all state (`forgetLogin`); a row already holding the pending pair's write (an earlier write that committed but reported an error) clears `pending`; a pending pair whose old nonce still matches is stored with one short try; an unsealed one (`refreshUnsealed`) is sealed first, and when its own access token is due for the call's window it is first refreshed with its own refresh token (the one GitHub honours; the row's was spent), the new pair replacing it (a rejection there drops the pair and clears the row's refresh token, audited once; unavailable sets `retryAfter` and uses the pending token) (`pendingStoreWait`, 3 s; a failure leaves it for the next use or sweep); a pending pair for a row that changed is revoked and dropped; then it returns when not due; for a `rejectedNonce` that matches, retries the clear and returns without calling GitHub; returns during `retryAfter`; opens the refresh token (a failure logs `decrypt failed` with `project_id` and `host`); calls GitHub (15 s). `ErrRefreshRejected`: Warn `reason=rejected`, `clearRejected` (ClearRegistryRefresh on the old nonce; audit `registry.github_refresh_rejected`, `via` `system`, only when the clear changed the row; a failed clear logs `github refresh clear failed` and sets `rejectedNonce`), then a re-read. `ErrFailed`: Warn `reason=unavailable`, set `retryAfter`, use the current token. Success: `sealAndStore` seals the pair; a seal failure (GitHub has already spent the old refresh token) keeps the pair unsealed in `pending`, logs `encrypt failed` (at most once a minute, `sealLogAfter`) and uses its access token, so the spent token is never sent again and the next use or sweep seals and stores it. `storeRefreshed` then writes with its own 20-second budget, up to 3 tries (`refreshStoreBackoff` 250 ms, then 500 ms). Stored: Info `github token refreshed` and the written material is returned (`withRefreshed`, no re-read). Otherwise the row is read again before anything is revoked, because a write can commit and still report an error (a reset after commit, so a retry then sees the nonce changed): a row holding our write (`holdsWrite`: the same sealed access nonce and ciphertext) counts as stored; a re-read that fails (other than `ErrNotFound`) is unknown, since our write may have committed, and parks the pair whatever the write reported; the store failing while the row still holds the old nonce also parks the pair in `pending` (Error `github refresh not stored`) and returns the new token for this use; a row holding something else (a manual write landed first) or no row means the conditional write was lost: the new access token is revoked, best effort, and that row is used. Reconnect (`handleGitHubCallback`, from reading the old token through the write) and disconnect (`deleteGitHubRegistry`, which reads the row again under the lock) take the same login lock. The callback waits at most `githubConnectLockWait` (30 s) or until the browser goes away; then it answers `bad_gateway` `GitHub sign-in failed; try again`, revokes the new token and leaves the row (the OAuth state is already spent, so the person starts again). A cancelled disconnect wait answers as the store error. A disconnect whose re-read under the lock finds the login changed (no longer `github`, or another GitHub account; a refresh of the same account is not a change) leaves the row untouched and answers `409 conflict` `The registry login changed; reload and try again`, with no audit row and no revoke, so it never removes a login it did not mean to. The token they revoke is the live one (`liveGitHubToken`: a matching pending pair's access token, else the stored one; nothing for a manual row, so a personal access token is never sent to GitHub), plus the access token of a pending pair that no longer matches the row (`staleOf`); they drop the pending pair, and the revokes run after the lock is released. Refresh safety holds within one process (§10.6): the conditional write keeps a second process from overwriting a newer row, but two processes refreshing the same login at once can still lose it.

Upkeep: `Server.RunGitHubRefresh` (started by `run.go`'s `startBackground` next to `startProblems`, not inside it, so it runs with `BOT_API_PROBLEMS=off`; `TestStartBackgroundUpkeep`) sweeps once at start and then on an hourly ticker; `SweepGitHubRefresh` lists `ListRegistryRefreshDue(now + 90 min)` plus the logins holding a pending pair and calls `refreshGitHub` with `refreshUpkeep` for each, within a 10-minute deadline (a per-login failure logs `github refresh sweep failed` with `project_id` and `host`). It does nothing while `githubRefreshOn` is false. It is a separate loop rather than a step of `hourlyProblems` because the problems sweep does not run at all when problems are off. `BOT_API_GITHUB_REFRESH` (`config.GitHubRefreshOff`) sets `Server.GitHubRefreshOff`.

Problems and revokes: `noteRegistryAccess` takes the image-access login kind and uses `detailGitHubLoginRefused` for a `github` login. `revokeGitHub` takes `expired` (`accessExpired`: `access_expires_at` past); a failed revoke of an expired token is an Info line with `reason=expired`, any other a Warn.

Spec `docs/spec-agent-self-upgrade.md` rev 1; migration 0032; agent-protocol v1.20. The server names only the version (`BOT_API_LATEST_AGENT_VERSION`); the host's helper checks its runner.toml opt-in, downloads from a fixed GitHub URL, verifies the signature and rolls back by itself, so the API never sees a bundle. Store interface `store.AgentUpgradeStore` (Postgres `db/agent_upgrades.go`, memstore `memstore/agent_upgrades.go`, parity and migration tests in `db/agent_upgrades_parity_test.go`); route, settle and sweep in `api/agent_upgrade.go`; hello and frame parsing in `agentws/agent_upgrade.go`.

- **One open row per host:** `StartAgentUpgrade` refuses with `ErrConflict` while a `started` or `running` row exists; Postgres takes a per-host advisory lock for the check and insert, and the partial unique index `host_agent_upgrades_open_uidx` backs it (a violation maps to `ErrConflict`). `SettleAgentUpgrade(id, from []string, to, …)` is a conditional update. The route moves a row only from exactly `started` (to running, or to failed when the agent answered with an error; with no answer the row stays started); the hello hook and the sweep settle from either open state (`store.AgentUpgradeOpenStates`), so a hook that read `started` still settles after the route set `running`. Whoever moves the row first wins, and only that caller writes the audit row and the problem.
- **Problems:** only outcomes nobody saw open one: `rolled_back`, `unknown`, and `failed` reported by the host. A task refusal is answered 409 to the caller and kept on the row. A problem is never left open forever: the next `succeeded` resolves it, a hello with no open row resolves it when the agent runs the newest row's target or the latest release or newer (`upgradeCaughtUp`, which also turns an `unknown` row whose target the host now runs into `succeeded`), and the minute sweep resolves it for a host that is current, gone, revoked or archived.
- **Clocks:** host results carry the host's time (`at`). The API assumes host and API clocks agree within minutes (both run NTP): `at` is compared with the row's start (30 s back, below) and a result more than 5 minutes ahead of the API clock (`agentUpgradeFutureLimit`) is ignored with a Warn line, so a host with a clock far ahead cannot make a stale result look new. A host whose clock is far behind has its real results ignored; its row then settles from `agent_version` on the next hello, or as `unknown`.
- **Why a task, then hello:** a task lives only while the agent's socket does, and the upgrade restarts the agent. The task only answers whether the helper started the upgrade unit; the outcome arrives as `last_upgrade` in the new agent's hello (or the old one's after a rollback), or as an `agent_upgrade_result` frame when the old agent sees a failure before it was replaced. The hub calls the API's `UpgradeHook` on the read loop after `hello_ok`, so a settle never delays the acknowledged hello that the installer's marker check waits for.
- **Old results:** the agent sends the same `last_upgrade` on every hello until the next upgrade writes a new one. A result counts only for the row whose `to` it names and only when its `at` is at most 30 s before the row started (`agentUpgradeResultSkew`); an older result for the same version belongs to an earlier attempt.
- **Stuck rows:** `RunAgentUpgrades` runs every minute regardless of `BOT_API_PROBLEMS`, and the start route settles the host's own stale row first, so a row never blocks a new upgrade for longer than 15 minutes.
- `programs.agent_upgrade` lives in the stored programs object (`omitempty`) and is cleared from every Host answer; `agent_upgrade_allowed` replaces it.

## Host resource alerts (api-v1 v1.49)

Spec `docs/spec-host-resource-alerts.md` rev 1; migration 0033; no agent change. A step of the minute problems sweep (`sweepHostResources` in `internal/api/problems_host_resources.go`, after the host file check, so it shares the 5-minute grace and `BOT_API_PROBLEMS=off`).

- **Watched hosts:** from `ListProblemHosts` (not revoked), always on, `last_seen_at` under 2 minutes old and `alerts_enabled` (no row means on; `settingsFor`). Their ids go into one `HostResourceStats(measurement, ids, now)` call per measurement (`mem`, `disk`, `cpu`, `load`): four grouped reads per minute whatever the host count, each over `(now-15m, now]` on the `(host_id, time DESC)` index, returning per host (and mount for disk) the newest value and count, average, minimum and maximum over the 5, 10 and 15 minute windows (and the average total for memory). The value is available bytes, `used_percent`, `100 - usage_idle` of `cpu-total`, or `load5 / n_cpus` (rows with no cores skipped). The memstore aggregates the same way (parity test). At most 50 mounts per host are judged, in path order (stats come sorted).
- **Judging** (`judgeResource`): memory opens on the 10-minute average `available < max(15 % of total, 96 MiB)` and resolves on the 5-minute average `>= max(20 %, 128 MiB)`; disk opens when the 10-minute minimum is `>= 90` (the newest sample is inside that window) and resolves when the 5-minute maximum is `< 85`; cpu opens on the 15-minute average busy `>= 90` and resolves under 75 over 5 minutes; load opens at 2.0 per core over 15 minutes and resolves under 1.2 over 5. An override replaces the open point and puts the resolve point 5 kinder (memory +5, disk and cpu −5); with a memory override the percent alone decides (no MiB floors). For an open subject the resolve test runs first, so 5 minutes of recovery resolve it while the longer open window still averages the bad minutes; otherwise the open test runs, and between the points nothing changes. A window counts only with at least half the samples the metrics interval gives it (`resourceSampleEvery` = `agentws.MetricsIntervalSec`, the interval the hub sends in its config frame); window labels in the text come from the window constants.
- **Leftovers:** a measurement whose newest sample is 2 minutes old is not judged. Every open `host_resource` row not judged this minute resolves, unless its measurement's read failed this minute: "No longer reported: the host no longer reports this mount." for a disk of a watched host (gone, or past the 50-mount cap), "No longer checked: …" otherwise (not always on, not reporting, alerts off, revoked, no recent samples).
- **Text, subjects and links:** subjects `<host>:mem`, `<host>:disk:<path>`, `<host>:cpu`, `<host>:load`. A mount that is not printable UTF-8, starts with `#`, or would push the subject past 300 characters is `<host>:disk:#<16 hex of sha256(path)>` (`pathHash`), so `ValidProblemOpen` never fails. Titles carry `mountLabel(path)` (non-printable characters as U+FFFD, at most 64 characters and "…"), the host name and numbers only. `needs_action` for memory and disk, `heads_up` for cpu and load; org owners and admins (`problemReader.sees`). The link is `/hosts/<id>?range=1h`, plus `&disk=<escaped path>` for disk; for a hashed subject `problemReader.resourceHref` matches the hash against the host's mounts of the last 24 hours (read once per host per request) and leaves `disk` out without a match.
- **Ingest:** disk paths with control characters are not refused at ingest: one refused sample refuses the agent's whole batch (`ValidateBatch`), which would drop all of that host's metrics. The sweep's hashing and labels cover them instead.
- **Settings:** `app.host_alert_settings`, one row per host, written only when a field changes (`host.alert_settings` audit with the host name and the changed fields; via `mcp` for a delegated token). The PUT is `delegatedAllow` with the handler's own org owner or admin check (`CapHostAdmin`): the API keeps no plan for it. The user's confirm step for MCP lives in the MCP server (`set_alert_settings`, then `confirm`), so all API state stays in Postgres.
- **Charts:** `QueryChart` takes the disk mount (`path = $5`, default `/`); `mem` adds `available`. `GET /v1/hosts/{id}/disks` is `ListHostDisks` over the last 24 hours (per mount the newest row's fstype, `total`, `used`, `used_percent` and time (api-v1 v1.59 item 1; a missing size is null), at most `store.MaxHostDisks` = 200 by path).
- **Docker usage (api-v1 v1.59 item 2):** `POST /v1/hosts/{id}/docker-usage` (`api/internal/api/docker_usage.go`) is `CapHostAdmin` (org owners and admins; delegated allowed). It refuses a revoked host (404), an offline host (503 `host_offline`, as every route), an agent before 0.2.17 (409 `agent_too_old`; a dev build's fourth part is ignored) and a second call while one runs for that host (409 `busy`; `Server.dockerUsageRuns`, a `sync.Map` released on every path, per API process) before any task, then `Hub.DockerUsage` (`agentws/docker_usage.go`) sends `docker_usage` with spec `{}` and `timeout_sec` 45 and waits up to 50 s. The hub reads the answer field by field (`ParseDockerUsage`: each entry decoded on its own, a null or wrong-typed one dropped, lists sorted again by size then name and capped at 10, strings at 200 characters, negative counts 0, unknown sizes null) and returns the reason as `CallError.Agent`; the handler maps `docker_usage_disabled` 409, `docker_unavailable` 502, `timeout` (or no answer) 504, the agent's `busy` 409 `busy`, no reason on an `unavailable` error 503 `host_offline`, anything else 502 `bad_gateway`, each with a fixed sentence. Every call after the host gate is audited as `host.docker_usage` (denied for the refusals, allowed with the failure code otherwise; after the wait it is written with `context.WithoutCancel`, so a caller who left is still recorded). Nothing is stored. The metrics `path` is refused with more than 1024 characters or a control character.
- **Cost:** `TestHostResourceOneQueryPerMeasurement` counts the reads (four per sweep); `TestHostResourceStatsPerf` (opt in, `BOT_TEST_PERF=1`, test database) times them over 7 days of samples for 10 hosts, on the server's own time (`EXPLAIN ANALYZE` planning plus execution), because wall time from a test machine is mostly network. On the pi4 test database (2026-11-23) the four reads took a median of 28.3 ms, of which planning over the hypertable chunks is the larger part.

## Remove a revoked host (api-v1 v1.40)

Spec `docs/spec-host-remove.md` rev 1. Deleting a host would mean rewriting history (the audit log, services, credentials, join tokens and ingest batches reference it), so a revoked host is archived instead: migration 0026 adds `app.hosts.archived_at` with the check `hosts_archived_revoked_chk (archived_at IS NULL OR revoked_at IS NOT NULL)`. `store.Host.ArchivedAt` is read wherever hosts are scanned (`hostCols`). `store.Store.ArchiveHost(ctx, hostID, at)` returns the host's `archived_at`: Postgres locks the row (`SELECT revoked_at, archived_at … FOR UPDATE`), answers `ErrState` for a live host, returns the stored time without a write for an archived one, and otherwise sets `at`; memstore follows the same rules. The lists filter in one place per store: Postgres `listHosts` (behind `ListHosts` and `ListOrgHosts`) has `h.archived_at IS NULL`, memstore `ListHosts` and `ListOrgHosts` skip archived hosts, and `ListProjectServices` drops rows of archived hosts in every view (`projectServiceWhere` in Postgres, `serviceInViewLocked` in memstore). Reads by id (`GetHost`, `ListServices` by host, metrics, processes, access) are unchanged. Parity tests: `internal/db/host_archive_parity_test.go` (it clears `archived_at` on its org at cleanup); the migration test runs the check, down and up again in one rolled-back transaction (`internal/db/host_archive_migration_test.go`). 0026 does not touch the columns the 0015 down and phase 1 restore rewrite, so those tests need no change. `handleHostArchive` (`POST /v1/hosts/{id}/archive`, `delegatedDeny`) gates with `CapHostAdmin` and audit action `host.archive` (a denial is audited by the gate), maps `ErrState` to `conflict` `revoke this host first`, writes `host.archive` only when this call archived the host (it was not archived when fetched and the store returned this call's time), and answers with `hostRead`. HTTP tests: `internal/api/host_archive_http_test.go`.

## Deploybot on containers (api-v1 v1.50)

Spec `../../docs/spec-deploybot-on-containers.md` §3.3; agent side agent-protocol v1.21; user-facing rules in `../README.md` (Deploybot on containers); images in `../../docs/containers.md`.

- **`network: "host"`** lives in `catalog` (`decodeNetwork`, `checkNetwork` in `networks.go`; `Image.Network`, written into the stored spec only when set, so older entries keep their bytes and hash). The gate `hostNetworkReady` (`internal/api/catalog_image.go`) runs for deploy, rollback and run in `imageMutate`, `finishImageShort` and `confirmImage`, after the shared-network gate, and reads `HostPrograms.HostNetwork` (hello `programs.host_network`, hidden from Host answers by `withUpdateHint`).
- **Late results.** The task id is chosen by the API (`agentws.Hub.ImageWithID`) and stored on the in-flight row before the frame is written (`SetImageOpTask`), so the mapping survives the process. `Hub.onTaskResult` hands a result to its waiter as before; when there is none it calls the `LateHook` (`Server.LateResultHook`, wired in `run.go` next to the upgrade hook) on the read loop with a 10 s store budget. The hook reads `ImageDeployByTask` (host and task id; a result from another host never matches), turns the result into an outcome with the same `takeDeploy` code as an on-time result (redaction forms from the entry's current spec, `lateForms`), and writes with `SettleLateImageDeploy`, whose `WHERE in_flight OR outcome = 'timeout'` makes a race with the waiting process or a second copy of the result harmless. `task_result_ack` is sent after `task_ack` for image deploy, rollback and start results (the waiter records the task kind) and for every result no waiter took, unless the hook reports a store error. Memstore keeps the task ids in a side map (`deployTasks`) keyed by row id; parity in `internal/db/deploy_task_parity_test.go`, HTTP tests in `internal/api/late_result_http_test.go` (restart = a second hub and Server over the same store).
- **Drops and the sweep.** When the waiter ends with `CallError.MaybeSent` (the socket dropped or was replaced after the frame was written), `performImage` keeps a deploy or rollback row in flight (it clears `hold`, so the deferred `ReleaseImageOp` does not run) and still answers `unavailable`; a non-`MaybeSent` unavailable stays the v1.47 `refused` row. `Server.RunImageOpSweep` (started in `run.go` next to `RunAgentUpgrades`) calls `SweepImageOps` every minute: `TimeoutStaleImageOps(now)` is one `UPDATE … WHERE in_flight AND in_flight_until < now RETURNING` joined to the entry (Postgres) or the same loop (memstore), so it needs no memory and is safe in several processes. Swept deploy and rollback rows are audited with `"swept": true` (`auditSettled`, shared with the late path's `"late": true`) and passed to `DeployHook`. Tests: `TestDropAfterWriteKeepsRowForLateResult`, `TestDropAfterWriteSweptToTimeout`, `TestDropBeforeWriteDeletesRow` (the hub's clock is moved past the ping window so the frame is never written), `TestParityTimeoutStaleImageOps`.
- **Review changes (api-v1 v1.50 item 9).** `CallError.FromResult` marks errors built from a `task_result`, so `performImage` acks (`Hub.AckResult`, the host's current socket) only results the agent keeps, and only after the row write; the hub acks `image_start` at delivery. `deliver` takes the delivering connection and returns `foreignConn` for a waiter of another socket (acked, dropped, waiter kept). `redactValuesCheck` is `redactValues` that reports decrypt failures, for `lateForms`. A late refusal is `auditLateDeny`. Tests: `internal/api/containers_review_test.go` (`failFinish` wraps memstore to fail `FinishImageDeployWith`; the race test runs a second hub over the same store in both orders).
- **Env-value secrets.** `config.FromEnv` reads `BOT_SECRETS_KEY`, `BOT_API_MCP_CLIENT_SECRET` and `BOT_API_GITHUB_CLIENT_SECRET` and refuses both forms of one; `LoadSecretsKey`, `LoadMCPClientSecret` and `LoadGitHubClientSecret` take the value or fall back to the existing file readers with the same per-secret checks.
- **`deploybot-server health`** is `cmd/deploybot-server/health.go`; it is not part of `api` because it must run in the distroless image without config.
