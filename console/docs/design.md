# Console (`console/` in bot-control-plane): design (v2)

**Date:** 2026-10-13. **Status:** Draft, design only.
**Cross-repo design (the source of truth for auth, permissions, and the API):** umbrella `docs/design-bot-agent-deploy.md`. This file covers only what changes inside `console/`.

## Direction

The console stops reading Postgres directly and becomes a BFF client of the API (decision D6). It holds no database login, no OAuth client secret, and no permission logic. It may hide controls the user's role cannot use, but the API decides.

Steps 2 and 3 landed together. The console no longer reads Postgres. Host overview and processes are tabs on `/hosts/[id]`. Catalog & services is a tab on `/projects/[id]` (it replaced separate Services and Catalog tabs on 2026-11-05). Both are fed only by the API. `BOT_API_URL` is required.

## Auth (BFF)

- New routes: `/signin` (Google only for now; GitHub later), `/auth/google/callback`, `/signout`, `/device` (the device-code approval page for MCP clients: sign in, enter the code, approve; umbrella §7), `/oauth/consent` (MCP browser consent: client name marked unverified, full redirect host, Allow or Deny), `/account/apps` (Connected apps, linked from the header account menu, with a revoke action), `/requests` (open requests, also in the account menu; api-v1 v1.33 item 8), and `/invite/[token]` (join a project from an invite link: lookup on load, Join posts accept, then 303 to that project).
- Sign-in: a server route calls the API `GET /v1/auth/google/start`, then redirects. The callback route posts `code` and `state` to `POST /v1/auth/google/callback` and receives the session token once.
- Cookie `bot_session`: `HttpOnly`, `SameSite=Lax`, `Path=/`, `Max-Age=604800`, and `Secure` when the origin is HTTPS (the dev `:5180` is HTTP over the tailnet, so no `Secure` there).
- Public site pages `/about`, `/privacy`, `/terms` and the 404 page `/not-found` (route group `(site)`, own layout; listed in `SITE_PATHS` in `src/lib/server/session.ts`, which a test ties to the route folders): `hooks.server.ts` renders them before reading the cookie, so they never call the API, keep the shared security headers and theme marker, and drop the global `noindex` meta. The root layout renders only the page for `(site)` routes. Their components import only `$lib/site` and `$lib/legal`, so stage 2 can move them to a separate static site. Lucide icons come from `@lucide/svelte/icons/*`, the only package import the public pages allow besides `svelte`. SEO (umbrella `docs/spec-seo-site.md`): on deploybot.dev the homepage is `/`, served with a 200. Caddy's apex block rewrites `/` to `/about` (and `/__data.json` to `/about/__data.json`) on the server and 301s `/about` to `/`. Because the console's `ORIGIN` is the console host, the server never sees the apex hostname, so the client router needs its own mapping: the universal `reroute` hook in `src/hooks.ts` (the pure `homepageRoute(url)`) returns `/about` only for hostname `deploybot.dev` and path `/`, so hydration and client navigation to `/` on the apex draw the About page instead of the app route; on any other host or path it returns undefined. After the reroute the client asks for `/__data.json?x-sveltekit-trailing-slash=1`; Caddy rewrites that to `/about/__data.json`, so the hook sees pathname `/about/` as a data request. For data requests `hooks.server.ts` drops that one trailing slash before the site-path check, so the request is served as the site page with no session (a document request to `/about/` still gets SvelteKit's 308 first, and `isSitePath('/about/')` stays false). Each site page renders its head through `src/lib/site/SiteHead.svelte`: title, meta description, canonical and `og:url` on `SITE_URL` (`https://deploybot.dev`, from `src/lib/site/links.ts`; About's is `/`), `og:type`, `og:site_name`, `og:title`, `og:description`, `og:image` (`/brand/og-image.png`, 1200×630, with alt) and `twitter:card` `summary_large_image`. The canonical stays on the apex on every host, so the copies on the console host are not duplicates. `static/sitemap.xml` lists the three apex URLs (no `lastmod`) and `static/robots.txt` names it; `tests/seo-site.test.ts` covers the reroute, the head tags, the sitemap and robots. Indexing fixes (umbrella `docs/spec-seo-indexing-fixes.md`): the Caddy apex block no longer 302s unknown paths to the console. It 301s an allowlist (`/signin`, `/projects` and their subpaths, which `SIGN_IN_URL` and the manifest's `start_url` rely on) to `https://console.deploybot.dev{uri}`, serves `/manifest.webmanifest`, and rewrites every other path to `/not-found`, so the visitor keeps the URL and gets a real 404. `/not-found` is a site path whose server load throws `error(404)`; `src/routes/(site)/+error.svelte` passes `page.status` to `src/lib/site/SiteError.svelte` and renders inside the site layout ("Page not found" with a link to `/`, title "Page not found · Deploybot", no canonical; other statuses get a generic text and title). Like the other site pages it drops `noindex`; a 404 is not indexed anyway. The console host's Caddy block 301s `/about`, `/privacy` and `/terms` (and their `__data.json`) to the apex pages, and the signed-in footer and the sign-in page link to the apex with `SITE_URL`, since the console host serves no public pages in production. Dev (:5180, no Caddy) still serves them directly. Links inside the site pages stay relative.
- The same pages also exist as the static app `../site/` (Cloudflare Pages, umbrella `docs/spec-site-pages.md`): until the cutover the console serves them, so a content change goes into both copies; the console's copies are removed in the release after the apex moves.
- `hooks.server.ts`: read the cookie, call `GET /v1/me` (cached for each request), and put the user in `event.locals`. Unauthenticated page requests redirect to `/signin`. `/api/*` returns 401. `safeNext` allows `/invite/<token>` only when the token is 43 base64url characters, with no query or extra segment. A signed-out `/invite/` request returns that redirect itself with `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, and `X-Frame-Options: DENY`. `/signin` responses send `Referrer-Policy: no-referrer` and `Cache-Control: no-store`, so `next` is not sent on to Google. A signed-in request to `/signin` is a 303 to `safeNext(next)` (default `/projects`), so the page shows only to signed-out visitors; `safeNext` never returns `/signin`, `/signout` or `/auth/*`, so this cannot loop. Secret inputs (the `/fill` value, env-set secret values, the registry token) never use `type="password"` once hydrated: `$lib/secret-input` makes them `type="text"` drawn as dots by CSS (`-webkit-text-security: disc`), with `autocomplete="off"` and the 1Password, LastPass and Bitwarden ignore attributes, so the browser does not offer to save a Deploybot secret as the user's password; a browser without that CSS, and the server-rendered first paint, keep `type="password"`, so a secret is never drawn in clear. Every response gets `Referrer-Policy: no-referrer` except `/projects/*` and `/connect/*`, which get `same-origin` (`referrerPolicyFor`, v0.2.35): their Connect GitHub forms post natively so the browser follows the redirect to github.com, and under `no-referrer` a native form POST carries `Origin: null`, which SvelteKit's CSRF check refuses in production (vite dev does not check). `same-origin` still sends no Referer to github.com.
- Every server-side call to the API sends `Authorization: Bearer <cookie value>`. Each call also sets `X-Forwarded-For` to `event.getClientAddress()` when that value is an IP, and does not copy `X-Forwarded-For`, `Forwarded`, `X-Real-IP`, or other client-address headers from the caller. The browser never talks to the API.
- Mutating forms send one `idempotency_key` per click. Catalog run, stop, and restart keep the same key from the time the dialog opens until that post succeeds, and ignore a second click while it is in flight. A failed post retries with that key. After success the dialog mints a new key. Logs omit the key. SvelteKit's origin check covers CSRF for form POSTs.

## New pages

- **Projects:** list, create (the creator becomes owner), rename and delete (owner).
- **Project page loading:** each tab fetches only the lists it shows (Hosts: hosts, plus the org's join tokens for an org admin; Catalog & services: hosts, members, the catalog, and the project's Deploybot services (`services?view=deploybot&include=health_checks&limit=200`, following `next_cursor` for at most 5 pages), grouped under their entries once all three have answered; Members: members, invites; Settings: env sets, registries, files), after the project itself. Calls that do not depend on each other run in parallel; only the copy grouping waits for the host list and the catalog. A failed list becomes that section's message. The catalog form asks for env-set names and file names with their own actions when the dialog opens. Those names are not loaded with the catalog tab. The Image field asks for registry tags (`?/catalogImageTags`) and a picked tag's digest (`?/catalogImageDigest`) the same way, through hidden forms (`ImageLookupPost.svelte`) placed after the save form.
- **Members:** list; admins add, remove, and change viewer/admin roles; the owner transfers ownership. Admin+ creates an invite link (viewer or admin, expiry 1, 7, or 30 days, uses 1, 5, or 25). The url is shown once in that dialog and is not put in the page URL, a cookie, or a log. Closing the dialog clears it; opening the dialog again shows the empty form. A url is shown only when its origin is this console's origin and its path is `/invite/<token>`. Pending invites list role, creator, expiry, uses, and status, and revoke with an icon-only Ban action.
- **Organizations (v1.24):** an org owns hosts and contains projects. A host's level in a project list is `access_level` only; `parseHost` no longer reads the `relation` and `share_level` mirrors, which api-v1 v1.26 removed (a host without `access_level` has no level). `/orgs/[id]` has Projects, Hosts, Members, Join tokens and Settings; the header switcher lists the session's orgs. New project asks for an org when the caller administers more than one. New organization (spec-new-org; `NewOrganization.svelte`, the `createOrg` action on `/projects`) is open to every signed-in user, as `POST /v1/orgs` allows any console session: it posts `{name}` (`cleanName`, 1–80), parses the answer with `parseOrg` (a malformed one is a 502) and redirects to `/orgs/<id>?tab=projects`; the layout's `/v1/me` read then lists the new org. Failures use `actionFailure` and stay in the dialog (`ownResult`) with the name kept. It is in the header's Org ▾ menu and on `/projects` next to New project; MCP still cannot create an org.
- **Hosts:** per project: access level, status (online, offline, or asleep for `always_on=false`), last seen, agent version; admin+ leaves a host; org admins revoke a credential.
- **Join host:** org owners and admins see an Add a host guide on the project Hosts tab (token grants that project deploy) and on the org Hosts tab (optional grant). Its first line says to run the commands below on the host being added (for example over `ssh -t`). The guide starts open only when the host list loaded and is empty. A failed host list is a Notice and leaves the guide closed. Creating a join token shows it **once**, in the Create join token dialog (`AddHostSection`, `JoinTokenResult`), with the project access it gives (the project tab's own project at deploy, or the org grant chosen, from the action result), and an enrol command that does not contain the token. The API install command is not shown. The server in the enrol command is taken from that API command (a loopback `ws://` server adds `--insecure-dev`), or the enrol command uses `<your server URL>` when the command is missing or rejected, or when the server value contains the token. An empty Hosts list with no host-list message links an org admin to Add a host and tells everyone else to ask an org admin. The page never shows the token again.
- **Ops (phase 2):** logs for every member, viewers included. Deploy (by container name: adopt if it exists, create otherwise) for admin+. Run, stop, and restart for admin+ on `owned` services. Results come back inline. History reads `GET /v1/projects/{id}/audit`. This replaces the spec-v1 rule that "the dashboard does not drive ops".

## Env

`BOT_API_URL` is required. There is no Postgres URL or password. No OAuth secrets (they live on the API). An unset or invalid `BOT_API_URL` makes every route except static assets return 503.

## Components

Pages render on the server. JavaScript is required for dialogs, the theme switch, and chart refresh. Search, sort, paging, tabs, and filters stay in the URL, and every write is still a SvelteKit form action. Shared pieces live in `src/lib/components/` and are built on the shadcn-svelte primitives in `src/lib/components/ui/` (generated; do not edit them). The exception is `ui/combobox`, written by hand on bits-ui `Combobox` because shadcn-svelte has no free-text combobox: `Root` (`open`, `onPick`), `Input` (bindable free-text `value`, `role="combobox"`, `aria-expanded`, `aria-controls` naming the listbox), `Content` (with an `aria-label` and an optional `footer` outside the listbox, which holds only options) and `Item`. bits-ui highlights the first option on its own; the primitive hides that highlight and its `aria-activedescendant` until the user moves with the arrow or Page keys (the first ArrowDown shows the first option, the first ArrowUp the last), and until then Enter closes the list and submits the form with the text as typed, so a typed reference is never swapped for an option. Home and End move the caret. Colours come only from the tokens in `src/app.css`. Icons are `@lucide/svelte`. `cn()` is in `src/lib/utils.ts`. Command lines, ports, pids, tokens, and enrol commands use the monospace stack. Dialogs mount only while open and use the generated portal. The generated primitives style states with `data-open:`, `data-closed:`, `data-checked:`, `data-unchecked:`, `data-horizontal:` and `data-vertical:`; bits-ui sets `data-state` and `data-orientation` instead, and the `@custom-variant` rules in `shadcn-svelte/tailwind.css` (imported by `src/app.css`) map them. `tests/console-polish.test.ts` fails when a `data-<word>:` variant used in `ui/` has no mapping (bare attributes such as `data-disabled`, `data-highlighted`, `data-placeholder` and `data-inset` need none).

A row with no `health_checks` key (an API older than v1.18) gets no checks and `Health checks need API v1.18 or later.`; a malformed one gets `Health checks could not be read.`; `[]` means no checks. `CatalogSection` builds `CatalogRow`s (`catalogRows`: entry, copies, and `idle` hosts a program never ran on, from `notRunningPairs` over every owned row of this project when the read was complete) and hands them to the client `DataTable`, so sort (`catalog.sort`, `catalog.dir`; default Last deployed, newest first), the Kind filter (`catalog.kind`) and paging (25 entries) apply to entries and an entry's copies are never split across pages. Search (`catalog.q`) matches the name column's search text, which is the entry name plus each copy's host name and label (`copySearchText`), as well as kind and command, so a match shows the entry with all its copies. The host filter (`catalog.host`) is a GET form with a select of reachable hosts (`hostChoices`: `access_level === 'deploy'`) plus All hosts, rendered through `DataTable`'s `toolbar` snippet so it shares one flex-wrap row with the search; `chosenHost` turns the param into a host id or the notice; it submits on change (no Apply button) and keeps the other params except the page and `catalog.logs` (`hostFilterHiddenFields`). With a host chosen, `rowsOnHost` keeps only each entry's copy and idle host there and drops entries with nothing there; the empty line (`catalogEmptyText`) is "Nothing in the catalog runs on this host." only when a host is chosen and no search or Kind filter is active, otherwise "No catalog entries."; a value that is not a reachable host is ignored with the Notice "That host is not available for this project." Entries are collapsed by default (spec §10, last bullet). The entry columns are Name (semibold, with the arrow), Kind, Command, Services (`copySummary`, not sortable), Last deployed and Actions; Run as and Port left the entry row. `copyState` (`src/lib/catalog-copies.ts`, spec §10 status badge rule) gives each service its word; `runtime` null is `loading` (a spinner), `undefined` means no read (no grant), and a runtime `unknown` means the read failed, timed out, was skipped (host not online) or is past the cap. In order: (1) a gone row, or a container that is stopped, exited, created, dead or missing, is Stopped; (2) a restarting container is Unhealthy; (3) a running or paused container is Unhealthy when its health is down and Running otherwise (unknown health does not make it unhealthy: the tooltip then says "No health check" when the row has no health source, or "Health not checked recently" when it has one); (4) when a container's live state was not read (the read failed or timed out, the host is not online, it is past the 100-copy cap, or the caller has no grant on the entry), its health decides: up is Running, down is Unhealthy, unknown is No status (tooltip "Couldn't read the state from the host"); (5) a program (no live read) is Unhealthy when its health is down, otherwise Running while the host reports it, and Stopped when gone. ## Theme

Cookie `bot_theme` is `system` (the default), `light`, or `dark`. Any other value counts as `system` and is never written back raw. `POST /theme` is public. It sets the cookie (`HttpOnly`, `SameSite=Lax`, `Path=/`, max-age one year, `Secure` only when the request is https) and redirects to a safe `next`, or to `/` when `next` is unsafe. The server writes `class="dark"` for dark, nothing for light, and `data-theme="system"` for system. An inline script in `src/app.html` (`nonce="%sveltekit.nonce%"`) adds `.dark` before paint when the choice is system and the OS prefers dark, and it follows later OS changes only while that attribute is still `system`. `ThemeSwitch` sets the class immediately, then posts `/theme` (`name="theme"`, hidden `next`) with `use:enhance` and does not reload the page. At 640 px and below the three choices are icons only, and the switch sits on the next header line. The signed-in row wraps, and a long account name truncates.

## Times

Absolute timestamps, including Last seen and chart axis labels, render in the viewer's time zone. `LocalTime` is the shared piece. The layout load reads cookie `bot_tz` (an IANA name; anything else is ignored) and otherwise uses the server's zone, so the server HTML and the first client render match. After mount, a browser whose zone differs switches the visible times and stores `bot_tz` (`SameSite=Lax`, `Path=/`, max-age one year, `Secure` only on https, not `HttpOnly`). The date shape stays day-month-year with a 24-hour clock. The zone abbreviation on a full timestamp is the viewer's.

The read mark is ignored because it is kept per key: a problem read as heads_up that escalates on the same row, or reopens within 30 minutes, comes back read (`needsAction`, which also needs unread, still drives the red dot and the label). The first read after a page load alerts nothing. Alerted keys are kept in per-tab storage (`deploybot:bell-toasted`, through `visitStorage`), so a reload replays nothing; a key that no longer needs action is dropped (and its cross-tab claim released), because the API reopens a problem that returns within 30 minutes under the same `problem:<id>` key, and that recurrence should alert again. Toasts (`createProblemToaster`) are error style, `important`, dismissible, `duration: Infinity`, with "View" (the problem's page) and "Dismiss"; when the problem toasts already showing plus the new ones exceed 3, one summary "N new problems need action" with "Open the bell" is shown instead, under its own id per read. The View and Dismiss buttons free their toast's place themselves (svelte-sonner removes a toast after an action or cancel click without calling `onDismiss`, which still covers the close button and a swipe). A problem toast's View and a problem notification's click go through the bell's `openKey`, the same path as a bell row: mark that key read (POST `/notifications`), go to its page, read the bell again; a failed mark still navigates and shows the mark error. Dismiss, the summary toast and a summary notification mark nothing. A summary notification opens only a console path (`consolePath`: `//host` or a URL falls back to `/projects`). A 401 on the bell (sign-out or session expiry) stops its reads and clears the tab's alert keys and the desktop choice, so whoever signs in next starts off.
- **Desktop notifications (`$lib/desktop-notify.ts`, `DesktopNotifySwitch.svelte`):** an opt-in checkbox item at the end of the account menu (the vendored indicator shows a check when on, and an "On"/"Off" word shows the state either way), its state read synchronously and bound through `toggleDesktop` (a function binding), so a dismissed or failed permission prompt shows off. `Notification.requestPermission()` is called only from that click. The choice is `deploybot:desktop-notifications` in localStorage (the only localStorage user besides the drawer widths), off when storage fails and removed at sign-out. Denied shows "Blocked in this browser's settings" as a menu item (arrow keys reach it, it is not disabled and reads at full opacity, choosing it keeps the menu open); no `Notification` hides the item.
- **Tabs (`createLiveHub`, `connectHub`, `browserLiveHub`):** one hub per page over `BroadcastChannel('deploybot-live')`. Each tab announces its visibility on load, on every change, every 60 s (`HEARTBEAT_MS`) and again on a `pageshow` from the back-forward cache; a tab silent for 3 minutes (`TAB_EXPIRY_MS`) is forgotten. The hidden tab that became hidden last (ties: the lower id) is elected: with notifications on and every console tab hidden, only it reads the bell, every 60 s (`HIDDEN_BELL_MS`); otherwise hidden tabs make no requests. New problems then become system notifications (`deliverProblems`): title "Deploybot", the problem title as body, its key as tag; more than 3 give one summary under `problems:<hash>`. Each key is claimed once across tabs (`deploybot:live-claimed`): a claim waits 50 ms and yields to a lower tab id that claimed the same key. Keys longer than 200 characters are dropped on receipt and on read. A click focuses the tab, opens the page and closes the notification. Every alert posts its keys as seen; hidden tabs add them to their alerted keys, so a return replays nothing. Claims are bounded to 300 in memory and in storage. Destroying the bell stops the hub's heartbeat, listeners and channel (`disposeBrowserHub`). The tab id falls back to `getRandomValues` or a plain id without `crypto.randomUUID` (insecure origins), and the hub is created inside try/catch, so the bell works without it.

### Referrer policy on client navigation (2026-11-22)

`hooks.server.ts` sends `Referrer-Policy` per path (`$lib/referrer-policy.ts`): `same-origin` on `/projects/<id>` and `/connect/<id>`, whose Connect GitHub forms post natively, and `no-referrer` elsewhere. A header sets only the policy of the document the server sent, and SvelteKit's client navigation keeps it. So a tab first loaded on a `no-referrer` page (`/projects` after sign-in, an org or host page, an invite) that then opened a project's Settings by link posted Connect or Reconnect GitHub with `Origin: null`, and SvelteKit's CSRF check answered "Cross-site POST form submissions are forbidden" until a reload. The root layout now also renders `<meta name="referrer" content=…>` from the same rule; the browser applies a changed referrer meta at once, so the document's policy follows every navigation. Token-bearing pages (`/invite/`, `/fill/`, `/fill-file/`, `/device`, `/oauth/consent`) stay `no-referrer`, and `same-origin` never sends a Referer to another site, so the GitHub redirect still carries none. `csrf.checkOrigin` is unchanged.

### Host config files (api-v1 v1.44, umbrella spec `docs/spec-host-config-files.md` rev 1 §2.8, 2026-11-22)

- **Tab:** `/hosts/[id]?tab=files` ("Config files", FileCog; `HOST_TABS` in `$lib/host-view.ts`). `files.name=<name>` opens one file; `files.v=<n>&files.mode=view|diff` shows one saved version or its diff against the applied one. The load (`loadHostFiles` in `$lib/server/host-files.ts`, dependency `host:files`) reads `GET /v1/orgs/{org}/hosts/{host}/files` with the host's `org_id`; a host without an org reads nothing and shows an info notice. Every member who sees the host gets the list; only org owners and admins (`isOrgAdmin` on the session orgs) read a file: `GET …/files/{name}`, plus `GET …/files/{name}/versions/{v}` for the applied version (the diff base) and for a viewed version, and the console's tracked applies. "Latest" is the higher of the list's `latest_version` and the highest version in the list (`latestVersion`). Pure parts (status and outcome words, the line diff with folded context and a 250k-cell cap, the `managed_url` line, key and value rules, staging, the poll step, the form-result reader) are in `$lib/host-files.ts`. View, Diff, Open and Close links carry `data-sveltekit-noscroll`; after the navigation focus moves to the file or version heading.
- **One editor per file:** the tab renders the file's editor inside `{#key file.name}`, so opening another file mounts a fresh editor and a draft or staged keys never carry over; each editor also posts only for the file it was opened for (`plainSaveAllowed`, `secretSaveBody`).
- **Plain file:** `PlainFileEditor.svelte` (Label and Textarea, live diff against the applied text in `FileDiff.svelte` redrawn 250 ms after typing stops, Save, "Insert Deploybot link"). Save posts `saveFile` → `PUT …/files/{name} {content}`; the browser submits a textarea's line breaks as CRLF, so the action turns CRLF back into LF before sending (a CR cannot survive a textarea anyway), and refuses an empty text, more than 65536 bytes or a NUL. A failed Save returns the typed text (`content`) and reads the page again (`invalidateAll`); a newer saved version replaces the editor text only when it has no unsaved changes, otherwise a note says the file changed and the text stays. `beforeNavigate` stops one link away from unsaved text with a note (the next one leaves; `confirm()` is not used in routes) and gives a page unload the browser's prompt; links within the same file and the page's own Save do not count. "Insert Deploybot link" adds `managed_url = "<origin>/hosts/<id>?tab=files&files.name=<name>"` before the first real `[name]` or `[[name]]` header line (so it stays a top-level TOML key; an array line such as `[1, 2],` is not a header), or at the end; it is disabled with a visible note once the text has a `managed_url` line, and nothing else touches the text.
- **Secret file:** `SecretFileEditor.svelte`: a key table (set or unset, never a value, plus the staged change), Set value per key and Add key (`SecretKeyDialog.svelte`, a masked input from `$lib/secret-input.ts` with no bound value; the dialog posts nothing), Remove (blocked on the last key) and Undo. Staged changes live in the component's memory (leaving with staged changes asks first, by the same rule as the plain editor, `unsavedLeave`), are listed ("KEY will be set", "KEY will be removed"), and Save posts `saveSecretFile` with one `changes` field added in `use:enhance` → one `PUT {base_version, set, remove}` (`parseSecretChanges` checks it again on the server); Discard drops them. `base_version` is the latest version (0 when none). Neither a load nor an action result carries a value (a failure returns only `filesMessage` and `filesField: 'secret'`), and the detail parser keeps only key names and drops any hash. A failed Save keeps the staged changes and reads the file again; a 409 says the file changed and Save puts them on top of the new version.
- **Apply:** `applyFile` → `POST …/files/{name}/apply {version, force?}` with `HOST_FILE_APPLY_WAIT_MS` (620 s: the API waits up to 610 s, the agent task's 600 s plus 10 (spec amendment A4), plus a margin) on Node's default fetch dispatcher. The action races that call against `hostFileApplyTimings.fastWaitMs` (25 s; Cloudflare cuts a request at about 100 s): an apply that ends in time answers as before; otherwise the call carries on in the process, tracked in a Map keyed `org:host:name` (started time, then the outcome, kept 10 minutes after it ends); the action first requires the caller to be an owner or admin of the posted org (`isOrgAdmin`, else 403 with no API call), and the load and the poll route list only that org's runs, to its owners and admins, and the action answers `{hostFileRunning}`. A second Apply of the same file while one runs starts nothing. If the detached call fails after the action answered (undici's 300 s `headersTimeout` or body timeout, apiFetch's own timeout, a network error), the run stays without an outcome and is marked `unknown`: the apply may still be running, and the API records it in the file's last apply. An unknown run does not block a new Apply (the API answers `conflict` if one still runs). The tab then polls the console route `GET /hosts/<id>/file-applies?org=<org>` (org owners and admins; no API call) every 3 s while visible; `stepWatches` settles a watch when its run has an outcome, or, when the run is gone (console restart) or unknown, when the list's last apply changes or is newer than the watch's start, giving up after 12 minutes. The load lists the tracked runs, so a reload keeps the progress note and Apply blocked. After an outcome the tab reads `host:files` again at once and once more 5 s later. Progress and outcome share one `aria-live` region; Apply buttons stay focusable (`aria-disabled`, a RowAction `blockedReason`) and a click while one runs is cancelled. The outcome shows the host's stage and reason tokens in monospace (`applyOutcomeMessage`; stages `lookup`, `settle`, `exec`, `target`, `check`, `idle`, `restart`, `health`, `rollback`); a `forbidden_spec` at stage `exec` (spec amendment A2: a check, health or idle program on the host failed its safety check) says "A program this file's check runs is not safe to run (see runner.toml); fix its permissions on the host.", any other `forbidden_spec` "The host refused this file under its policy (runner.toml).". A 409 `worker_busy` says "The program on this host is running a job. Applying now interrupts it." and shows "Apply anyway" outside the live region, behind a ConfirmAction that posts `force=1`; the same progress note shows while that confirmed post runs (`ConfirmAction` `onSubmitting`). Applies are serialized per host and unit (spec amendment A1): two files that restart the same unit cannot apply at once, and the 409 `conflict` text names the file already running; the tab shows it as the error. Other API errors (`host_offline`, `unsupported_agent`, `timeout`) show their message, and the page is read again. The console sends no `settle_sec`, so the default follows the host's health wait: 60 s, or the health command's `--wait` plus 15 s when that is longer.
- **On host status:** the agent's reasons map to the list's words: `missing` → missing; `symlink`, `not_regular`, `owner`, `mode`, `nlink`, `dir` → wrong owner; `too_large`, `io_error` → unknown.
- **Bell:** problem kind `host_file` (org owners and admins): `problemKindOf` reads a `/hosts/` href with `tab=files` as `host_file` before the `host_offline` rule; the row icon is FileWarning. Problem alerts and desktop notifications handle it like every other problem.
- **Bell:** problem kind `agent_upgrade` (api-v1 v1.48 item 6, org owners and admins): `problemKindOf` reads a `/hosts/` href ending `#agent-upgrade` as `agent_upgrade` before the `host_offline` rule; the row icon is CircleArrowUp.

### Host resource alerts (api-v1 v1.49, umbrella spec `docs/spec-host-resource-alerts.md` rev 1 §6, 2026-11-23)

- **Alerts card:** `HostAlertsSection.svelte`, under Edge on every host tab, for anyone who sees the host (`loadAlertSettings` in `$lib/server/host-alerts.ts`, read alongside the tab). Org owners and admins of a live host (`canEditAlerts`) get a Switch labelled "Alerts" (`alerts_enabled`; its state is the switch itself), three number fields with "Default (n)" placeholders, each with its help line tied by `aria-describedby`, and Save (`saveAlerts` → `PUT /v1/hosts/{id}/alert-settings`, then a 303 back and the toast "Saved alerts." from `$lib/success-toast.ts`); an empty field is the default (null). The memory help says the default also alerts under 96 MiB while a set value uses the percent alone. The switch starts from the stored value and follows it only when that value changes, so the 30 s Overview refresh keeps an unsaved switch. A refusal (the form check or the API's text) shows as the card's Notice, tied to the form and marking the field it names `aria-invalid`. `$lib/host-alerts.ts` holds the fields, ranges, `alertFieldValid`, `alertFieldMessage` and `alertSettingsFromForm`; `parseAlertSettings` reuses the same ranges. Others see the values read-only.
- **Memory chart:** the load asks for `used_percent`, `available` and `total` and draws Used (amber, `--chart-3`) and "Free to use" (green, `--chart-5`), the latter `available / total × 100` per bucket (`withAvailablePercent` in `$lib/host-view.ts`). The second line is labelled "Free to use", not "Available", and drawn green, so a high value never reads as high usage (Joe, 2026-11-24).
- **Disk chart:** Overview reads `GET /v1/hosts/{id}/disks`; with more than one mount a "Disk" link strip picks one (`?disk=<path>`, `parseDiskPath`: empty, longer than 1024 or with control characters is `/`), the chart title names it and the range links keep it (`overviewHref`). Without `?disk=`, a host with exactly one mount charts that mount; only the disk chart waits for the mount list. The metrics call adds `path` when it is not `/`.
- **Disk usage card (api-v1 v1.59):** `DiskUsageCard.svelte`, on Overview after the Snapshot card, for everyone who sees the host: a DataTable of the `/disks` mounts (Mount, Used, Size, %, and As of, the sample's `LocalTime`, hidden below `sm`), highest % first (`mountsByUse` in `src/lib/disk-usage.ts`), "No disk data" when empty; `parseHostDisks` keeps `total`, `used`, `used_percent` and `at` (null when missing or unusable). Org owners and admins of the host's org also get "Check Docker usage", the named action `dockerUsage` (`checkDockerUsage` in `src/lib/server/disk-usage.ts`), which posts `POST /v1/hosts/{id}/docker-usage` with a 55 s wait (`DOCKER_USAGE_WAIT_MS`); the button reads "Checking Docker usage…" while it runs. A revoked host gets no button; a host that is not online gets it disabled, with the tooltip and screen-reader text "This host is offline; Docker usage needs it online.", which is also what an API `host_offline` answer shows. `parseHostDisks` keeps up to 200 mounts, the API's own cap. The answer (`parseDockerUsage`, field by field, lists of at most 10, strings of at most 200) shows a one-line total, the four totals (Images, Containers, Volumes, Build cache: count, size, reclaimable), the largest images, volumes and containers, and the reclaim note. An API refusal's sentence shows in the card as a `Notice`. Sizes use `formatDecimalBytes` (1000-based, as `docker system df` prints them; Joe 2026-11-24); the rest of the console keeps the 1024-based `formatBytes`.
- **Bell:** problem kind `host_resource`: `problemKindOf` reads a `/hosts/` href with `range=` (memory, cpu, load, and disk with `&disk=`) as `host_resource`; the row icon is Cpu. Memory and disk are `needs_action` and pop up like other problems; cpu and load are `heads_up` and stay in the bell.
