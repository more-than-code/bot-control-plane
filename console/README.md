# Console (`console/`)

The console part of [bot-control-plane](../README.md) (formerly the bot-console repo; the package and release bundle keep the name `bot-console`). SvelteKit console for Deploybot. It is a BFF in front of the API (`../api`): the browser never calls the API, and this app has no database login. Sign in with Google, then open a project and a host. A project has a Catalog & services tab: each catalog entry with its running copies nested under it. A host has Overview, Processes and Config files tabs.

JavaScript is required. Search, sort, paging, tabs, and filters stay in the URL. Writes are SvelteKit form actions. Brand files (favicons, apple-touch and manifest icons, header lockups) are copied from the umbrella `docs/brand/logo/` into `static/brand/`; `static/manifest.webmanifest` lists the app icons. The UI is Tailwind CSS v4 and shadcn-svelte (style `nova`, neutral base, Lucide icons). `cn()` lives in `src/lib/utils.ts`. Colours are the tokens in `src/app.css` (light on `:root`, dark on `.dark`), including the Deploybot status tokens. The header theme switch posts to `/theme` and stores `bot_theme` (`system`, `light`, or `dark`; default `system`).

## Setup

Requires Node.js 22+ and pnpm:

```bash
pnpm install
```

Copy `.env.example` to `.env`. The app reads these variables on the server only (`$env/dynamic/private`):

| Key | Purpose |
|-----|---------|
| `BOT_API_URL` | Required API origin, no path. Unset or invalid → 503 `Console is not configured (BOT_API_URL)` |
| `BOT_API_ALLOW_INSECURE_HTTP` | Set to `1` to allow a non-loopback `http://` API URL (development/internal testing only) |
| `BOT_API_OAUTH_AUTHORIZE_HOSTS` | Comma-separated `authorize_url` hostnames. Default `accounts.google.com` |

`https` is accepted. `http` is accepted only for `localhost`, `127.0.0.1`, and `::1`, unless `BOT_API_ALLOW_INSECURE_HTTP=1`.

Do not commit `.env`. `.env` is gitignored.

`vite dev` and `vite preview` load `.env` themselves. `node build` does not, so export the variables or run with the working directory set to this `console/` folder. A systemd `EnvironmentFile=` is the better production source.

## Scripts

| Script | What it does |
|--------|----------------|
| `pnpm dev` | Dev server on `0.0.0.0:5180` (`strictPort`) |
| `pnpm build` | Production build into `build/` |
| `pnpm preview` | Preview the build on `0.0.0.0:5180` |
| `pnpm check` | `svelte-check` |
| `pnpm test` | Unit tests (`node --test`). They mock `fetch`. There is no API server in the tests. |

Production, behind the reverse proxy:

```bash
PORT=5180 HOST=127.0.0.1 ADDRESS_HEADER=X-Forwarded-For XFF_DEPTH=1 node build
```

`PORT` defaults to 3000 and `HOST` to `0.0.0.0` in the Node adapter. Bind to loopback (`HOST=127.0.0.1`) when a reverse proxy is the only client. `ADDRESS_HEADER=X-Forwarded-For` and `XFF_DEPTH=1` make `event.getClientAddress()` the rightmost forwarded address, the one the closest proxy added. The console sets that address as `X-Forwarded-For` on every API call. The API rate-limits Google sign-in start (20 per minute), invite redemption, and OAuth by client IP, and it uses the rightmost `X-Forwarded-For` address only when the TCP peer is `BOT_API_TRUSTED_PROXY` (`127.0.0.1` in production). Without the header, every console user shares that loopback bucket. A client who can reach the console directly can spoof `X-Forwarded-For`, which is why the process listens on loopback. `vite dev` ignores these two variables and uses the socket peer. If `getClientAddress()` throws, or returns an empty or non-IP value, the console sends no `X-Forwarded-For`.

In development, run `pnpm dev` on port 5180 against a running API (`go run ./cmd/deploybot-server api` from the repository root, e.g. `BOT_API_URL=http://127.0.0.1:8090`).

## Pages

Success confirmations for an image save, a health-check save and Add member show as a toast at the bottom of the window (the shadcn-svelte Toaster, bottom-center, app pages only); errors stay inline.

Problem alerts (umbrella `docs/spec-console-live-updates.md` §0; details in `docs/design.md`, "Problem alerts and desktop notifications"):

- A problem that newly needs action gets one toast from the same toaster: its title, "View" and "Dismiss"; it stays until dismissed. None on the first bell read after a page load, none for a key already alerted in the tab (so a reload replays nothing), and a problem that stops needing action is forgotten, so a recurrence alerts again. More than 3 at once give one "N new problems need action" with "Open the bell".
- Desktop notifications (account menu, off by default; the browser asks permission only when you turn it on; "Blocked in this browser's settings" when it was denied): while every console tab is hidden, a new problem is one system notification across tabs instead of a toast; clicking it focuses the tab and opens the problem's page. Only then does one hidden tab read the bell, every 60 s. Signing out, or a session that expired, turns it off and forgets the tab's alert keys.

## Auth

`BOT_API_URL` is required. Every page except `/about`, `/privacy`, `/terms`, `/not-found`, `/signin`, `/theme`, `/auth/google/callback`, and static assets needs a session. The signed-in app shell has a footer with Privacy and Terms links to the apex pages (`https://deploybot.dev/privacy`, `/terms`). A page without a session redirects to `/signin?next=<path>`, and `next` has to be a same-origin relative path.

Sign-in is one "Sign in with Google" button. The server asks the API for the Google URL, stores the OAuth `state` and `next` in a short-lived HttpOnly cookie, and sends the browser to `authorize_url`. That redirect happens only when the URL is `https` and its parsed hostname is in `BOT_API_OAUTH_AUTHORIZE_HOSTS`. The callback checks `state`, posts the code to `/v1/auth/google/callback`, and stores the API token in the `bot_session` cookie. That cookie is HttpOnly, SameSite=Lax, Path=/, Max-Age 604800, and `Secure` only when the console request itself is https. The browser does not receive the session token in a response body.

`/signout` asks the API to delete the session and always clears the cookie. Mutations are form posts to this app. The server calls the API.

A join token is shown once, on the create result, and is not written to browser storage. The API install command is not shown. The page shows `sudo ./install.sh enroll --server '<server>' --runner` instead, with `<server>` taken from that command (plus `--insecure-dev` when that server is `ws://` on `127.0.0.1` or `localhost`, the only `ws://` the agent accepts), and tells the admin to paste the join token at the hidden prompt. The token is not in the command or its copy button. If the command is missing, not the expected form, or its server value contains the token, the page says `Server URL not shown: unexpected format` and the enrol command uses `<your server URL>`. An invite link is the same kind of one-time secret: admin+ creates it on the Members tab, the dialog shows the url once, and closing the dialog clears it. The url is shown only when its origin is this console and its path is `/invite/<token>`. The pending list never includes the token. Opening the link does not join; Join is a POST. `/signin` responses send `Cache-Control: no-store` and `Referrer-Policy: no-referrer`. Buttons follow the caller's project role. The API still enforces that role. `forbidden` and `not_found` are messages on the page. Lists that stop at the page or item cap, or that see a repeated cursor, say `More items not shown`.

The header (spec `docs/spec-header-org-project-bell.md`, api-v1 v1.37) reads `logo / Org ▾ / Project ▾ ……… bell  theme  avatar`. The lockup (light or dark to match the theme) links to `/projects`. **Org ▾** (trigger "Organization: <name>") names the open project's org, the open org page's or host page's org, or elsewhere your first org by name; its menu lists your orgs (a check on the current one; owners and admins open `/orgs/<id>`, members `/orgs/<id>?tab=projects`), then "New organization" (any signed-in user may create one; it is offered wherever the Org menu or the phone org items render, and always on `/projects`; the New organization dialog, posting to `/projects?/createOrg`; it lands on the new org's Projects tab), then "Organization settings" (owners and admins, `?tab=settings`) or "Organization" (members), then "All projects". **Project ▾** (trigger "Project: <name>") names the open project, "Select a project" on an org or other page, "All projects" on `/projects`; its menu lists your projects in that org by name with a check on the current one, then "New project" for org owners and admins (the New project dialog, posting to `/projects?/create` in that org). A project-only member sees the org's name as plain text (from `/v1/me` `org_name`); an API without `org_name` shows the project part only. Below `sm` only Project ▾ shows, and its menu starts with the org name and the org items. All menus are the vendored `dropdown-menu`; the header reads the session's `/v1/me` orgs and projects, no extra API call. The org and project pages have no breadcrumbs (the host page keeps its own). The **bell** (lucide `Bell`, named "Notifications, N unread" or "Notifications", an accent dot while anything is unread) opens a `popover`: "Notifications" and "Mark all read", rows newest first (unread dot, Sparkles for a release or ServerCog for a host update, title, detail and age; read rows muted), and "See all changes" to `/whats-new`. Opening marks nothing; a row click marks that row read and opens it; "Mark all read" marks every row. The bell reads the console route `/notifications` after the page loads and whenever it opens (GET proxies `GET /v1/me/notifications`, POST `{keys}` or `{all:true}` proxies `POST /v1/me/notifications/read`; signed in, same origin, JSON, `no-store`; a signed-out caller gets a JSON `401`, never the sign-in redirect, from `hooks.server.ts`). A failed read shows "Notifications could not be loaded." above the last list that loaded (no dot when none loaded); an older answer than the latest request is ignored. "Mark all read" is disabled while it runs and when nothing is unread; a failed mark shows "Could not mark as read." (a row click still opens its page). The old `bot_seen_version` cookie is imported once on a page load: every release item (the newest five releases) at or below that version is marked read, so an upgrade does not resurface releases already seen; the write is bounded at 2 s and a failed or slow one keeps the cookie for the next load. Since api-v1 v1.41 (spec `docs/spec-bell-problems.md`) the bell also shows **problems**: a host offline (lucide `ServerOff`, links to the host page), a refused registry login (`KeyRound`, links to Settings › Registries) and a failed or rolled-back deploy (`RotateCcw`, links to the entry in Catalog & services). Open problems come first and are never cut; a problem row shows its detail and its age ("open 25 min", "resolved 3 h ago"), and a resolved one is read and muted. The dot is red (`destructive` token) while an unread open problem needs action, else the accent dot, and the bell is named "Notifications, N unread, M need action" (the last part only when M is above 0). The bell reads again every 2 minutes while the tab is visible and the popover is closed, so the list does not change while you read it (the timer stops when the header unmounts). A problem that comes back within 30 minutes reopens the same row, so if you had read it, it stays read. The proxy accepts kind `problem` only with a `level` (`needs_action` | `heads_up`) and a `state` (`open` | `resolved`), treats a resolved one as read, and keeps up to 200 items so open problems are never dropped. Then the theme switch (System, Light, Dark), and, when signed in, the user's Google avatar left of their name (only an `https` URL is used, loaded with no referrer; without one, or if it fails to load, a circle with the name's first letter), a menu linking to Connected apps, Open requests and What's new (with the version, no dot), and Sign out.

This console has not been run against the API or Google from the unit tests. They mock `fetch`.
