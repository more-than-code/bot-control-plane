# MCP gateway (`mcp/`)

The MCP part of [bot-control-plane](../README.md) (formerly the bot-mcp-server repo), started as `deploybot-server mcp` (or as `bot-mcp-server`). Stateless MCP gateway (Streamable HTTP at `/mcp`) for external AI agents. Every tool call is forwarded to the API (`../api`) with a short-lived token exchanged from the caller's user token, so permissions are exactly the console's. It also contains `deploybot login`, a device-code login CLI (`cli/`, built from `../cmd/deploybot`).

- Design: `docs/design.md`.
- Contract (frozen): `../docs/contracts/api-v1.md`.

The server stores nothing and writes no files. The CLI writes only `~/.config/deploybot/token` (directory `0700`, file `0600`, atomic replace). The file is JSON, `{"api":"<base URL>","token":"<token>"}`.

## Run

```bash
export BOT_MCP_LISTEN=127.0.0.1:8091
export BOT_MCP_API_URL=https://<api>
export BOT_MCP_PUBLIC_ORIGIN=https://<mcp>
export BOT_MCP_CLIENT_SECRET_FILE=/path/to/client-secret
go run ./cmd/deploybot-server mcp   # from the repository root
```

`BOT_MCP_CLIENT_SECRET_FILE` is mode `0600`. The server reads the first line and refuses to start if the file is missing, empty, shorter than 32 characters, or not mode `0600`. That line is the secret for client id `bot-mcp-server`. It only allows exchanging a user token. It is never logged and never sent to `/v1/*`.

`GET /health` is unauthenticated. `GET /.well-known/oauth-protected-resource` gives the resource `<BOT_MCP_PUBLIC_ORIGIN>/mcp` (the URL clients connect to; the API's `BOT_API_MCP_RESOURCE` must equal it), names the API origin as the authorization server, and lists scope `deploybot`. `POST /mcp` requires `Authorization: Bearer <token>`. The server exchanges that token and calls the API with the delegated token only.

`POST /mcp` checks `Host` before that exchange. The header must be the host of `BOT_MCP_PUBLIC_ORIGIN`, compared case-insensitively: the bare name, or with the scheme's default port (`443` for https, `80` for http). An origin that names a non-default port matches that port only; an explicit default port counts as none. `localhost`, `127.0.0.1`, and `[::1]` are also allowed, with or without a port. Any other value, including an empty `Host`, is HTTP 403 with the body `forbidden: invalid Host header`. The response and the refusal log do not include the header.

Each `/mcp` request writes one `request` log line (2026-10-27): `method` (`GET`, `POST`, `DELETE`, `HEAD`, `OPTIONS`, else `other`), `status`, `ms`; for a POST whose body the server read in full (up to 64 KiB), the JSON-RPC `rpc` method (up to four slash-separated words of letters and underscores such as `tools/call` or `subscriptions/listen`; `response` for a client reply, `batch`, or `other`) and, for `tools/call`, `tool` (a lowercase tool name, else `other`); `client_closed=true` when the client went away before the handler finished; `aborted=true` if the handler panicked. A request refused by the Host or token check is logged with its status and no `rpc`, because its body is not read. It never logs headers, tokens, request ids or arguments. `/health` and the metadata route are not logged.

`BOT_MCP_API_URL` is an origin (`https://host[:port]`, optional trailing slash). A path, query, or fragment is refused at startup. `BOT_MCP_API_URL` and `BOT_MCP_PUBLIC_ORIGIN` must be `https`. Cleartext `http` is allowed only for `localhost`, `127.0.0.1`, and `::1`, or when `BOT_MCP_ALLOW_INSECURE_HTTP=1` (development/internal testing only). The API client does not follow redirects.

Phase 1 tools are read-only: `list_orgs`, `list_projects`, `list_hosts`, `list_services`, `query_metrics`, `list_processes`, `service_health_history`, `host_snapshot`, `probe_service`. `host_snapshot` and `probe_service` contact the host when they are called.

Catalog tools call api-v1 v1.6. `list_catalog` reads a project's catalog and does not contact a host. It returns each entry's name, kind, `command_display`, `last_deployed_at`, and `my_actions`, and does not return the program spec or its environment. `last_deployed_at` (api-v1 v1.21) is the API's RFC3339 time of the newest image deploy or allowed program run started from the console or MCP, or null; it is null when the API does not send it (an older API) or sends something that is not an RFC3339 time, and the call does not fail. It is read-only: the catalog write tools do not accept it, and their `confirm` result does not include it. `entry_logs` and `entry_status` contact the host when they are called; logs and status do not need confirmation. Log lines, including any `lines` on a confirm or status result, are redacted (URL userinfo, then keywords), each line capped at 2048 bytes, and the lines together capped at 64 KiB. A `lines` value that is not an array of strings is not returned raw. They are also cut at 200 items. `run_entry`, `stop_entry`, and `restart_entry` are real, audited actions. With the delegated token the API does not act on those calls: it answers 202 with a plan and a `confirmation_id`. Any other status, including 200, is a tool error and is not shown as a program status. The tool shows that plan and the id, and says nothing ran yet. In the structured result, every confirmation string has control characters replaced, and `plan` is capped at 1024 runes. After the user agrees, `confirm` posts `{"idempotency_key"}` to `/v1/confirmations/{confirmation_id}` and returns the program status. Right after a run or restart, the program's ports and `started_at` can still be empty; they appear in `entry_status` after the host's next status report, and the `confirm` description says so. That second call is what runs, stops, or restarts the program. Arguments are checked before any API call (catalog name, UUIDs, idempotency key, `lines` 1–1000).

Catalog image entries (api-v1 v1.8) use the same confirmation. `list_catalog` adds, for an image, the image reference, service or job, ports, volume short names, managed file names, env key names, env set names, `healthcheck` true or false (not the command), `logging` (`max_size_mb` and `max_files`, or null), and `networks` (shared network names, `null` when unset). It does not return env values, the command, the entrypoint, volume targets, or file targets and contents. There are no file tools. `deploy_entry` (`project_id`, `entry`, `host_id`, `idempotency_key`, optional `force`) and `rollback_entry` (those, plus `digest`) need the deploy permission, and the host must run containers. The entry's project needs `deploy` access to the host (api-v1 v1.24); otherwise the call is `forbidden`. `digest` is `sha256:` and 64 lowercase hex digits. The first call does not act. `confirm` does, and for an image it returns the outcome, a short digest, the exit code, and the last log lines. The 202 text of `deploy_entry` and `rollback_entry` ends with `When you confirm, pass project_id and entry as well.` Pass them on that `confirm` (they are not sent to the API). An image confirm, and a confirm without `project_id` and `entry`, waits at most 50s. If the deploy or rollback is still going, the result is `still running on the host`, the action keeps running on the host, and `entry_status` shows the outcome. `confirm` must use the same `idempotency_key` as the `deploy_entry`, `rollback_entry`, `set_health_checks`, `create_catalog_entry`, `update_catalog_entry`, `delete_catalog_entry`, run, stop or restart call that returned the confirmation; another key is `conflict` (`idempotency_key does not match the request that issued this confirmation`) and nothing runs. A program confirm with `project_id` and `entry`, and `deploy_entry` / `rollback_entry` themselves, keep the 35s deadline. `list_catalog` returns only allowlisted fields; a catalog body that is not an object with an `items` array is an error and is not shown. `deploy_entry`'s plan includes the last 3 deploys (full digest in the structured result, short digest in the text, outcome, and time). With `force: true` the structured result has `force: true` and the plan says so. The 202 result keeps only the confirmation id, plan, expiry, history, and that flag. An image deploy result keeps the outcome, digest, exit code, status, and redacted lines. A timed-out deploy or rollback has `status.state` `unknown`, and the confirm text says unknown. `entry_status` shows unknown the same way. A state other than `running`, `exited`, `created`, `paused`, `restarting`, `dead`, `missing`, or `unknown` is not shown. `entry_status`, and a confirm body that is only a status, then return `error: status response was not usable` and do not return the body. On a deploy result the outcome stays and `status` is omitted. `command_display` and the image reference are redacted when they contain URL userinfo. There is no container remove tool. `list_catalog` returns no env values. `entry_logs` and `entry_status` also render an image container.

`set_health_checks` (`service_id`, `checks`, `idempotency_key`) replaces every health check on a service. Nothing changes until `confirm`, after the user agrees. Checks connect only to 127.0.0.1 on the host. Read the current checks with `get_health_checks` first. The set replaces all checks. The call is `PUT /v1/services/{id}/health-checks` with `{"checks","idempotency_key"}`. `confirm` must use that same `idempotency_key`; another key is refused and nothing changes. `expect_status_min` and `expect_status_max`, when set, must be 200–399. The plan is shown in full up to 10886 runes. A longer plan is an error and is not shortened. `confirm` reports how many health checks were set.

`create_env_set` (`project_id`, `name`, `keys`, `idempotency_key`; api-v1 v1.27 item 4) creates an env set from key names: each key is generated by the API (`generate` kind `password`, `hex` or `base64url`, always secret), a placeholder the user fills in the console (secret unless `is_secret` is false), or, since api-v1 v1.32 item 2, a plain key with its `value` (only with `is_secret` false and no `generate`; else `bad_request: a value can be given only for a plain key`, checked before the API). The value description says never to put a secret there: a secret is a generated key or a placeholder, and a plain template refers to it with `${KEY}`. No secret value is sent, and no value is returned: the plan and the result name keys only. When the API's plan warns that a plain key looks like a secret, the description tells the agent to tell the person before confirming. It returns a plan; nothing changes until `confirm`, which returns the set's key names and flags. `list_env_sets` (`project_id`, optional `name`; item 5) returns each set's key names with `is_secret`, `needs_value` and `reveal_pending`, never a value or preview. A deploy or program run that uses a key with `needs_value` is refused until it is filled in the console; that refusal, and the `${KEY}` reference refusals, reach the tool result as the API wrote them (they name keys, never values). Neither tool contacts a host.

`create_catalog_entry` (`project_id`, `name`, `spec`, `idempotency_key`), `update_catalog_entry` (the same arguments), and `delete_catalog_entry` (`project_id`, `name`, `idempotency_key`) write an image catalog entry (api-v1 v1.12). Nothing changes until `confirm`, after the user agrees. The calls are `POST /v1/projects/{id}/catalog` with `{"name","kind":"image","spec","idempotency_key"}`, `PUT /v1/projects/{id}/catalog/{name}` with `{"kind":"image","spec","idempotency_key"}`, and `DELETE` that path with `{"idempotency_key"}`. Their descriptions start with "Image entries only": program entries are created, edited and deleted in the console. Secret env values belong in env sets entered in the console, not in `spec.env`. These calls do not contact the host. `confirm` of that plan does not contact the host either. It returns the entry name and image reference, with the same fields `list_catalog` keeps, and it does not return env values, secret_env values, or file contents. A delete confirm says the entry was deleted. Running containers are not stopped. `confirm` must use the same `idempotency_key`. Read the entry with `list_catalog` before replacing it. The plan text is the API sentence with control characters replaced. It is not keyword-redacted, so inline env values and `secret_env` sources stay as the API wrote them. The plan is shown in full up to 4278903 runes. A longer plan is `error: plan too long to show`, and the confirmation id is not returned.

Docker health (api-v1 v1.11) is one health source. `list_services` and `get_health_checks` keep `health.source` (`docker`, `check`, or null) and a null `latency_ms`. The text says Docker health when `source` is `docker`. `service_health_history` keeps a Docker row (`protocol` `docker`, null `check_id`, `port`, `http_status`, and `latency_ms`, result `success` or `unhealthy`). `spec.healthcheck` on `create_catalog_entry` and `update_catalog_entry` takes `test` (required) and optional `interval_sec`, `timeout_sec`, `retries`, and `start_period_sec`. `test` is the command and its arguments (for example `["redis-cli","ping"]`); Deploybot adds Docker's `CMD`, so a first item of exactly `CMD`, `CMD-SHELL` or `NONE` is refused locally (api-v1 v1.18); for a shell use `["sh","-c","…"]`. The API checks the remaining rules and fills defaults. `update_catalog_entry` is for an owner or admin. A catalog-write plan stays the sentence the API wrote. `entry_logs` still keyword-redacts the API lines, so a secret preview (`abcd…` or `••••`) is unchanged. Container logs default to 10 MB × 3 files on Deploybot; `spec.logging` on `create_catalog_entry` and `update_catalog_entry` sets `max_size_mb` (1–100) and `max_files` (1–10), and `list_catalog` returns that object or null. `spec.health_policy` (api-v1 v1.15, services only) on `create_catalog_entry` and `update_catalog_entry` takes optional `on_deploy_failure` (`rollback` default, `stop`, `keep`), `on_unhealthy` (`none` default, `restart`, `rollback`; needs `spec.healthcheck`), `unhealthy_after_sec` (15–600, default 45) and `max_actions_per_hour` (1–10, default 3); a job, a missing healthcheck, or `on_unhealthy` combined with `on_deploy_failure` `keep` is refused locally. `list_catalog` returns `health_policy` for a service (the stored values with defaults filled in) and null for a job. Deploy history rows can have outcome `auto_restarted`, `auto_rolled_back` or `auto_gave_up` from the agent (no user); the short deploy history (`deploy_entry` plan) lists non-automatic rows only.

`get_health_checks` (`service_id`) reads `GET /v1/services/{id}`. It returns `health_checks` (id, protocol, port, path, interval, expect bounds, enabled), plus `name`, `ports`, and `health`. Other fields are dropped. It does not contact the host.

Organizations (api-v1 v1.24) own hosts and contain projects. `list_orgs` reads `/v1/me` and returns only its `orgs` (id, name, slug, the caller's role). An API older than v1.24 sends no `orgs`, and the summary says `0 orgs: this API predates organizations`; a body that is not an object or whose `orgs` is not an array of objects is `error: status response was not usable` and is not returned. `list_projects` returns each project's `org_id` and `via` (`org` when the caller reaches it only as an org owner or admin, with role `admin`) and names the org in its summary: `lab (admin via org) in More Than Code`. `list_hosts` takes exactly one of `project_id` or `org_id`. With `project_id` it lists the hosts the project may use, each with `access_level` (`metrics` or `deploy`), summarized as `srv-01 online (deploy)`. The deprecated `relation` and `share_level` were removed in api-v1 v1.26 and the summary no longer reads them. With `org_id` (org owners and admins) it calls `GET /v1/orgs/{id}/hosts`. The API does not send each host's `access` list to delegated sessions (api-v1 v1.24 item 1), so the summary is `srv-01 online`; per-host project access is in the console. There is no tool that writes orgs, members, join tokens or host access; those are console-only, and the API refuses delegated sessions on them. `list_services` takes `host_id` or `project_id`; with `project_id` the query (`q`, `sort`, `dir`, `limit`, `cursor`, `view`) is passed through and the result is paged and limited to what that project may see. `view` is `all` (default when omitted), `deploybot`, or `deploybot_and_discovered`. A service's `gone_at`, when set, means the host no longer reports it. `list_processes` shows the whole host.

Shared networks (api-v1 v1.25). `create_catalog_entry` and `update_catalog_entry` accept `spec.networks`: 1–4 unique names matching `^[a-z0-9][a-z0-9-]{0,31}$`, or null; an empty array, a bad name, a duplicate or more than 4 is refused before the API is called (leave the field out for none). The API stores `[]` and null as absent. `list_catalog` returns `networks` for every image, `null` when unset (api-v1 v1.25 amendment A4), so a listed entry can be written back as it is. The `list_hosts` summary adds the shared networks the API returned for the caller, as `srv-01 online (deploy) (shared networks: dd 10.200.10.0/24)`; for a delegated session the API sends only the networks open to the project in view, with name and subnet and no member list, and an empty list on `org_id`. A deploy or rollback of an entry with `networks` to a host whose agent predates 0.2.9, or whose `runner.toml` does not open a listed network to the project, is the API's `bad_request` with its reason; the deploy plan adds `also joins shared network(s): <names>`. Operator steps (the `shared_networks` key in the host's `runner.toml`, set by its administrator (root), and upgrading the agent to 0.2.9 first) are in bot-agent `docs/install.md`, section "Shared networks".

Value requests (api-v1 v1.28, spec rev 2). `request_env_value` (`project_id`, `set`, `key`, `reason?`) asks the signed-in person to enter one env value on the console page `/fill/<id>`; `get_env_value_request` (`request_id`) reads its state (`pending`, `filled`, `declined`, `expired`). Both descriptions start: "Secret values are never sent through this tool or shown to you." Arguments are checked before the API is called (UUID, set name, key rule, reason at most 200 characters with no control, format or separator characters; there is no value argument). Every client ends with the link as text and a structured result of `request_id`, `url`, `expires_at` and `elicitation` (`not_supported`, `accepted`, `declined` or `cancelled`). A client on MCP 2026-07-28 whose per-request capabilities declare `elicitation.url` first gets an input-required result (SEP-2322) with one URL-mode elicitation (`elicitationId` = the request id) and a `requestState`; its retry reads the request's state (added as `state`, and worded per state: pending with its expiry, filled, declined or expired) and never creates a second request. A 2025-11-25 client gets the link only: this gateway is stateless and cannot send `elicitation/create`. A `decline` or `cancel` answer is reported, and the request stays open until it expires. Asking again for the same key replaces the earlier request, whose link then answers expired (api-v1 v1.28 rev 3). The API `url` is shown only when it ends in `/fill/<request_id>` with no query, fragment or user info. The create conflict keeps its key name (the generic redaction would read `KEY already` as `KEY=value`).

File requests (api-v1 v1.30, spec `docs/spec-file-request.md`). `request_file` (`project_id`, `name`, `reason?`, `secret?`, default secret) asks the signed-in person to add one managed file on the console page `/fill-file/<id>`, by pasting it or picking a local text file; `get_file_request` (`request_id`) reads its state. Both descriptions start: "File contents are never sent through this tool or shown to you." There is no content argument; the name must follow the v1.9 rule. Results, the 2026-07-28 URL input request and its retry (which reads the state and never creates a second request), the link-as-text fallback for every client and the url check (it must end in `/fill-file/<request_id>`) work exactly as for `request_env_value`. The create conflicts (file exists, too many open file requests, too many files) reach the agent unchanged; the file-exists text keeps its file name even when the generic redaction would read a name such as `credentials.json` as a secret. `check_readiness`'s next step for an `add_file` fix now names `request_file`.

Automatic project settings (api-v1 v1.29, spec `docs/spec-settings-automatic.md`). `check_readiness` (`project_id`, exactly one of `entry` or `spec`, `host_id?`) returns the readiness checks (`env_sets`, `env_values`, `env_refs`, `files`, `registry`, and with `host_id` `host_access`, `host_online`, `host_images`, `host_policy`, `networks`), each with a status (`ok`, `missing`, `warn`, `unknown`), a message, a fix and, when not ok, a `next` step: `fill_value` points to `request_env_value` and `create_env_set` to `create_env_set`; `add_file` to `request_file` (since v1.30) and `connect_github` to `connect_registry` (v1.31); a registry login and deploy access are things to ask the person to do in the console; `host_policy_snippet` points to the tool of that name. `image_access` (`project_id`, `image`) says `public`, `private_ok`, `private_no_login`, `login_failed`, `not_found` or `unknown`, and which login is stored. `host_policy_snippet` (`project_id`, `entry`, `host_id`) returns the `runner.toml` lines and the `install.sh` command for the host's root to apply. All three are read-only, start "No env value, secret preview or registry token is ever returned by this tool.", and rebuild their results from allowlisted fields, so nothing else the API might send reaches the agent. A `deploy_entry` refusal ends with a pointer to `check_readiness`. Connect GitHub itself, the callback and Disconnect are console only.

Connect GitHub from chat (api-v1 v1.31). `connect_registry` (`project_id`, `registry` = `ghcr.io`, `reason?`) asks the signed-in person to connect GitHub for the project on the console page `/connect/<id>`, where they continue to github.com and approve `read:packages`; `get_registry_connect_request` (`request_id`) reads `pending`, `connected`, `declined` or `expired`; for the last two it adds that `check_readiness` shows whether ghcr.io got connected anyway (a person who finishes on GitHub after the request ended still connects). Both start "No registry token is ever sent through this tool or shown to you." and allowlist their results, so no token (or anything else the API might add) reaches the agent. As `request_env_value`, the link is always in the text; a 2026-07-28 client that declares `elicitation.url` also gets a URL input request, and its retry reads the state without a second create. `check_readiness` now names `connect_registry` as the next step for a `connect_github` fix.

Routes (api-v1 v1.35). `set_routes` (`project_id`, `entry`, `routes`, `idempotency_key`) replaces an entry's public routes (`hostname`, `path_prefix?`, `port`, `client_ip_from?` `cloudflare`, `no_store_paths?`) and returns the API plan, which names every address that goes live or stops; nothing changes until `confirm`, whose result lists the entry's routes and their state. `list_routes` (`project_id`, `entry?`) reads them. Domains and the host edge switch are console only. `list_hosts` says whether each host's edge is on, and `check_readiness` knows the `routes` check.

## Deploybot

```bash
go run ./cmd/deploybot login --api https://<api>   # from the repository root
go run ./cmd/deploybot logout
```

`--api` overrides `DEPLOYBOT_API_URL`. `--client-name` defaults to `deploybot`. `--print` writes the token to stdout instead of the token file. `--insecure-http` allows an `http` API URL that is not loopback. Exit code 2 means the device code expired. Exit code 3 means the user denied it.

`logout` sends the saved token only to the `api` stored in the token file. It deletes the file when signout succeeds or returns unauthorized. Any other signout failure keeps the file. `--force` deletes the local file anyway. An `--api` value or `DEPLOYBOT_API_URL` that differs from the saved issuer (trailing slashes ignored) is refused and the token is not sent.

## Use with Claude Code

Once OAuth is live, add the server with no token header. Claude Code discovers the protected-resource metadata and signs in in the browser:

```bash
claude mcp add --transport http deploybot https://<mcp>/mcp
```

`deploybot login` stays the headless fallback for clients without a browser:

```bash
deploybot login --api https://<api>
claude mcp add --transport http deploybot https://<mcp>/mcp --header "Authorization: Bearer $(python3 -c 'import json,pathlib; print(json.loads(pathlib.Path.home().joinpath(".config/deploybot/token").read_text())["token"])')"
```

The header is the `token` field. The file also stores the API base URL, so the raw file is not a bearer token. The MCP server exchanges that token; it does not forward it to the API.

Agent usability round 1 (api-v1 v1.32, spec `docs/spec-agent-usability-1.md`). `confirm` passes the API's state texts through: the caller's own expired plan is `conflict: this confirmation expired; call the tool again for a new one`, a used one `conflict: this confirmation was already used`; another user's or an unknown id stays `not_found: not found`. `entry_status` takes `host_id` optionally: without it, the tool reads the project services list (`view=deploybot`, 200 per page, at most 5 pages) and uses the one host where the project's copies of the entry run (rows with that `catalog_entry`, not gone); with several hosts it answers `bad_request: <entry> runs on N hosts: name (id), …; pass host_id`, and with none `bad_request: no running copy of <entry> was found in this project; pass host_id (list_hosts lists the project's hosts)`; when a cursor is still set after 5 pages the list is cut short, so it picks nothing and answers `bad_request: this project has too many services to pick a host automatically; pass host_id (list_services with project_id shows where the entry runs)`. None of these contacts a host. `check_readiness` with `spec` (the ImageSpec `create_catalog_entry` takes, validated the same way first) calls `POST /v1/projects/{id}/catalog/readiness` and stores nothing; env sets, keys and files the spec names may still be missing and show as checks. `request_env_value`, `request_file` and `connect_registry` put the link alone on the first line of their text, and their descriptions ask the agent to list several links together, with their expiry, in one message.

Agent usability round 2 (api-v1 v1.33). `update_env_set` (`project_id`, `name`, `idempotency_key`, and at least one of `set` (plain keys only), `add` (as `create_env_set` keys), `remove`, `make_secret` (a plain key with an empty value is refused, `bad_request: a secret value cannot be empty; give KEY a value first`; an empty placeholder may still be made secret)) and `delete_env_set` (`project_id`, `name`, `idempotency_key`) return a plan to `confirm`, like `create_env_set`; the confirm result is the set's names and flags, or `deleted env set NAME.`. `list_env_sets` asks for private sets too (`?include=private`) and shows each set's `used_by` and, for an entry's private set `@<entry>`, its `entry`. `create_catalog_entry` and `update_catalog_entry` accept in `spec.secret_env` `{"fill": true}` or `{"generate": {"kind", "length"?}}` for a secret only that entry uses; `request_env_value` takes `entry` instead of `set` for such a key, and may name a secret key that already has a value (the person replaces it). `check_readiness` knows `env_pairs` and, for a missing private key, names `request_env_value` with `entry`; with `spec`, the object forms are sent as given, and a fill key's next step is `request_env_value` with the new entry's name after `create_catalog_entry` and `confirm`. `shared_network_snippet` (`project_id`, `host_id`, `network`, `subnet`?) returns the `runner.toml` lines a host's root adds to open a shared network to the project. `confirm` ignores `project_id` without `entry` (an env set or catalog-entry plan); `entry` without `project_id` is `bad_request`.

Update awareness (spec `docs/spec-update-awareness.md`, api-v1 v1.34). The server version (`serverInfo.version`) is the newest release in the repository's `CHANGELOG.md`, embedded at build time by the root package `changelog`; there is no hand-edited version in `run.go`. The `initialize` result carries server instructions: one sentence on Deploybot, then `Server vX.Y.Z (date). New in this release: <up to 3 items>. Call whats_new for the full list.` The read-only tool `whats_new` (`count` 1–10, default 3; anything else is `bad_request: count must be 1–10`) answers `{"version","entries":[{"version","date","items"}]}` from the same file, newest first, and makes no API call. `list_hosts` passes each host's `latest_agent_version` and `update_available` through (the API sends `update_available` false for a revoked host), and its summary adds ` (agent update available: X.Y.Z)` for a host with `update_available`.
