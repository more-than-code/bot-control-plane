# MCP gateway (`mcp/` in bot-control-plane): design

**Date:** 2026-10-13. **Status:** Approved design (D1–D31), wave 1 = phase 1.
Cross-repo design: umbrella `docs/design-bot-agent-deploy.md` §7. Contracts: `../docs/contracts/api-v1.md`, `../docs/contracts/oauth-v1.md` at the repository root.

## Layout

Paths are relative to `mcp/`; the binaries are built at the repository root: `cmd/deploybot-server` (`deploybot-server mcp`, or called as `bot-mcp-server`) and `cmd/deploybot` (the CLI).

```
run.go                Run(ctx, args): MCP server, Streamable HTTP at /mcp, GET /health
cli/                  CLI: `deploybot login` (device flow), `deploybot logout`
internal/apiclient/   typed client for api-v1 (delegated bearer on /v1)
internal/tools/       one file per tool; schemas and handlers
```

## Auth

- **Host allowlist.** Before the token exchange, `/mcp` accepts a `Host` that is the `BOT_MCP_PUBLIC_ORIGIN` host, compared case-insensitively: the bare name or the scheme's default port (`443` for https, `80` for http), or exactly the port when the origin names a non-default one (an explicit default port counts as none). It also accepts `localhost`, `127.0.0.1`, and `[::1]`, with or without a port. Any other `Host`, including an empty one, is HTTP 403 `forbidden: invalid Host header`. The handler does not call the exchange, and it does not log or return the header value. The SDK's localhost protection is disabled because this list replaces it, so a proxy can pass the public `Host` through to the loopback listener. A Caddy `header_up Host` line is not needed. `/health` and `/.well-known/oauth-protected-resource` are not checked.
- **Access log (2026-10-27).** `withAccessLog` wraps `/mcp` outside the Host check, so refusals are logged too: one `request` line with `method`, `status`, `ms`, the JSON-RPC `rpc` method and, for `tools/call`, `tool`, plus `client_closed=true` when the request context ended before the handler returned and `aborted=true` on a handler panic (the line is written in a `defer`, then the panic continues). It does not read the body itself: a capturing reader keeps a copy of the first 64 KiB the SDK reads, and the method is parsed after the handler returns, only if the body was read to EOF within that limit. So a request refused before the SDK (Host, token) is never read and gets no `rpc`. `rpc` must match `^[a-z][A-Za-z_]{0,31}(/[a-z][A-Za-z_]{0,31}){0,3}$` (else `other`; a shape rather than a fixed list so newer protocol methods such as `server/discover` and `subscriptions/listen` stay visible), `tool` must match `^[a-z][a-z0-9_]{0,40}$` (else `other`), and the HTTP method is one of five (else `other`), so a client cannot choose what the log says. Headers, tokens, ids and arguments are never logged. The status writer ignores 1xx headers, and implements `Unwrap` and `Flush`, so `withWriteBudget`'s `http.ResponseController` deadline still reaches the connection. Checked: a request outliving the server `ReadTimeout` is not flagged `client_closed` (the stdlib clears the read deadline before watching for EOF; `TestAccessLogLongRequestNotClientClosed`). Added to tell client cancellations (Caddy `aborting with incomplete response`) apart by method, Daikou feedback item 12.
- Every MCP HTTP request must carry `Authorization: Bearer <token>`. Missing → HTTP 401 with `WWW-Authenticate: Bearer resource_metadata="<origin>/.well-known/oauth-protected-resource"`.
- `/.well-known/oauth-protected-resource` names the API origin (scheme, host, port) as the authorization server and advertises `scopes_supported: ["deploybot"]`. `BOT_MCP_API_URL` must be that origin: a path other than `/`, a query, or a fragment is refused at startup. Browser clients use the authorization-code flow (`docs/spec-mcp-oauth.md`, contract `../../docs/contracts/oauth-v1.md`). `deploybot login` stays the headless fallback.
- **Token scope (umbrella D35, confirmed by Joe):** a token is a session of the user's account (`app.sessions`, no project column). It reaches exactly the projects the user belongs to, with the user's role in each (since api-v1 v1.24 also the projects of an org where the user is owner or admin, as `admin`), checked live by the API's `authz.Authorize` on every call (non-member → `not_found`, role too low → `forbidden`). This is intended; there are no per-project tokens.
- **Token exchange (umbrella D36 ended).** The server holds one client secret (`BOT_MCP_CLIENT_SECRET_FILE`, mode 0600, at least 32 characters, client id `bot-mcp-server`; or, since api-v1 v1.50 item 2 for containers, the env value `BOT_MCP_CLIENT_SECRET` with the same one-line, 32 to 4096 byte rule; both set refuses to start with `BOT_MCP_CLIENT_SECRET and BOT_MCP_CLIENT_SECRET_FILE are both set; set only one`) and never acts without a user token. For every `/mcp` request it exchanges the caller token at the API origin (`POST /oauth/token`, `client_secret_basic`, token-exchange grant, `resource` = API origin) unless a cached delegated token exists. The cache is in memory, keyed by SHA-256 of the caller token, expires 30 seconds before `expires_in`, and drops the oldest entry past 10 000. At most 256 exchanges run at once; one more distinct caller token is HTTP 503 and is not sent to the authorization server. A subject refused with `invalid_grant` or `invalid_request` is remembered for 60 seconds (same SHA-256 key, at most 10 000, oldest dropped) and answered 401 with no further exchange. A transport error or a 5xx is not remembered. `/v1/*` is called with only the delegated token. The caller token is not sent upstream and is not passed to tool code. Exchange `invalid_grant` or `invalid_request` → HTTP 401 with `WWW-Authenticate: Bearer error="invalid_token", resource_metadata=…` before any MCP handling. An unreachable authorization server or a 5xx → HTTP 503, so the client does not discard its token. A 401 from the API during a tool call drops that cache entry and is still a tool error `unauthorized: <msg>` (HTTP 200): the MCP Go SDK v1.8.0 cannot return HTTP 401 from inside a tool result. Any other API error becomes a tool error with the API's `code` and `msg`. Neither token nor the client secret is logged.

**Organizations (api-v1 v1.24, spec `docs/spec-organizations.md` §4.4).** Read-only. `list_orgs` returns only the `orgs` array of `/v1/me`; an older API without it gives an empty list and the summary `0 orgs: this API predates organizations`, and a malformed body is a tool error, not an empty list. Host summaries read `access_level` (project list) or `access` (org list). The `relation` and `share_level` fallback was removed with those fields in api-v1 v1.26. There is no MCP tool for org, member, join-token, host-access or credential writes; the API refuses delegated sessions on those routes (v1.24 item 10), and only `GET /v1/me`, `GET /v1/orgs/{id}`, `GET /v1/orgs/{id}/projects` and `GET /v1/orgs/{id}/hosts` are delegated reads.

Shared networks (api-v1 v1.25). `create_catalog_entry` and `update_catalog_entry` accept `spec.networks`: 1–4 unique names matching `^[a-z0-9][a-z0-9-]{0,31}$`, or null; an empty array, a bad name, a duplicate or more than 4 is refused before the API is called (leave the field out for none). The API stores `[]` and null as absent. `list_catalog` returns `networks` for every image, `null` when unset (api-v1 v1.25 amendment A4), so a listed entry can be written back as it is. The `list_hosts` summary adds the shared networks the API returned for the caller, as `srv-01 online (deploy) (shared networks: dd 10.200.10.0/24)`; for a delegated session the API sends only the networks open to the project in view, with name and subnet and no member list, and an empty list on `org_id`. A deploy or rollback of an entry with `networks` to a host whose agent predates 0.2.9, or whose `runner.toml` does not open a listed network to the project, is the API's `bad_request` with its reason; the deploy plan adds `also joins shared network(s): <names>`. Operator steps (the `shared_networks` key in the host's `runner.toml`, set by its administrator (root), and upgrading the agent to 0.2.9 first) are in bot-agent `docs/install.md`, section "Shared networks".

Ports, volumes and files (`internal/tools/spec_mounts.go`). The write schema of `create_catalog_entry`, `update_catalog_entry` and `check_readiness` gives `spec.ports`, `spec.volumes` and `spec.files` full item schemas: a port is `{host, container, public?}` (integers 1–65535, at most 16, host ports unique; `public` false, the default, binds 127.0.0.1 and true binds 0.0.0.0, which needs `allow_public_ports` in the host's `runner.toml`), a volume `{name, target, read_only?}` (at most 8) and a file `{file, target}` (at most 16). The same rules (ImageSpec rules 4, 8 and 13) are checked before the API is called, so a refusal names the item and field, such as `ports[0] is a string; each port is {...}` or `ports[0].host_ip is not a field: ...`, and gives the accepted shape, instead of the API's bare `invalid ports`. A file target that overlaps a volume target is refused locally too. Only `unknown file` (the file is not in the project) is left to the API. No message echoes a value; an unknown key is named only when it is a plain `[a-z_]` word. The API keeps its own checks and messages.

**Value requests (api-v1 v1.28, spec `docs/spec-env-request-value.md` rev 2 §3.1 step 3 and §3.4).** `request_env_value` is registered with `server.AddTool` directly (not `addTool`) because it reads `req.ProtocolVersion()`, `req.ClientCapabilities()` (per request on 2026-07-28) and the retry's `RequestState` and `InputResponses`. Only on 2026-07-28 or later, with `elicitation.url` declared, does the first call return `InputRequests{"open_fill_page": url elicitation}` with no content (the SDK refuses a result that has both) and `RequestState` = base64url JSON of the request id and url. The retry decodes that state (the id must match the 43-character pattern and the url must end in `/fill/<id>`, else `bad_request` before any API call), reads `GET /v1/value-requests/{id}` (the API answers only the person who asked), refuses a state whose set or key differs from the arguments, and returns the link text with the state. The state names nothing the agent does not already see, so it is not signed. Older protocols never get an input request: on this stateless gateway the SDK's server middleware would try to deliver it as `elicitation/create` and fail. `TestRequestEnvValueThroughGateway` runs both protocols through the real handler. `get_env_value_request` allowlists the ValueRequest fields; anything else in the API body is dropped.

**Request tools, shared parts (`internal/tools/requests.go`, 2026-11-16).** `request_env_value` and `request_file` are registered with `addElicitingTool`, which reads the protocol version, per-request capabilities and a retry's `RequestState` and `InputResponses` into a `requestCall`. A `requestKind` per type (`valueRequestKind`, `fileRequestKind`) holds what differs: the rule sentence, the title, the console page and API read path, the done state (`filled` for both; `stateOK` allowlists pending, declined, expired and that), the done and expired sentences, the noun and the check tool. It parses the 201 body (the url must end in `<page><id>`), decodes the retry state (so a value-request state is refused by request_file and the other way round), builds the input-required result and the final result and summary. Since api-v1 v1.32 (spec agent-usability-1 F1) both summaries (`requestKind.summary`, `connectSummary`) start with the link alone on the first line, and the three request descriptions include `severalLinks` (list several links together, with their expiry, in one message). `keepFixedMessage(fail, code, fixed)` restores a fixed create conflict that the generic redaction would mangle: `KEY already has a value; edit it in the console`, and `file NAME already exists; replace it in the console` for names such as `credentials.json`.

**No URL input requests (2026-11-23, DD 8hp8).** `request_env_value`, `request_file` and `connect_registry` no longer return `InputRequests` to any client: the first call answers with the link text and the structured result (`elicitation` `not_supported`). A client that showed the URL elicitation but got no answer from the person (an agent's user away, or on a phone) held the call until its own time limit, never got the result, and a retry replaced the link. The paragraphs here that describe the 2026-07-28 input request record what was built before; `wantsURLInput`, `inputRequired` and the elicitation messages are gone. `addElicitingTool` still reads a retry's `RequestState` and `InputResponses`, so a retry carrying a state an older gateway sent still reads the request and creates nothing (`Test*LegacyRetry`); `Test*NoInputRequest` and the `*ThroughGateway` tests check that a 2026-07-28 client declaring `elicitation.url` is never elicited and gets one create. The frozen api-v1 text records this as v1.28 item 10, and v1.30 item 9 and v1.31 item 10 point to it.

**File requests (api-v1 v1.30, spec `docs/spec-file-request.md` §3.4, `internal/tools/file_requests.go`).** The retry reads `GET /v1/file-requests/{id}` and refuses a state whose project or file name differs from the arguments. `get_file_request` allowlists the FileRequest fields (`request_id`, `project_id`, `name`, `secret`, `state`, `expires_at`, `created_at`); anything else in the API body, such as content, is dropped. `check_readiness` turns an `add_file` fix with a valid v1.9 name into "call request_file with project_id P and name N; the person adds the file in the browser." `TestRequestFileThroughGateway` runs both protocols through the real handler.

**Connect requests (api-v1 v1.31, `internal/tools/connect_requests.go`).** `connect_registry` is registered with `addElicitingTool` and uses `connectRequestKind` (done state `connected`) for the shared create check, input request, state and read path (`requests.go`); its summary text is its own (`connectSummary`), because a connect is approved, not filled: the first call posts `POST /v1/projects/{id}/registries/github/requests` with `{}` or `{"reason"}`, checks the answer's id and that its url ends in `/connect/<id>` (no query, fragment or user info), and returns either the link text or, on 2026-07-28 with `elicitation.url`, the shared `InputRequests{"open_fill_page": url elicitation}` with the state (base64url of id and url). The retry decodes the state (refused before any API call when the url is not a connect url), reads `GET /v1/registry-connect-requests/{id}`, refuses a state of another project, and returns the link text with the state. `registry` is checked against `ghcr.io` before any call. `get_registry_connect_request` allowlists the ConnectRequest fields (`registry` must be `ghcr.io`) and `last_failure` (api-v1 v1.39 item 2: `null`, or `reason` from the five known values, else the shape error, and `at`); `connectFailureText` puts the reason in plain words in the summary. `TestConnectRegistryThroughGateway` runs both protocols through the real handler with SDK clients and a fake API that plants a token field.

Phase 2 service actions (later wave): `service_logs`, `deploy_service`, `redeploy_service`, `run_service`, `stop_service`, `restart_service`. Catalog program actions are below.

**Readiness, image access and the host-policy snippet (api-v1 v1.29 items 6–8, `internal/tools/readiness.go`).** Three read-only, closed-world tools on the delegated token: `check_readiness` (`GET …/catalog/{name}/readiness`, `host_id` only when given; or, with `spec` instead of `entry`, `POST …/catalog/readiness` with `{"spec","host_id"?}`, api-v1 v1.32 item 3: exactly one of the two, the spec checked by `validateImageSpec` first, and its input schema built at init from `catalogWriteSchema`'s `spec` so the two stay the same; the summary calls it "This spec"), `image_access` (`GET …/image-access?image=`) and `host_policy_snippet` (`GET …/catalog/{name}/host-policy-snippet`). Arguments are checked first (UUIDs, the entry name rule, an image of at most 512 characters with no whitespace). Results are rebuilt, never passed through: a readiness row keeps `check` and `status` from fixed lists, the message (the v1.27 env texts and `env K in set S does not exist` unredacted, as they name keys only; anything else through `publicString`), and a fix with its action from a fixed list and only `set`, `key`, `name`, `registry` and `host_id` that match their rules; image access keeps three enum or host fields; the snippet keeps the pattern and the project slug (`^[a-z0-9][a-z0-9-]{0,79}$`, as `store.Slug`) that match their rules and rebuilds the `runner.toml` lines and the command from them (the note is redacted). Each non-ok row gets a `next` step (`add_file` names `request_file` since v1.30), and the summary text lists them. The MCP gateway has no console origin, so the steps name the console place ("project Settings, Registries") without a link. `deploy_entry` adds "Run check_readiness …" to an API refusal (`bad_request`, `forbidden`, `unavailable`); transport errors are unchanged. `image_access` is allowed by the org-tool name guard by name: it reads registry access, not org or host access.


## Local plans (api-v1 v1.49)

Some writes (agent upgrades and alert settings) are accepted by the API directly from a delegated token, with the API's own role check, and keep no plan in the API (its state stays in Postgres so it can run on more than one node). For those the confirm step lives here. `internal/tools/local_plans.go` is a small generic store (`localPlans[T]`, created with a TTL and a noun): `add` keeps a value under a random 43-character id (the `confirmation_id` pattern), bound to the caller (`auth.CallerKeyFromContext`, the SHA-256 of the caller's token that `RequireDelegated` sets; never the token) and to the call's `idempotency_key`; at most 10 pending per caller and 1000 per store, for the store's TTL. `take` answers only the caller who made the plan: another caller's id, or one this server did not issue, falls through to the API's `POST /v1/confirmations/{id}`; a wrong key keeps the plan; a plan is used once. `confirm` checks the local stores before the API. An MCP restart drops pending plans.

Users: `upgrade_agent` (`pendingUpgrades`, `localPlans[upgradePlan]`, `confirmUpgrade`; api-v1 v1.48) and `set_alert_settings` (`pendingAlertSettings`, `localPlans[alertSettingsPlan]`, `confirmAlertSettings`; v1.49). Each store has its own TTL (both 10 minutes) and its own noun in the refusals ("too many pending upgrade confirmations"). `confirm` asks the upgrade store, then the alert-settings store, then the API.

`list_catalog` returns only `{"items":[...]}`. A program item is `name`, `kind`, `command_display`, `last_deployed_at`, and `my_actions` (strings only, except `last_deployed_at`). Every item, program or image, has `last_deployed_at` (api-v1 v1.21): the API string when it parses as RFC3339, otherwise null, including when the API omits the field (an older API); a bad value never fails the call. The catalog-write `confirm` projection does not include it. An image (`kind` `image`) also returns the image reference (`spec.image`, otherwise `command_display`), `image_kind` (`service` or `job`), ports (`host` and `container` only when they are numbers, `public` only when it is a boolean), volume short names, managed file names (api-v1 v1.9 `spec.files[].file`), env key names (plain and secret, sorted, no values), env set names, `healthcheck` (true when `spec.healthcheck` is an object, otherwise false; the argv is not returned), `logging` (`max_size_mb` and `max_files` when both are integers, otherwise null), and `networks` (the string names in `spec.networks`, `null` when absent or empty, so the entry can be written back; api-v1 v1.25 amendment A4). `my_actions` includes `deploy` when the API grants it. Command, entrypoint, user, volume targets, file targets and contents, restart, memory, and every other catalog field are dropped. A body that is not an object with an `items` array is `error: catalog response was not usable` and is not returned. Kept strings have control characters replaced. list_catalog returns no env values. There is no container remove tool and no registry tool. `create_env_set` and `list_env_sets` (api-v1 v1.27 items 4 and 5) are the env-set tools: `create_env_set` validates `{project_id, name, keys:[{key, generate?, is_secret?, value?}], idempotency_key}` before the API (1–64 distinct keys matching the env key rule, generate kind and length rules, no `is_secret: false` with `generate`; `value` only with `is_secret` explicitly false and no `generate`, at most 4096 bytes with no NUL, CR or LF, api-v1 v1.32 item 2; the plan and confirm result never carry it; the API's reminder sentence for a plain value under a secret-looking key name arrives inside the plan, and the description asks the agent to tell the person before confirming) and returns the plan like a catalog write (`confirmationCatalog`). `list_env_sets` (`project_id`, optional `name`) and an env set `confirm` result (HTTP 201 whose body has `keys` and no `kind`, `envSetPayload`) pass through `projectEnvSet`, an allowlist of `name` and each key's `key`, `is_secret`, `needs_value` and `reveal_pending`, so a value or preview never reaches a tool result even if the API sent one. An API `bad_request` whose message is exactly one of the v1.27 env refusals (`envRefusalPatterns`: the item 6 needs-value text and the item 7 reference texts, key and set names only, and the v1.39 item 4 inline-env refusal `<KEY> looks like a secret: put it in secret_env or in a secret env-set key`) is passed through without the keyword redaction, which would otherwise read `SMTP_PASSWORD in` as a secret pair and hide the key to fix; any other message is redacted as before. `create_catalog_entry`, `update_catalog_entry`, and `delete_catalog_entry` (api-v1 v1.12) return the API plan and a confirmation id and do not change the catalog. The plan keeps inline env values and `secret_env` sources. Control characters in it are replaced. It is shown in full up to 4278903 runes. A longer plan is an error (`plan too long to show`) and returns no confirmation id. Nothing changes until `confirm`. Their descriptions start with "Image entries only"; program entries are created, edited and deleted in the console. Secret env values belong in env sets entered in the console. `confirm` of a catalog write does not contact the host. HTTP 201 is the created entry and HTTP 200 with an entry is the replaced entry, both projected like one `list_catalog` image item. HTTP 200 with a null payload says the entry was deleted. Env values, secret_env values, and file contents are not returned. Running containers are not stopped.

Rolling an image entry forward (no API change; uses the v1.24.1 GET-then-PUT round trip). `get_catalog_entry` reads one entry with GET `/v1/projects/{id}/catalog/{name}`. For an image it returns `name`, `kind`, `command_display`, `last_deployed_at`, `my_actions` and `spec`: the ImageSpec keys `update_catalog_entry` accepts (`imageSpecKeys`), with `ports` kept to `host`, `container`, `public`; `volumes` to `name`, `target`, `read_only`; `files` to `file`, `target`; `healthcheck` to `test` and its four timings; `logging` and `health_policy` to their documented keys. Inline `env` values are returned (they are plain by rule; the update plan already shows them), `secret_env` as its `<set>.<KEY>` references, never a secret value, a file content, `spec_hash` or `private_keys`. Strings have control characters replaced and the result passes the usual line redaction. A program returns what `list_catalog` shows for it. `set_entry_image` reads the entry the same way, refuses a program entry (`bad_request`, programs are edited in the console), replaces only `spec.image` in the stored spec (every other key is sent back byte for byte, including keys the MCP does not know) and PUTs it as `update_catalog_entry` would. The API's update plan names only the changed field (`image: old → new`), and the API's spec_hash check at confirm refuses the write if the entry changed in between. `image` is 1–1024 bytes with no whitespace or control characters; the API parses the reference. After `confirm`, `deploy_entry` runs the new image; `rollback_entry` still takes only a digest the entry deployed before. `list_image_tags` (api-v1 v1.46) lists the tags to choose from: see below.

Listing image tags (api-v1 v1.46 item 1). `list_image_tags` takes `project_id` and exactly one of `entry` (an image entry: GET `/v1/projects/{id}/catalog/{name}` gives the stored image; a program entry is refused before any registry call) or `image` (1–512 bytes, no whitespace), and `limit` (1–50, default 20). It calls GET `/v1/projects/{id}/image-tags?image=<ref>` (owner or admin; the API ignores the tag and digest) and keeps, for each item whose tag passes the v1.16 tag rule, `tag`, `image` (`<repository>:<tag>`, ready for `set_entry_image`), `updated_at` when the API sent one (normalised to RFC 3339 UTC; an unparseable time fails the call) and, with `entry`, `current` (the tag equals the stored image's tag). The result also has `repository`, `order` (`time` or `name`; an API before v1.46 sends none and gets `name`), `truncated` (the API's flag, or the limit cut the list) and, with `entry`, `current` (the stored image). The summary says whether the order is push time or version name, so an agent does not call a name-sorted first tag the newest. Deploys stay on `set_entry_image`, `confirm` and `deploy_entry`.

Docker health (api-v1 v1.11 and the v1.13 admin edit). `list_services` passes `health.source` through and the summary says Docker health when it is `docker`. `get_health_checks` keeps `status`, `last_checked_at`, `latency_ms` (including null), and `source` (`docker`, `check`, or null), and drops every other health field. `service_health_history` returns the API rows, including `protocol` `docker` with null `check_id`, `port`, `http_status`, and `latency_ms` and result `unhealthy`. `create_catalog_entry` and `update_catalog_entry` accept `spec.healthcheck` (`test` is 1–32 strings of 1–1024 bytes; `interval_sec` 5–300, `timeout_sec` 1–60, `retries` 1–10, `start_period_sec` 0–600; all optional except `test`). `test` is the command and its arguments; a first item of exactly `CMD`, `CMD-SHELL` or `NONE` is refused locally with the API's v1.18 message, and a later item with those words is allowed. The API checks timeout against interval, rejects a job, rejects NUL, and fills defaults. `update_catalog_entry` says an owner or admin may replace the entry. A catalog-write plan is still shown as the API wrote it. `entry_logs` still keyword-redacts lines, so `abcd…` and `••••` pass unchanged. Container logs (api-v1 v1.14) default to 10 MB × 3 files on Deploybot; `create_catalog_entry` and `update_catalog_entry` accept optional `spec.logging` with `max_size_mb` (1–100) and `max_files` (1–10), and `list_catalog` returns that object or null. `spec.health_policy` (api-v1 v1.15, services only) on `create_catalog_entry` and `update_catalog_entry` takes optional `on_deploy_failure` (`rollback` default, `stop`, `keep`), `on_unhealthy` (`none` default, `restart`, `rollback`; needs `spec.healthcheck`), `unhealthy_after_sec` (15–600, default 45) and `max_actions_per_hour` (1–10, default 3); a job, a missing healthcheck, or `on_unhealthy` combined with `on_deploy_failure` `keep` is refused locally. `list_catalog` returns `health_policy` for a service (the stored values with defaults filled in) and null for a job. Deploy history rows can have outcome `auto_restarted`, `auto_rolled_back` or `auto_gave_up` from the agent (no user); the short deploy history (`deploy_entry` plan) lists non-automatic rows only.

`run_entry`, `stop_entry`, `restart_entry`, `deploy_entry`, `rollback_entry`, and `set_health_checks` are real and audited. They do not act. `set_health_checks` replaces every health check on a service. The caller passes `idempotency_key`, and the PUT body is `{"checks","idempotency_key"}`. `confirm` must use that same key; a different key is refused and nothing changes. `expect_status_min` and `expect_status_max`, when set, are 200–399. Nothing changes until `confirm`. Checks connect only to 127.0.0.1 on the host. Read the current checks with `get_health_checks` first. The set replaces all checks. `get_health_checks` returns `health_checks`, `name`, `ports`, and `health`, and drops every other field. A `set_health_checks` plan is shown in full up to 10886 runes. A longer plan is an error (`plan too long to show; send fewer checks`) and is not shortened. Run, stop, restart, deploy, and rollback still cap a plan at 1024 runes. `confirm` of a body with a `checks` array reports how many health checks were set and keeps only HealthCheck fields, whatever other keys the body has. The 202 result is the same plan and confirmation id as the catalog actions. Deploy and rollback require the deploy permission, and the host must run containers; the API enforces both. The API answers **202** `{"confirmation_id","plan","expires_at"}`. Any other status on those tools, including 200, is a tool error (`expected a confirmation`) and is not shown as a result. The 202 result shows the plan and the confirmation id and says nothing ran yet. The structured payload keeps only `confirmation_id`, `plan`, `expires_at`, `history`, and `force` when it is true. Run, stop, restart, deploy, and rollback redact `plan` and cap it at 1024 runes. A catalog-write plan is not redacted. An image deploy result keeps `deploy` outcome, digest, and exit code, `status`, and redacted `lines`. Other fields on those bodies are dropped. `digest` is `sha256:` plus 64 lowercase hex digits. `deploy_entry` then reads `GET …/deploys?host_id=` and attaches the newest 3 rows as `history` (`digest` full, `outcome`, `time` from `finished_at` or else `started_at`). The text shows a 12-hex digest. A failed history read still returns the plan. Rollback does not attach history. After the user agrees, `confirm` posts `{"idempotency_key"}`. Optional `project_id` and `entry` stay on the MCP call; both are required together when either is set. HTTP 200 for a program is the program status; right after a run or restart its ports and `started_at` can still be empty until the host's next status report, and the `confirm` description says so. HTTP 200 for a health-check confirm is how many checks were set; the structured body keeps HealthCheck fields and drops the rest. HTTP 200 for an image deploy is the outcome, short digest, exit code (including 0), and the last 3 log lines. The structured `lines` array still has the redacted tail. That call contacts the host. When `force` was true, the structured result has `force: true` and the plan says so. Logs and status never need confirmation. For an image, logs name the container and status reports container state, short digest, exit code, and restart count. `status.state` may be `unknown` when a deploy or rollback timed out; the text says unknown. Any other state is not shown. `entry_status`, and a confirm body that is only a status, return `error: status response was not usable` and do not return the body. On a deploy result the outcome stays and `status` is omitted. `deploy_entry` and `rollback_entry` still return only the 202 plan; the timeout status is on the `confirm` that completes them.

Inputs are refused before the API call: `entry` matches `^[a-z0-9][a-z0-9-]{0,47}$`, ids are UUIDs, `idempotency_key` is 1–128 characters from `[A-Za-z0-9._:-]`, `confirmation_id` is 43 base64url characters, `digest` matches `^sha256:[0-9a-f]{64}$`, and `lines` is 1–1000 when set (omitted lines let the API default to 200). API errors pass through as `code: msg`, and `msg` is redacted with the same line redaction. Every `lines` array (logs, and `lines` on a confirm or status payload) is redacted with the agent-protocol v1.0.3 URL pattern and then the v1.0.2 keyword pattern, each line capped at 2048 bytes, total at most 64 KiB. A `lines` value that is not an array of strings is not returned raw: a string is redacted into one line, and any other shape is dropped. A shortened line or a dropped line sets `truncated`. The same 200-item list cap still applies after that.

The confirm that runs a deploy or rollback is synchronous and can take minutes. The API client keeps a zero `http.Client.Timeout` and sets a context deadline per call. The default stays 35s. `deploy_entry` and `rollback_entry` use that default: they only reserve a confirmation. `confirm` of a known program also uses it. `confirm` of an image, an unknown entry, after a failed catalog read, or without `project_id` and `entry` waits at most 50s (`apiclient.MaxCallTimeout`, changed from per-entry budgets of up to 4000s on 2026-10-16, Joe). MCP clients end tool calls after about a minute, so a pull plus health wait reached the caller as a transport timeout. The API runs deploy, rollback and remove on a context without cancel, so the action finishes on the host after the 50s and the entry's deploy history shows the result. Only that confirm maps a deadline (`postWithin` returns `deadline` true) to `error: still running on the host; deploy_history for that entry and host shows the outcome and why` (api-v1 v1.47; before, it pointed to deploy_entry's history). Since api-v1 v1.42 (spec-deploy-stuck §2.4) the history lists the running row first with `ends_by`. confirm does not know the host, so with `project_id` and `entry` `runningEndsBy` reads `GET /v1/projects/{id}/hosts`, then, in parallel, the deploy history of each `deploy`-access host within 3s (`runningLookupTimeout`; a project with more than 5 deploy hosts, `maxRunningLookupHosts`, gets no time and no history reads), and when exactly one first row is `in_flight` the text says `still running on the host, ends by HH:MM UTC at the latest; …`; otherwise it is the text without the time. The write deadline of such a confirm is extended by those 3s as well. Test: `internal/tools/running_ends_by_test.go`. A confirm without `project_id` and `entry` used the 35s default and a generic error until v0.2.34; an image recreate takes about 60s, so callers saw `api request failed` while the deploy finished (spec-release-v0234 §2.3). A program confirm without them still answers within the budget, since the API waits about 30s on the agent. The 202 text of `deploy_entry` and `rollback_entry` ends with `When you confirm, pass project_id and entry as well.` Other deadlines and transport failures stay `error: api request failed`. The HTTP server `WriteTimeout` is 70s. Only the confirm that is about to perform an image deploy or rollback, or whose budget is unknown (including a confirm without `project_id` and `entry`), extends that response's write deadline, to the budget plus 70s. A program confirm with `project_id` and `entry` and every other request stay at 70s. `/health` does not extend. A dropped client cancels the upstream call, which does not stop an image deploy, rollback or remove on the API. There is no cap on how many long confirms run together. `ReadTimeout` and `IdleTimeout` are unchanged.

Routes (api-v1 v1.35): `set_routes` validates the routes locally (at most 16, hostname, path, port, `client_ip_from` `cloudflare`, at most 8 `no_store_paths`), PUTs `/v1/projects/{id}/catalog/{entry}/routes` and shows the 202 plan like a catalog write but keeps its line breaks (`confirmationRoutes`: one address per line, not redacted, capped, other control characters replaced, an allowlist of confirmation_id, plan and expires_at). `confirm` of a routes plan (HTTP 200 with `entry` and `routes`) is summarized by `routesConfirmed`. `list_routes` reads the project or entry route list. `list_hosts` reads the host `edge` summary and `programs.edge`. The readiness allowlist includes `routes`. Tool count 39.

Agent upgrades (api-v1 v1.48, `internal/tools/upgrade_agent.go`). The API accepts MCP-delegated sessions on `POST /v1/hosts/{id}/agent-upgrade`, so the confirmation is kept by this server. `upgrade_agent {host_id, idempotency_key}` reads `GET /v1/hosts/{id}` and refuses locally when `latest_agent_version` is not an X.Y.Z (`bad_request`), `update_available` is false (`bad_request`), `agent_upgrade_allowed` is false (`unsupported_agent`, naming `agent_upgrade = true` in runner.toml and bot-agent 0.2.15) or `agent_upgrade` is `started` or `running` (`conflict`). Otherwise it keeps a plan in memory (`pendingUpgrades`, a `localPlans` store, see Local plans: a random 43-character id, the caller key, the host, the version read, the key; 10 minutes; at most 1000, and at most 10 per caller) and answers like a 202 plan (`finishConfirmation`: nothing ran yet, the id, the expiry and one plan sentence). It does not contact the host. `confirm` checks this store before the API: an id it holds with another key is `conflict` (the plan stays), an expired one is `conflict` with the API's expired text, and a match is used once and posts `{"version"}` with the 50 s budget (`MaxCallTimeout`, write deadline extended). A 202 returns `{"upgrade_id","state":"running","host_id","to"}` and says the result comes later through `list_hosts`; an API refusal passes through as `code: msg`; a deadline says the host has not answered yet. An id this server did not issue goes to `POST /v1/confirmations/{id}` as before. A restart of the MCP server drops pending plans. Each plan is bound to its caller: `auth.RequireDelegated` puts the SHA-256 of the caller's token on the request context (`auth.CallerKeyFromContext`; never the token), and `confirm` from another caller treats the id as not found (the plan stays). A caller whose MCP token is refreshed between the two calls asks again. Whether the caller is an org owner or admin is not visible on a delegated host read, so that check stays with the API at confirm. `list_hosts` passes `agent_upgrade_allowed` and `agent_upgrade` through (the payload is not projected), and its summary adds "; upgrade_agent can install it" or "; upgrades from Deploybot are off on this host" to the update hint (nothing when an older API sends no flag) and "(agent upgrade to X <state> (<reason>))" for the newest row. Tool count 45. Test: `internal/tools/upgrade_agent_test.go`.

## `deploybot login`

Device flow against `--api <base-url>` (or `DEPLOYBOT_API_URL`): request a code, print the URL and user code, poll at `interval` (honour `slow_down`), and save the token to `~/.config/deploybot/token` (mode 0600, directory 0700). `--print` prints the token instead of saving it. `deploybot logout` calls `/v1/auth/signout` and deletes the file.

**Agent usability round 1 (api-v1 v1.32, spec `docs/spec-agent-usability-1.md`).** `confirm` maps the API error through `fromAPI` like every tool, so the v1.32 item 1 texts (`this confirmation expired; call the tool again for a new one`, `this confirmation was already used`) reach the agent as written (`TestConfirmPassesStateTexts`). `entry_status` without `host_id` calls `entryHost` (`entry_status.go`): it reads the project services list with `view=deploybot&limit=200`, following `next_cursor` for at most 5 pages, keeps rows of this project whose `catalog_entry` is the entry and whose `gone_at` is null, and uses the single host it finds; if `next_cursor` is still set after the 5th page the list is incomplete, so it infers nothing and asks for `host_id` (too many services); with none or several it returns a `bad_request` tool error naming the hosts (names through `summaryField`, ids checked against the UUID pattern) and makes no status call. Tests use SDK clients over an in-memory transport against a fake API (`agent_usability_test.go`).

**Agent usability round 2 (api-v1 v1.33, `internal/tools/env_set_update.go`, `env_sets.go`, `value_requests.go`, `readiness.go`, `confirm.go`).** `update_env_set` sends `PATCH /v1/projects/{id}/env-sets/{set}` and `delete_env_set` sends `DELETE` with `{"idempotency_key"}`; both validate locally first (the update reuses `validateCreateEnvSet` for `add`, so a value only on a plain key) and present the 202 through `confirmationCatalog`. `actedOrPending` recognises the two confirm answers: `{"name","deleted":true}` exactly, and a set (keys, no kind) projected through `projectEnvSet`, which keeps names and flags only and now accepts `@<entry>` names, an `entry` that matches the name, and `used_by` names that pass the entry rule. `list_env_sets` adds `include=private`. `request_env_value` takes exactly one of `set` and `entry`; with `entry` it posts to `/v1/projects/{id}/catalog/{entry}/value-requests` and names the key `@<entry>.KEY` in its text, and `projectValueRequest` accepts a private set name. The readiness projection allows `env_pairs`, keeps an `@`-prefixed `fix.set`, passes the pair warning and the private-set env texts unredacted (fixed shapes with key and set names only), and maps a private `fill_value` to `request_env_value` with `entry`; a `fill_value` with a key and no set (a spec's private fill key) points to `request_env_value` after the entry is created, and its fixed message passes unredacted. `shared_network_snippet` calls `GET /v1/projects/{id}/hosts/{host_id}/network-snippet` and returns the snippet only when every line is a comment or one of the two allowed `runner.toml` shapes. `confirm` treats `project_id` alone as absent (unknown action, image budget) and refuses `entry` without `project_id` with a text that fits any plan.

## ImageSpec `network` (api-v1 v1.50 item 1)

`create_catalog_entry` and `update_catalog_entry` accept `spec.network`: `"host"` or null (schema `enum`, described in the schema and both tool descriptions). `validateImageSpec` refuses any other value and `"host"` together with a non-empty `networks` before the API is called; the value is forwarded unchanged and the API checks it again. `get_catalog_entry` returns it with the other ImageSpec keys (`imageSpecKeys`). The deploy, rollback and run gate (`409 unsupported_agent` when the host's `runner.toml` does not allow host networking for the project) is the API's; its message reaches the agent as the tool error. Tests: `internal/tools/network_host_test.go`, `config_env_secret_test.go`.
